回目录

6 站（数据流）主要落在 8 层中的哪一层
① 数据（读文件 + 动态组批）第 3 层·数据与存储
② 稀疏查表（key 分发/查表/回传）第 3 层·数据与存储（内部是五级流水）

④ loss 与梯度（全局 sum/N）第 3 层（动态组批的 loss 归一）
⑤ 反向 + 通信（梯度跨卡）第 2 层·通信 + 第 4 层·分布式策略
⑥ 更新（owner 更新稀疏表 + optimizer 更新稠密参数）第 4 层 + 第 3 层

横穿全程的四个横切层是：第 1 层·硬件与集群（所有站的物理基础）、第 5 层·调度与重叠（同样的搬运/通信如何少暴露等待）、第 6 层·算子与编译（单个 kernel/attention/MoE 内部如何少算、少搬、少 launch）、第 8 层·观测（每站怎么判断是否真的快）。它们不是训练 step 的先后站点，而是每一站都会受到的约束或验证口径。

项目一｜GR 分布式训练引擎建设与性能优化

回目录
04_projects/gr_distributed_training_engine.md

这个项目不是单纯“搭训练框架”，而是把零售推荐从传统 LRM 推向生成式推荐 GR 时，训练系统必须同时承载 TB/10TB 级稀疏 Embedding、B 级稠密 backbone、30B 级 MoE、复杂 Attention/MoE 算子、多硬件 GPU/NPU。项目主线是：先让超大稀疏和稠密模型训得起来，再通过通信重叠、算子优化、动态组批和观测闭环把它训得更快、更稳定。

项目拆解：稀疏表、稠密/MoE、算子硬件三条链一起打通

回目录

第一条是稀疏表链路，目标是让 TB/10TB 级 embedding 表能训练：

  • 问题：稀疏参数量远超单卡 HBM，不能把全表搬进设备。
  • 机制：全量参数按 key 分片放在 owner rank 的 host MEM；HBM 只放当前/下一窗口工作集。训练时 sample rank 发 key，owner rank 查向量，反向后 embedding 梯度再回 owner 更新。
  • 加速点：稀疏 Embedding 五级流水 用预取、双 Buffer 和窗口错位，把 host 侧查表与网络交换尽量藏在当前窗口计算后面。
  • 正确性边界：提前预取可能读到旧参数，窗口切换前必须同步 current∩next 的交集行，保证下一窗口读到上一窗口更新后的版本。

第二条是稠密和 MoE 链路，目标是让 B 级 dense / 30B 级 MoE 放得下、跑得动：

  • 问题：OOM 不只来自参数；参数 W、梯度 G、优化器状态 O、激活和 expert 参数都会占 HBM。
  • 机制：ZeRO/FSDP 拆 O/G/W，AC/SAC 用重算换激活显存，EP 把 expert 横向铺开，让 token 经 router 只去 top-k expert。
  • 代价：参数 all-gather、梯度 reduce-scatter、EP dispatch/combine all-to-all 和激活重算都会进入训练时间线。
  • 答辩边界：先说清拆的是训练状态、激活还是 expert，不能把这些通信都混成 all-reduce。

第三条是算子与多硬件链路，目标是在模型能跑后提高有效计算密度：

  • 问题：attention 中间矩阵反复落 HBM，expert 小 GEMM/launch 太碎，复杂 mask 仍算无效 block，长短样本混批让快卡等慢卡。
  • 机制：FA4 / CompileMask / MoE 融合 / Label Packing 分别处理少搬、少算、少 launch、少重复编码；动态 token 组批 压平每卡 token 量。
  • 硬件边界：Backbone Infra 把训练/导出路径和 GPU/NPU 差异隔离起来，业务代码不直接感知 NCCL/HCCL、编译和算子差异。

结果与指标：每个数字都有口径

回目录
  • 业务落地：支撑 10+ 业务场景从 LRM 向 GR 升级落地，说明训练引擎不是单模型脚本，而是多场景可复用能力。
  • 稀疏容量：支撑 10TB 级稀疏参数和千卡横向扩展。10TB 是系统级容量目标，不是单卡 HBM；千卡线性比 NPU 512 die 约 0.89，1024 die 从 0.64 回到 0.926（Nest 双流后），主要归因是 emb 通信与 dense 计算重叠，不能说成“通信量减少”。
  • MoE 规模：支撑 30B 级 MoE 训练，例如 Qwen3-30B-A3B（总参约 30B、每 token 激活约 3B）。真正要看的是 expert 分布、token dispatch/combine、状态分片和负载均衡是否协同。
  • 有效算力：B300 上 Qwen3-4B、Qwen3-30B-A3B Backbone MFU 分别达 53.8%、29.57%。这是 Backbone 前反向口径；是否含 dataloader、embedding、通信时间要按 profiler 口径确认。

关键技术点：答辩最该讲清的边界

回目录
  • 强一致：双 Buffer 预取会提前读参数，必须靠 current∩next 交集 key 的整行同步保证下一窗口不读旧值。
  • 线性比归因：0.64→0.926 主要是 Nest 双流减少通信等待暴露，不是外层五级流水单独做到，也不是通信字节减少。
  • MFU 口径：MFU 比 GPU-Util 更接近有效算力，但必须说明分子 FLOPs、分母峰值、step time 是否含通信/数据等待。
  • DeepSpeed/FSDP 边界：OneRec 当前 dense 侧 DeepSpeed stage=1 与 FSDP2/ZeRO-3 概念不能混写；FSDP2 来源于本地 torchtitan 调用方，项目配置仍需核验。

项目二-1｜LRM 长序列训练能力建设

回目录
04_projects/lrm_long_sequence_training.md

这个项目的核心是把推荐模型的行为序列从百级扩展到十万级。序列变长后，问题不是“显存大一点”就能解决，而是数据供给、稀疏查表、通信坐标、padding 计算、模型导出都会一起放大。项目主线是：先让长序列样本稳定进入训练，再减少查表和通信碎片，最后把 padding dense 计算改成只算真实行为。

项目拆解：长序列把数据、通信、计算三条链同时放大

回目录

第一条是数据供给链路，目标是让长序列样本不要卡住训练 worker：

  • 问题：长序列样本解析、特征构造和变长列处理都很重；如果绑在训练 worker 内，GPU 会等 CPU 备数。
  • 机制：Sample Service 把数据处理解耦成可横向扩展的数据服务，提前产出训练批次。
  • 项目口径：训练吞吐提升 1.6 倍。

第二条是稀疏查表和通信链路，目标是减少长序列带来的 lookup 碎片和重复坐标载荷：

  • 问题 1：小 lookup 多。同一历史位置有 SKU、品类、品牌等多路字段，逐路查表会产生很多 kernel/A2A 调度碎片。
  • 机制 1：合表/合并查询。合表/合并查询 把同表多特征聚合成批量 lookup。
  • 问题 2：坐标重复传。多列字段若各带一份 indices+dense_shape，H2D/RPC 会重复传元数据。
  • 机制 2：SparseGroup。SparseGroup 让逐位置对齐的多列字段共享稀疏坐标，各列只保留自己的 values。
  • 项目口径：算子数减少 40%、吞吐提升 7.5%；六列值+坐标理论载荷从 144T→64T，H2D/RPC 稀疏输入载荷降低约 56%。

第三条是计算稀疏化链路，目标是不要为 padding 做 dense 计算：

  • 问题：长序列 batch 化后会 padding 到 [batch,max_seq,hidden]，但 padding 不是用户真实行为。
  • 机制：CP-GSU 保留真实行为位置索引和紧凑 value，只对有效位置做 gather/scatter/聚合。
  • 项目口径：冗余计算减少 70%，显存 70GB→20GB，吞吐提升 70%。
  • 待核验边界：CP-GSU 全称、结构位置和输入输出 shape 仍待逐行核验。

第四条是模型与导出链路，目标是把训练能力变成可上线能力：

  • 机制：支持 SIM、TWIN、MARM 等长行为模型，并打通训练到导出的流程。
  • 边界：这条链路证明工程闭环，不应和前面三条性能优化混作同一类机制。

结果与指标：4 倍是端到端叠加结果

回目录
  • 序列规模：从百级扩展到十万级，说明数据、稀疏、计算、模型导出链路都打通。
  • 整体收益：综合训练性能达到优化前 4 倍，这是数据 IO、查表/通信、计算稀疏化叠加后的端到端结果，不是单项收益。
  • 数据供给：Sample Service 吞吐提升 1.6 倍，衡量的是 CPU 备数不再明显拖住 GPU。
  • 查表效率：合表/合并查询让算子数减少 40%、吞吐提升 7.5%，衡量的是小 lookup 和 kernel 调度碎片减少。
  • 通信压缩：SparseGroup 的 56% 是六列值+坐标理论载荷以及对应 H2D/RPC 场景下降，不是整模吞吐提升 56%。
  • 计算稀疏化：CP-GSU 的 70GB→20GB 和吞吐 +70% 是 padding dense 改真实行为稀疏计算后的项目口径。

关键技术点：答辩最该讲清的边界

回目录
  • 4 倍不是单点归因：目前没有单独归因每条线贡献比例，不能说某一个机制带来 4 倍。
  • SparseGroup 省的是坐标载荷：共享 indices/dense_shape，不合并字段 values/key，不减少整表参数。
  • CP-GSU 不是 Ring Attention：CP-GSU 是 padding 计算稀疏化；CP/Ring Attention 是 KV 环传的上下文并行。
  • CP-GSU 结构待核验：机制和数字口径可讲，但全称、shape、算子实现仍是 open gap。

项目二-2｜统一训练框架与 9N-ModelZoo 建设

回目录
04_projects/modelzoo_training_framework.md

这个项目解决的是训练工程复用问题：零售多个算法场域如果每个业务各写一套训练代码，数据、特征、模型、loss、评估、导出、PS/Horovod 后端都会重复建设。项目主线是把这些环节拆成可配置组件，再用 ModelZoo 和多后端训练把业务建模周期从月级缩短到周级。

项目拆解：把业务脚本收敛成可配置训练平台

回目录

第一条是DAG 配置化链路，目标是把业务脚本变成可组合流水线：

  • 问题：训练不是单函数，而是数据、特征、模型、loss、评估、导出的完整链路；过去写死在脚本里，换数据源、模型或导出策略都要改代码。
  • 机制：DAG 化后，各环节变成可组合节点，业务通过配置组织训练流程。
  • 结果：复用同一套 train/eval/predict/export 骨架。

第二条是多后端训练链路，目标是让稀疏和稠密各走适合自己的参数管理方式：

  • 问题：搜广推模型同时有大规模稀疏 Embedding 和较重稠密网络，单一训练后端很难同时处理好两者。
  • 机制：PS 管大规模稀疏参数；Horovod / all-reduce 管稠密梯度。
  • 边界：all-reduce 只对应稠密梯度同步，不能把稀疏表当普通 dense 参数同步。

第三条是ModelZoo 模型底座链路，目标是减少重复建模：

  • 问题：多个场景从零搭模型，会重复开发 backbone、特征处理、训练入口和导出逻辑。
  • 机制：ModelZoo 沉淀 10+ 模型底座，业务按场景选择和组合。
  • 结果：业务建模周期从月级缩短到周级。

第四条是性能链路，目标是减少 GPU 等 CPU/调度：

  • 问题：GPU 利用率低不一定是模型算不动，常见原因是数据 IO、切图、调度让设备空等。
  • 机制：I/O 优化和切图加速让设备等待减少、计算更连续。
  • 项目口径：3+ 模型底座 GPU-Util 从 30% 提升到 70%；这是资源利用率口径，不等于吞吐同比例提升。

结果与指标：复用范围、交付效率、资源利用分开看

回目录
  • 复用范围：支撑零售 10+ 算法场域，提供 10+ 模型底座，说明它不是单模型脚本，而是训练平台能力。
  • 交付效率：业务建模周期由月级缩短至周级，来自 DAG 组件化、ModelZoo 复用和 train/eval/predict/export 标准化。
  • 资源利用：3+ 模型底座 GPU-Util 30%→70%，说明 GPU 更忙；仍需结合吞吐、等待时间和 MFU 判断是不是有效利用。

这一层的内部逻辑

回目录

硬件层按三个问题读，顺序不能反：

  1. 数据在哪里：参数、激活、样本、通信 payload 是在 HBM、host MEM、PCIe、NVLink/HCCS 还是 RoCE/IB 上移动。
  2. 算力在哪里：大 GEMM/attention 主要吃 Tensor Core/Cube；逐元素、归约、控制逻辑吃 vector/scalar/SM 调度。
  3. 瓶颈是谁：用 时间 ≈ 数据量/带宽 + 启动延迟 判断搬运瓶颈，用 算术强度 I=F/V 判断带宽受限还是算力受限。

所以第 1 层不是直接给优化方案，而是给上层一个约束：如果数据必须跨机走慢链路，第 2/5 层就要尽量少传或隐藏；如果算术强度低，第 6 层就要少搬或提高复用；如果 HBM 放不下，第 3/4/6 层才需要分层存储、分片或重算。

两张卡怎么衔接

回目录

先读 硬件互联，因为它回答“数据从 A 到 B 走哪条路”：

  • 机内 device↔device：NVLink / NVSwitch / HCCS，决定 collective 的机内上限。
  • host↔device：PCIe / DMA / H2D，决定样本、稀疏工作集搬上设备的上限。
  • 跨机 device↔device：RoCE / IB，决定千卡扩展、all-to-all、all-reduce 的跨机上限。

再读 加速器内部，因为它回答“数据到了芯片后，算得快不快”：

  • 矩阵单元决定大 GEMM/attention 的峰值算力。
  • HBM/缓存/搬移引擎决定数据能否及时喂给矩阵单元。
  • 算术强度和功率封顶解释为什么 GPU-Util 高不等于 MFU 高、纸面峰值不等于持续算力。

回目录
  • 第 1 层只给物理上限，不决定 DP/ZeRO/TP/EP 怎么选。

这四类不是并列的“产品名”，而是一次数据流会经过的空间层级。例如稀疏查表可能同时涉及：owner 的 host MEM 读参数行 → H2D 到 owner HBM → owner 通过 RoCE/IB 把向量发回 sample rank → sample rank 在本卡 kernel 内使用向量。

判据一句话：同卡内部看 HBM/SMEM/DMA；host↔device 看 PCIe/NVLink-C2C；同机设备间看 NVLink/NVSwitch/HCCS；跨机看 RoCE/IB 网卡。

为什么有效：通信优化先选对链路

回目录

通信时间 ≈ 字节数 / 有效带宽 + 延迟 × collective 次数。优化三条路——少传字节、用更快链路、减少小而碎的 collective——都建立在对“当前通信走哪条链路”的判断上。

代价模型：容量、带宽、延迟和固定启动开销一起决定瓶颈

回目录

GPU 内存储分层（从快到慢）：

  • 寄存器 / 共享内存（SM 私有）→ L2（分片 + 交叉互连，SM 间交换的唯一通道）→ HBM/显存 → 主机内存。
  • HBM 靠堆叠存储 die + 宽接口提带宽；GDDR 靠多颗存储芯片。
  • 统一内存两种别混：Apple UMA 是 CPU/GPU 共享同一块物理内存（无需复制）；CUDA Unified Memory 是统一虚拟地址、按需在 CPU/GPU 间迁移页（不是同一物理内存）。

三个量别混：容量是能放多少，带宽是单位时间传多少，延迟是一次请求多久返回。H100 SXM = 80 GB / 3.35 TB/s，H200 SXM = 141 GB / 4.8 TB/s——容量和带宽的增幅并不同步。

要跑满带宽，得靠并发在途请求（Little 定律）：在途事务数 ≥ R_target × L / s。接口带宽再高，在途请求不够就喂不满；在途请求太多又会排队加延迟。

互联的时间模型：固定开销 + 数据量

回目录

一次点对点传输 T = α + V/R（α=启动/完成通知固定开销，R=有效单向带宽，V=数据量）。所以：

  • 小消息被 α 主导：8 KiB 在 NVLink 上传输约 0.02 μs，但 α=2 μs，总耗时 2.02 μs；换更快链路几乎没收益。
  • 大消息被 V/R 主导：2 MiB 传输约 4.66 μs，换更快链路收益明显。
  • 转折点 V* = αR：H100 NVLink（450 GB/s、α=2 μs）约 879 KiB；小于它就该合并传输省 α，大于它才值得提带宽或减字节。

多卡集合通信的固定开销更狠：跨机 16 bytes 的 AllReduce 实测约 25 μs，100 次就是 2.5 ms——此时减少轮次比减少字节更有效。

算术强度：算力 vs 带宽的比值，判断瓶颈

回目录

算术强度 I = F/V（每字节数据能做的 FLOPs）。同一个矩阵乘，batch 越大、权重被复用次数越多，I 越高：

  • M=1（单行）：I ≈ 1——权重搬进来只算一次，带宽受限。
  • M 增大到 256：FLOPs 涨 256 倍，权重访存几乎不涨，I 也涨约 256 倍——转向算力受限。

这就是 roofline 的核心：硬件有个“转折点” = 峰值算力 / 峰值带宽（如 H100 约 295 FLOPs/byte）：

  • I 低于转折点 → 带宽受限：优先减少 HBM 往返或提升数据复用，例如 FlashAttention 不落完整 attention 矩阵。
  • I 高于转折点 → 算力/调度受限：优先让矩阵单元持续有大块工作，例如 grouped GEMM、kernel fusion、减少 launch。
  • 三类优化别混：FA 主要降访存、提高有效算术强度；CompileMask 通过块跳过减少被 mask 区域的 QKᵀ 和访存；MoE 融合主要改善小 GEMM/launch/调度效率，不等于单纯把 I 抬高。

为什么有效：先判断瓶颈，再选优化方向

回目录

算术强度把“算多少”和“搬多少”放到同一把尺上。I 低说明矩阵单元在等数据，优化要先减少 HBM 往返或提高复用；I 高但吞吐仍低，说明问题更可能在矩阵单元利用率、kernel launch、调度或功率封顶。这样可以避免把所有加速都笼统说成“提高算力”。

代价边界：数据搬移、能耗和功率封顶决定持续算力

回目录

每字节能耗随距离增长（量级）：

  • 片上 SRAM ~1 pJ/byte、NVLink-C2C ~10 pJ/byte、HBM2 ~32 pJ/byte、LPDDR DRAM ~160 pJ/byte；一次 BF16 乘加（2 FLOPs）只 ~0.75 pJ/FLOP。
  • 数据搬移比计算更耗电：单请求 decode 的能量里，权重读取占约 90%，计算几乎可以忽略。
  • 所以数据复用首先是能耗问题，其次才是带宽问题——这也是 batch 越大越省电、以及“别反复搬数据”的根因。

功率封顶：峰值算力为什么不能持续

回目录

芯片有热设计功耗（TDP，H100 SXM 700 W、B200 1000 W），由内存和计算共用：

  • HBM 满带宽约吃掉 100 W，留给计算约 0.60 pJ/FLOP 的预算。
  • 实际每 FLOP 能耗超过预算，功率控制器就降频，峰值算力到不了。
  • 所以 MFU 的分母严格说该用“持续算力”，而不是纸面峰值——这也是“GPU 100% 不等于充分”的硬件根源。

这一层内部怎么读

回目录

先不要问“这是哪个策略用的通信”。先问一条更底层的问题：这张卡下一步计算缺什么张量。

如果缺的是“所有卡都需要同一份完整结果”，通信语义就是复制/拼完整，对应 broadcast 或 all-gather。比如某层计算前需要完整参数，参数分片就要被 all-gather 回来。

如果缺的是“多个 rank 对同一个逻辑对象各算了一份贡献”，通信语义就是归约，对应 reduce、all-reduce 或 reduce-scatter。比如多个 batch 分片各自算出梯度，需要合成全局梯度；如果每张卡只保留自己负责的分片，就用 reduce-scatter。

如果缺的是“每条数据要去不同目标 rank”，通信语义就是重分发，对应 scatter、gather、all-to-all 或 all-to-allv。比如 token 要去目标 expert，稀疏 key 要去参数 owner，都不是求和，而是按目标重新分桶。

如果缺的是“上一段的输出就是下一段的输入”，通信语义就是相邻传递，对应 send/recv。比如 pipeline stage 之间传 activation，或 ring attention 里 KV 块沿环轮转。

最后，如果缺的是“远端 owner 管着的稀疏参数行”，通信就不是一个单次 collective 能讲完，而是一段往返：sample rank 发 key，owner rank 回向量，反向后 sample rank 再把 embedding 梯度发回 owner 更新。

这就是第 2 层的主线：先识别缺的张量 → 再判断通信语义 → 再选择原语 → 最后估 payload/链路/延迟。

集合通信算法：环形、树形、分层与在网归约

回目录回项目

同一原语有多种实现算法，差别在轮数、每轮传输量、以及哪些链路被用上。设 n 张卡、每卡持有 M 字节、每轮固定开销 α、单向有效带宽 B：

  • 环形 AllReduce：先 ReduceScatter（n−1 轮，每轮传 M/n），再 AllGather（n−1 轮），共 2(n−1) 轮，每卡发送 2(n−1)M/n。

  T_ring = 2(n−1)·α + 2(n−1)·M/(n·B)

小消息被 2(n−1)·α 主导（α 取 2 μs：八卡 10 KiB 约 28 μs，其中 28 μs 是启动）；大消息被 M/B 主导。

  • 树形（二项树）：两两归约 + 广播，2log₂(n) 轮，但关键路径每轮都传完整张量：

  T_tree = 2log₂(n)·(α + M/B)

小消息轮数少、树更快；大消息环更快。令 T_ring = T_tree，八卡 α=2 μs、450 GB/s 时转折点约 1.65 MiB——小于它树更快，大于它环更快。

跨机时还要分层（hierarchical AllReduce）：先机内 ReduceScatter → 跨机 AllReduce → 机内 AllGather。

  • 好处：减少跨机字节，更关键的是让每张网卡都有分片要传。
  • 何时划算：跨机带宽由多张独立网卡提供时，分层几乎无代价（NVLink 450 GB/s 远高于网卡 50 GB/s）。
  • 何时不划算：跨机带宽是共享接口（如多卡共用一张网卡的 PCIe 槽）时，本地归约增加的时间可能盖过它省下的远端传输。

在网归约（in-network，NVIDIA SHARP）：让交换机在转发时顺带做加法，端点每份数据只发一次、收一次，不再两两传递。服务器越多越划算：两台时和环只差一次启动，32 台时在网归约时间约为环的 49%。瓶颈会从网卡转到交换机归约引擎的吞吐。

选算法的口径：先看数据量落在 α 主导还是 V/R 主导，再看跨机带宽是独立网卡还是共享接口，最后决定用环、树、分层还是在网归约。

这一层内部怎么读

回目录

先从样本入口开始。推荐样本天然是变长的：有的样本行为很短，有的样本行为很长。如果按样本数装 batch，不同卡拿到的真实 token 数会差很多，慢卡会拖住全局 step。因此第一个问题是动态 token 组批：让 batch 按计算量而不是按样本数装，同时把 loss 改成全局有效监督 token 总数 N 归一，避免动态 batch 破坏梯度口径。

样本进来以后，还不能直接查表。业务字段里的 brand=Nike、shop=Nike 字面值可能相同，但语义不同，必须查不同 embedding 行。因此第二个问题是特征编码：把 (slot, id) 编成全局唯一 key。这个 key 是后面所有稀疏链路的索引：没有 key，就没有 owner 分桶、查表、更新、准入淘汰。

key 生成后，进入稀疏表主链路。样本在 sample rank 上，但参数行可能归另一个 owner rank 管。于是一次查表要走一个闭环：sample rank 发 key → owner rank 从 host MEM/HBM 工作集查参数行 → 向量回 sample rank → 反向后 embedding 梯度回 owner → owner 更新参数行。稀疏 Embedding 五级流水和双 Buffer 就是在这个闭环上做预取和错位重叠，让查表/搬运少暴露在当前 step 里。

主链路清楚以后，再看两个局部优化。合并查询优化的是“同一段查表里小 lookup 太多”：把同表多特征拼成一次批量 lookup，减少 kernel/A2A 调度碎片。SparseGroup优化的是“多列稀疏输入重复带坐标”：多列行为字段逐位置对齐时，共享一份 indices+dense_shape，各列只保留自己的 values，减少 H2D/RPC 里的重复坐标载荷。两者都发生在稀疏侧，但优化对象完全不同。

最后看表生命周期。稀疏表不是无限大，新 key 是否建行要由 access 准入控制，老 key 是否删除要由 shrink 淘汰控制；训练中断能否恢复、在线能否轻量加载，则由 checkpoint / SRBin 解决。它们不改变一次查表的通信语义，但决定这张大表能不能长期稳定训练。

动态 token 预算组批：让 batch 按计算量而不是样本数装

回目录回项目
03_concepts/dynamic_token_batching.md

一句话结论

回目录回项目

动态 token 预算组批解决的是：长短样本混在一起时，每个 rank 的真实计算量不均。

它把组批单位从固定样本数改成固定 token 预算：长历史样本少装，短历史样本多装，让每个 micro-batch 的 token 量接近，从而减少多卡同步时“快 rank 等慢 rank”。同一条输入链路上还用了 Arrow 列式备数，但 Arrow 解决的是 CPU 逐行对象处理开销，不能和 token 预算的收益混为一谈。

问题与设计主线：先按 token 量切 batch，再用 Arrow 高效备数

回目录回项目

固定 batch_size=N 的隐含假设是：每条样本成本差不多。推荐样本不满足这个假设，因为历史长度差异很大：

  • 长历史 batch：attention、embedding、backbone 都更重，step 时间长。
  • 短历史 batch：先算完也不能进入下一步，因为梯度同步、EP dispatch/combine 等同步点要等最慢 rank。

所以核心矛盾不是 batch size 大小，而是：样本条数不能代表真实计算量。

设计拆成两件事，顺序发生在同一条数据路径上：

环节决定什么解决什么
token 预算组批哪些行组成一个 batch每个 batch 计算量不均，导致跨卡等待
Arrow / collator 备数这些行怎么变成训练张量Python 逐行对象构造慢，CPU 备数开销高

收益归因时必须分开：负载更均匀 和 CPU 备数更快 是两条不同链路。

具体切 batch 的流程是：

  1. 读 chunk：Reader 一次读 R 行。
  2. 算成本：token_counter_fn 给每行样本估 token 成本。
  3. 做前缀和：计算前 k 行累计 token 成本。
  4. 找切点：选累计成本 ≤ M(max_tokens) 的最长前缀。
  5. 保留 carry：没用完的行带到下一个 batch 或下一个 chunk。

项目配置示例：每个 batch 的 token 预算约为 286720，Reader 一次先读 1024 行候选样本。这里要分清：一次从文件预读多少行不等于最终训练 batch 有多少样本；动态路径下，最终 batch 已经由 token 预算决定，不再由固定样本数决定。

执行边界与正确性：Reader 只管切批，OneRec 组装业务张量，loss 按全局 N 归一

回目录回项目

工程边界在 collate_fn：

  • airecord（通用 IO 层）：读文件、按预算组批、断点续训、EOS 退出；只知道每行成本和 batch 切点。
  • OneRec（领域层）：理解业务字段含义，例如哪些列是行为序列、哪些列是标签，把列式 batch 组装成训练张量。

依赖方向是：OneRec import airecord，airecord 不认识 OneRec。这样通用 Reader 可复用，业务语义留在领域 collator 里。

动态 batch 还会带来正确性问题：每个 micro-batch 的 有效监督 token 数 n_micro 不同。如果每个 micro 内先求 mean，再对 micro 求平均，那么 3 个有效 token 的 micro 和 9 个有效 token 的 micro 会被等权处理，训练目标就变了。

正确目标应该等价于：


loss_update = 全局 Σloss / 全局有效监督 token 总数 N

实现口径是：

  1. 模型 forward 返回 sum（reduction="sum"），不要在 micro 内除以 n_micro。
  2. 训练循环累计整个更新窗口的有效监督 token 总数 N。
  3. 关掉框架默认的“按梯度累积步数再平均一次”，避免重复缩放。
  4. 在一次参数更新前，把累计梯度按 W/N 补回正确尺度（W 是数据并行卡数，N 是全局有效监督 token 总数）。

一句话：batch 可以动态，但每个有效监督 token 在 loss 里的权重不能变。

为什么有效、什么时候不有效

回目录回项目

动态 token 预算组批的因果链是：


历史长度差异大

→ 固定样本数组批导致各 rank token 量不均

→ 慢 rank 决定同步点完成时间

→ 按 token 预算组批压平 micro 的真实计算量

→ 快 rank 等慢 rank 的时间减少

Arrow 列式备数的因果链是：


逐行 Python 对象构造多

→ CPU collate/解析时间高

→ GPU 等数据

→ Arrow 列式读取 + 零拷贝 collator

→ CPU 备数开销下降

有效前提：样本历史长度分布很不均，并且 多卡同步等待或 CPU 备数是瓶颈。

收益不大的情况：样本长度本来均匀，或瓶颈在显存、通信带宽、MoE all-to-all，而不是 batch 内 token 波动。评估默认看累计 per_rank_samples/s、MFU 和 step time 分布，不能只看单个 batch。

怎么设计：先判断哪些信息要查 embedding，再生成全局 key

回目录

一条样本进入稀疏查表前，读者只需要先抓住三件事：

  1. 离散信息才查 embedding：品牌、店铺、SKU、query token 这类“取值是一个 ID/词”的字段，需要变成 key 去查 embedding；价格、时长、曝光次数这类连续数值，不建稀疏 key，直接作为数值特征进入 dense 侧。
  2. 字符串要先切成 token：普通 ID 可以直接编码；query 等文本要先切成多个 token，每个 token 再进入后续 key 编码。
  3. key 必须带字段身份：最终编码的是 (字段身份, 原始值)，例如 (brand, Nike) 和 (shop, Nike) 必须生成不同 key。源码里常见形式是 Hash(slot_name, id) 这类组合 hash。

这一步的产物不是向量，而是key。key 之后才会被分桶到对应 owner rank，owner 再用 key 从 host MEM/HBM 工作集查出向量。

为什么必须带 slot：防止“同名不同义”查错行

回目录

如果只 hash 原始值，brand="Nike" 和 shop="Nike" 会得到同一个 key，最后查到同一行参数。这样模型无法区分“品牌 Nike”和“店铺 Nike”，语义已经在查表前被破坏。

带 slot 后，逻辑变成：

原始字段原始值编码对象结果
brandNike(brand, Nike)品牌命名空间下的一行
shopNike(shop, Nike)店铺命名空间下的另一行

这里的 global hash 不是“物理上合成一张表就完事”，而是让不同字段共享一个全局 key 空间，同时通过字段身份保持命名空间隔离。具体源码可能有自己的组合 hash 函数；读者只需要记住目的：同名不同义不能查到同一行。

主角：四样东西，两个角色

回目录回项目

整条链路只围绕四样东西、两个角色转。先明确两个角色，避免把 owner 和 CPU/GPU 混为一谈：

  • rank（卡）：训练里的一个设备进程（GPU/NPU），每张卡既有主机内存（host MEM），也有设备内存（HBM）。
  • owner（属主 rank）：负责保管某个参数 shard 的那张卡——全量参数行长期存在它的 host MEM，训练时只把当前窗口命中的工作集搬到它的 HBM。
  • sample rank（样本所在卡）：样本被分到的那张卡，负责用查出的向量算稠密前反向。
东西是什么谁持有/谁负责
key稀疏特征 ID（商品/用户/行为），只是个整数索引样本产生，owner 按 key 分片保管

梯度反向得到的“向量该怎么改”sample rank 算出来，交回 owner 聚合

主线：先懂单窗口闭环，再懂跨窗口流水

回目录回项目

先别管“五级”，只看一个窗口：一份样本从 key 到参数更新，四样东西各动一次，串成 5 步。拿“样本在 A 卡、商品 key 归 B 卡管”走一遍：

  1. key 分发（A→B）：A 对 key 去重、按“key 归属的 owner”分桶，把 key 发给 owner B——“这些 key 我要用”。工程里常叫 Input Dist。
  2. 参数行装入（B 的 host MEM→B 的 HBM）：B 从自己 host MEM 里的分片，把命中的参数行搬进 HBM 工作集。
  3. 查表 + 向量回传（B→A）：B 在 HBM 查表，把向量发回 A。
  4. 稠密前反向（A 本地）：A 拼特征过 backbone 算 loss，反向得到这些向量的梯度。
  5. 梯度回传 + 更新（A→B）：A 把梯度发回 B，B 聚合同 key 的多份梯度后更新参数行。工程上这一步可能走 all-to-all。

记住两点：这 5 步有先后、不能乱；Grad A2A 传的是“当前 batch 命中的那些向量的梯度”，不是 loss 也不是整表梯度。

五级流水让相邻窗口的 5 步错位重叠

回目录回项目

这里最容易混，先明确边界：“五级流水”和上面的“5 次搬运”是两回事。 上面是一个窗口内部的 5 步串行；五级流水是把多个窗口排成队，让每个窗口处在不同阶段，错位重叠。

五级的端到端口径是 5 站。先看业务动作，再看工程名字：


① 提前读下一批样本 → ② 样本搬上设备 → ③ key 分桶交换 → ④ 查表并回传向量（Emb Lookup）→ ⑤ 稠密前反向 + 更新

上面第 3 节的 5 次搬运，主要落在 ③④⑤ 这三站里。真正的并行是：同一时刻，多个窗口各在干一件事——


G0 在 ⑤ 算模型/更新，G1 在 ④ 查表/预取，G2 在 ③ 分桶交换，G3 在 ② 搬样本……

所以“为什么快”不是“一个窗口五件事同时做”，而是“搬表、查表与当前窗口计算重叠，减少设备等待 host 侧查表和网络交换”。代价也在这：HBM 要放两份工作集，且提前加载会带来正确性问题。

双 Buffer 是错位的落地

回目录回项目

每张表在 HBM 里准备两块工作区：一块服务当前窗口，一块提前准备下一个窗口。current/next 是角色，不是固定物理名字：


训练 G0：A=current 在算，后台对 B 先 Dump 旧窗 G−1、再 Load 新窗 G1（同一次复用任务，相差两个窗口）

G0 结束：等预取 + 等 G0 更新完成 → 同步交集行 → 切换 current/next

训练 G1：B=current 在算，后台对 A 先 Dump G0、再 Load G2

补充一句防误解：有些源码变量只列出“搬样本、key 分桶、预取”这三个准备阶段；Reader 在上游，当前窗口的查表与前反向在它之外。端到端五级和源码里的三个准备阶段是不同范围，别当成五级=三个。

唯一的难点：提前预取会读到旧参数 → 强一致

回目录回项目

双 Buffer 的副作用是：下一个窗口可能提前装好了 key=100 的参数，但当前窗口反向后又把 key=100 更新了。如果下一个窗口直接用提前装好的旧值，就读错了。

修法是在窗口边界做交集同步：


G1 预取 future.get() 完成 ───────┐

                                 ├→ 把 G0∩G1 交集 key 的最新整行 A→B → 切表 → G1 前向

G0 反向和更新完成 ────────────────┘

语义保证：下一窗口读到的参数，不早于上一窗口更新完成后的版本。

  • 连续命中的 key 靠交集同步保持新鲜。
  • 隔窗再次出现的 key 靠旧 buffer 退役回写 host MEM、再从 host MEM 表加载。
  • 诚实边界：源码交集函数还留着“current 独有 key 回写”的 TODO，完整强一致要结合 buffer 退役、checkpoint/eval flush 和运行验证，不能只凭交集函数下结论。

怎么选、代价、口径（收尾）

回目录回项目

1. 表的存放策略看“表有多大、能不能常驻 HBM”。

  • 现用现搬：要用时再从 host MEM 搬到 HBM，能跑但等待暴露多。
  • 预取 + 双 Buffer：提前准备下一窗口工作集，是大表主路径，用复杂调度换等待隐藏。
  • 整表常驻 HBM：小表最快，但受 HBM 容量限制。
  • 每卡完整复制小表：适合容量很小、复制成本可接受的表。

主线就是：现搬能跑但慢 → 预取双 Buffer 藏等待 → 全 HBM 最快但容量受限。

一个配置陷阱要单独记：配置文件里的初始策略不一定是最终执行策略，模块构造时可能把“现用现搬”强制改成“预取 + 双 Buffer”。判断实际路径要追到模块构造处，不能只看配置初值。

2. 本质代价是“用复杂搬运换 HBM 容量”。

  • 多了 key / 向量 / 梯度 A2A。
  • 多了 host MEM ↔ HBM 的工作集搬运。
  • 多了 双 Buffer、窗口切换、交集同步 的调度复杂度。

换来的收益是：全量稀疏表不用常驻 HBM，HBM 只放当前/下一窗口工作集。

3. 10TB/千卡线性比是系统级口径。

  • 10TB 是分布式容量目标，不是单机内存，也不是单卡 HBM。
  • 千卡线性比：NPU 512 die 约 0.89，扩到 1024 die 塌到 0.64，Nest 嵌套双流后 1024 die 回到 0.926（+34.3%）。
  • 归因要准确：Nest 让 embedding 通信与 dense 计算重叠，盖住约 71% 通信；不是减少通信量，也不能说是外层五级流水单独做到。

合表 / 合并查询：把多次 Embedding 查询聚成一次批量 lookup

回目录回项目
03_concepts/merge_lookup.md

一句话结论

回目录回项目

合表/合并查询解决的不是“表太大放不下”，而是一次训练 step 里小查表太多：同一个样本要查 SKU、品牌、店铺、类目等很多特征，如果每个字段都单独分发 key、单独启动 lookup kernel，就会把 A2A 和 kernel 调度切得很碎。合并查询把同表多特征拼成一次批量 lookup，再按特征拆回，减少碎片。

它接在五级流水哪一段

回目录回项目

稀疏查表主链是：key 分桶 → owner 查表 → 向量回传 → 梯度回 owner 更新。合并查询只优化其中的 owner 查表/向量组织 这一段：

  1. 上游 特征编码 已经产出多个字段的 key。
  2. InputDist 会按 owner 分桶，把 key 送到负责参数行的 rank。
  3. 合并查询把同表或同布局的多个小 key 列表拼成更大的批量查询。
  4. lookup 结束后，再按每个字段原来的长度切回去，保证模型看到的特征语义不变。

所以它不是替代五级流水，而是嵌在五级流水的查表阶段里，减少“多次小 lookup”带来的调度和通信碎片。

怎么设计：先对齐布局，再合并真正能合并的查询

回目录回项目

两层动作不要混：

  • 按 embedding 行宽 dim 分组：行宽相同的表才能放进同一种规整 buffer，使用同一种 A2A element 粒度和 kernel 配置；行宽不同的向量不能硬塞进同一个 2D buffer。
  • 表内多特征合并查询：同一张表服务多个特征时，先把这些字段的 ID 拼成一条长列表，一次 lookup 查完，再按原字段长度拆回去。

关键边界：按 dim 分组是布局条件，表内多特征拼接才是合并查询本体。同 dim 的不同表只是更容易共享调度/通信组织，不等于天然可以语义合查。

为什么有效，和 SparseGroup/五级流水怎么区分

回目录回项目

合并查询有效，是因为它把 N 次小 lookup 变成 1 次更大的 lookup，减少 kernel 启动、A2A 调度和查表碎片。项目口径是算子数减少 40%、训练吞吐提升 7.5%。

三者边界如下：

机制优化对象不要误解成
合并查询lookup 次数、kernel/A2A 调度碎片减少整张表容量
SparseGroup多列稀疏输入重复坐标合并不同字段的 values/key
五级流水查表/搬运与训练计算的等待暴露减少单次 lookup 的数学计算量

SparseGroup：共享稀疏索引/坐标，减少长序列输入重复传输

回目录回项目
03_concepts/sparse_group.md

SparseGroup 接在“特征已经是稀疏序列、准备进入查表链路”这一段：同一个用户行为位置上，SKU、品类、品牌等字段通常有效位置完全对齐，却各自携带一份“这个有效位置在 batch 里的坐标”。SparseGroup 让组内共享一份稀疏索引/坐标结构，各字段只保留自己的取值，从而减少 H2D/RPC 里重复传输的稀疏元数据。

边界要先说清：这是 Tritium/TF 输入侧的实现，输入形态是“坐标 + 取值”的稀疏张量；OneRec 当前 PyTorch 路径更常见的是“连续 values + offsets/lengths”的 jagged 输入。两者都表达变长序列，但接口不同，不能混为一谈。

它在数据链路里解决哪一段重复

回目录回项目

长序列样本进入稀疏查表前，字段通常长这样：


view_sku_seq   = indices + dense_shape + sku_values

view_cate_seq  = indices + dense_shape + cate_values

view_brand_seq = indices + dense_shape + brand_values

如果这些字段来自同一条行为序列，它们的样本号和行内位置一致，重复传多份坐标和逻辑形状就是在传同一份结构。SparseGroup 改成：


shared indices + shared dense_shape + sku_values + cate_values + brand_values

所以它省的不是参数行、不是 Embedding 向量，也不是 loss/梯度，而是稀疏输入结构里的重复坐标。

怎么设计：共享稀疏索引/坐标，但不合并字段语义

回目录回项目

SparseGroup 拆的是稀疏表示，不是模型层：

拆分对象共享吗含义
稀疏索引坐标共享每个有效行为落在 batch 的哪个样本、哪个位置
逻辑形状共享这组序列整体有多大
字段取值不共享每个字段自己的 key/value，如 SKU id、品牌 id

这就解释了为什么它能省通信又不破坏语义：位置结构共享，字段取值不共享。下游恢复逐字段稀疏输入后，Embedding lookup 仍然按各字段自己的取值/key 查表。

上线前必须确认组内字段确实逐位置对齐。只看总长度相等不够；如果 SKU 过滤、品牌缺失、截断策略不同，字段之间的位置语义就会错位，强行共享坐标会查错。

通信量怎么算：56% 是输入载荷口径，不是整模收益

回目录回项目

按六列字段、每列 T 个有效位置估算，旧格式每列都传 indices + values：


旧：6 × (16T indices + 8T values) = 144T bytes

新：1 × 16T indices + 6 × 8T values = 64T bytes

下降：(144T - 64T) / 144T ≈ 55.56%

因此“56%”只能表述为：六列、值+坐标理论载荷从 144T→64T 的下降，以及对应 H2D/RPC 场景里的稀疏输入载荷下降。它不是单独坐标字节下降 56%，不是整模吞吐提升 56%，也不能推出模型参数显存、Embedding 表容量或整卡显存下降 56%。

为什么可能带来吞吐收益，和相邻机制怎么分工

回目录回项目

SparseGroup 的收益来自三处：

  • CPU 解析减少：组内只对参考列做坐标转换，减少多列重复 RaggedToSparse。
  • H2D/RPC 载荷减少：共享 indices+dense_shape 后，流水线 buffer 和网络传输少搬重复结构。
  • 下游接口保持稳定：恢复逐字段 SparseTensor，下游稀疏 Embedding/行为层不必改成全新语义。

它和相邻机制的关系是：

机制省什么不省什么

五级流水查表/搬运等待暴露不改变稀疏表示本身

准入与淘汰：稀疏表怎么控制容量

回目录
03_concepts/access_shrink.md

一句话结论

回目录

稀疏表的容量控制发生在 key 生命周期的两端：access / Filter 决定新 key 是否值得建一行参数，shrink / ShrinkPolicy 决定老 key 是否还值得继续占空间。它不改变一次查表怎么通信，但决定这张表能不能长期训练而不被长尾 ID 撑爆 host MEM。

主线：一条 key 从出现到被删除，会过两道闸

回目录

第一道闸在入表前。样本里来了一个新 key，系统不能立刻给它创建参数行；否则一次性长尾 ID 越多，稀疏表越膨胀。access 的作用就是先问：这个 key 是否出现得足够多、足够有业务价值，值得分配一行 embedding 参数。

第二道闸在入表后。某个 key 已经有参数行，但如果长期不出现、频次低、参数范数很小，继续保留它只会占 host MEM 和 checkpoint 空间。shrink 的作用就是定期清理这些冷 key。

所以这张卡的逻辑不是“多个策略列表”，而是：新 key 先被准入挡一遍，老 key 再被淘汰清一遍；两端一起收，表容量才可控。

怎么设计：access 管新 key，shrink 管老 key

回目录

access / Filter：入表前判断是否建行。

  • None：全准入，最简单，但表增长最快。
  • Count：出现次数达到阈值才准入，挡住一次性长尾。
  • Probability：按概率准入，高频 key 累计更容易进表。
  • ShowClick：用 α·展现 + β·点击 形成分数，分数过阈值才准入。

shrink / ShrinkPolicy：入表后判断是否删除。

  • GlobalStep：距离上次更新太久则淘汰。
  • L2Weight：参数范数太小，说明贡献弱，可淘汰。
  • TimeFreqCombine：同时考虑时间和频次，清理又久又低频的 key。

关键实现点：Value.version 这个 32-bit 字段被多种策略复用。GlobalStep/Count 把它当“步数/次数”，ShowClick 用 reinterpret_cast<float*> 位重解释当“分数”。同一块内存不同读法，策略不能随意混用，否则读出来的语义会错。

和其它稀疏卡的边界

回目录
  • 特征编码 负责把 (slot,id) 变成 key；access/shrink 决定这个 key 是否占参数行。
  • 稀疏 Embedding 五级流水 负责 key 怎么查表、向量怎么回传、梯度怎么更新；access/shrink 不改变这个通信闭环。
  • 稀疏表 checkpoint 负责把参数行、optimizer state 和删除记录落盘；shrink 产生的删除记录会影响恢复。

为什么能解决容量问题

回目录

稀疏表膨胀的根因是长尾 key 太多，而每个 key 一旦建行，就会长期占用参数、优化器状态和 checkpoint 空间。access 先把低价值新 key 挡在表外，shrink 再把长期无贡献的旧 key 清出去。一个减少新增，一个清理存量，表容量才不会随长尾 ID 无限制增长。

和我的项目怎么关联

回目录

项目一/二的稀疏表都靠这条控制容量：

  • 用了什么能力：access（Filter 准入）+ shrink（ShrinkPolicy 淘汰），分别卡在 key 生命周期两端。
  • 解决什么问题：长序列把 key 空间放大，每个长尾 ID 都建行会让稀疏表无限膨胀、挤爆 host MEM。
  • 达到什么效果：这是“表能持续训练、不 OOM”的保障，不是单独报数字的点；具体用哪个 Filter/ShrinkPolicy、α/β 等参数待按部署配置核验。

稀疏表 checkpoint：训练续训和在线加载不是同一种存档

回目录
03_concepts/ckpt_save_load.md

一句话结论

回目录

稀疏表落盘要先分清保存目的：训练 checkpoint 要带 optimizer state 和删除记录，保证断点能接着训；在线 SRBin 只要参数，追求体积小、加载快。两条链目标不同，所以格式不能混用。

主线：训练要“接着更新”，在线要“轻量加载”

回目录

训练侧保存的不是一份普通参数文件。稀疏表里每个 key 对应参数行，还可能有 Adam m/v、master weight、版本信息和 shrink 删除记录。训练断了以后，如果只恢复参数、不恢复 optimizer state，后续更新轨迹就不是原来那条训练轨迹。因此训练 checkpoint 必须保留参数行 + optimizer state + 删除记录。

在线侧目标正好相反。在线服务只需要用参数做推理，不需要继续按训练优化器更新，也不需要保留训练时的中间状态。它更关心文件体积、加载速度、服务内存，所以会导出 SRBin，必要时做 int8/int4 量化。

这就是这张卡的核心：训练侧为可续训保存更多状态；在线侧为可服务删除训练状态。

怎么设计：先问保存目的，再决定保存哪些状态

回目录
保存目的要保存什么格式 / 模式恢复后做什么
场景要保存/加载什么工程形态结果
训练续训参数行 + optimizer state + 删除记录训练完整快照恢复到断点前训练状态，继续用原优化器状态更新
换优化器 / 微调参数行，不复用旧 optimizer state只加载参数参数恢复，optimizer state 重新初始化
预训练初始化只拿参数初始化，不分配稀疏 optimizer buffer只把参数当初值后续按新任务创建状态

增量 saver 只影响训练侧怎么少写盘：

  • All：全量落盘。
  • Inc：只落新增 .data 和删除 .shrink。
  • 恢复时：重放增量，得到完整表。

为什么不能混用

回目录
  • 不能用 SRBin 做训练续训：SRBin 去掉 optimizer state，恢复后无法接着原训练轨迹更新。
  • 不能把训练 .data 直接当在线轻量格式：训练格式带状态和删除记录，不是为在线体积和加载速度设计。
  • 量化只用于在线，不用于训练：训练还要保留可更新精度和优化器状态；在线只需要推理参数。

和我的项目怎么关联

这一层内部怎么读

回目录

先从 DP 基线开始。DP 不拆模型，只拆 batch：每张卡都有完整模型，处理不同数据，最后把梯度同步成同一个全局更新。DP 的意义是建立语义基线：多卡训练最后仍要像一个大 batch 在更新同一个模型。

如果显存瓶颈来自训练状态副本，就进入 ZeRO/FSDP。普通 DP 每张卡都有完整参数 W、梯度 G、优化器状态 O；ZeRO/FSDP 的问题不是“矩阵乘太大”，而是这些状态重复存太浪费。因此它按阶段拆 O、G、W：拆得越多，单卡显存越省，但计算前后需要更多 all-gather / reduce-scatter 把缺的参数或梯度补回来。

如果瓶颈来自单层矩阵太大或单层 GEMM 想并行，就进入 TP。TP 拆的是一层内部的大矩阵，比如 FFN 里的 W1/W2 或 attention 里的 QKV/O。它不负责 optimizer state 分片；它的核心问题是局部 hidden 怎么在矩阵切分后被求和、拼接或重新分片。

如果瓶颈来自层数太多、整段网络放不下一张卡，就进入 PP。PP 拆的是层边界，把连续层段放到不同 stage。它传的不是参数分片，而是 stage 边界 activation 和反向 activation gradient；为了减少 bubble，还要把 batch 切成 micro-batch 排流水线。

如果瓶颈来自长序列，就进入 SP/CP。SP 更偏把序列维上的层内激活分开，减少非 GEMM 层激活显存；CP/Ring Attention 更偏把上下文/KV 分块，让本地 query 通过环形轮转看到远端上下文。两者都和“序列”有关，但缺的张量和通信时机不同。

如果瓶颈来自 MoE expert 太多，就进入 EP。EP 拆的是 expert 参数：每张卡只放部分 expert，router 选中 expert 后，token hidden 必须 all-to-all 到目标 expert 所在 rank，算完再 all-to-all 回原 token 位置。EP 传的是 token hidden，不是 expert 参数。

这就是第 4 层主线：先用 DP 建立全局一致更新语义，再按瓶颈对象选择拆状态、拆矩阵、拆层、拆序列/上下文、拆 expert。

策略之间的边界

回目录
  • ZeRO/FSDP vs TP：前者拆训练状态 O/G/W；后者拆一层内部矩阵乘。
  • TP vs PP：TP 在同一层内部横向拆矩阵；PP 在层与层之间纵向拆 stage。
  • SP vs CP：SP 主要省层内序列激活；CP/Ring Attention 主要解决长上下文 attention 的远端 KV 可见性。
  • EP vs TP：EP 拆不同 expert；TP 可以继续拆每个 expert 内部的大矩阵，两者可以叠加，但对象不同。

只要说不清“拆的对象是什么”，后面的通信量就一定会乱。

DP：复制模型，拆 batch，同步梯度

回目录
03_concepts/dp_data_parallel.md

Data Parallelism（DP，数据并行）是最基础的多卡训练：每张 GPU 放一份完整模型 W，拿不同数据算前向/反向，最后把所有 GPU 对同一参数算出来的梯度求平均，让每张卡更新出同一份新参数 W'。

主线：拆 batch 提吞吐，但必须同步梯度保持同一个模型

回目录

DP 的逻辑链很短：先把 batch 切到多张卡上并行算，再把每张卡算出的局部梯度合成一个全局梯度。单张 GPU 的吞吐有限，DP 通过让多张卡同时处理不同样本来提高总 batch 吞吐。它不减少单卡模型显存，因为每张卡仍放完整模型；它解决的是“同一个模型如何并行吃更多数据”，代价是每步要同步梯度。

拆的是什么

回目录

DP 拆的是 batch/样本，不是模型。假设全局 batch 是 1024，8 张卡，每张卡处理 128 个样本。每张卡都有完整参数 W，区别只是看到的数据不同。

怎么设计：每卡算局部梯度，再 all-reduce 成全局平均

回目录

单卡训练时，一个 batch 经过模型得到 loss，反向传播会算出每个参数对 loss 的梯度。DP 下每张卡的 batch 不同，所以梯度也不同：


GPU0: loss_0 -> gradient G_0

GPU1: loss_1 -> gradient G_1

...

GPU7: loss_7 -> gradient G_7

如果直接各自更新，8 张卡的 W 会变成 8 份不同模型。为了让它们等价于“一个大 batch 训练”，必须对同一个参数位置的梯度求平均：


G_avg = (G_0 + G_1 + ... + G_7) / 8

W' = optimizer_update(W, G_avg)

reduce 和 gather 分别是什么

回目录
  • reduce：把多张卡上的同一类数据合并成一个结果。DP 里合并的是梯度，操作是求和/平均。
  • gather / broadcast：把合并后的结果让需要它的卡都拿到。
  • all-reduce：把这两步合在一个 collective 里：每张卡都参与求和，每张卡最后都得到同一个求和结果。

所以 DP 说“reduce + gather”是概念分解；工程上通常直接用 all-reduce 完成。

通信对象与通信量

回目录
  • 传的是什么：梯度张量 G，不是样本，不是参数 W。
  • 什么时候传：反向传播产生梯度后，优化器 step 前。
  • 为什么传：为了让不同数据上算出的梯度合成全局 batch 的平均梯度。
  • 通信量：若梯度总大小为 P_grad 字节，N 张卡 ring all-reduce 单卡通信量约 2 * (N-1)/N * P_grad。

和 ZeRO 的关系：ZeRO 继承 DP 语义，只是拆训练状态

回目录

ZeRO 是对 DP 的训练状态做拆分。DP 保留完整 W/G/O；ZeRO-1 拆 O；ZeRO-2 拆 O/G；ZeRO-3 拆 O/G/W。它们都保留“不同卡看不同数据、需要全局一致更新”的 DP 语义。

ZeRO / FSDP：把“模型状态”拆开，用通信换显存

回目录回项目
03_concepts/zero_parallelism.md

ZeRO（DeepSpeed）的核心不是把网络层切开，而是把训练时最占显存的三类状态拆到多张卡上：优化器状态 O、梯度 G、参数 W。FSDP（PyTorch）是同一思想的另一套实现。DP 是每张卡都放完整模型；ZeRO/FSDP 是尽量只在“需要用到的瞬间”把缺的部分通信回来，用更多通信换更低显存。

主线：先识别重复状态，再决定拆 O/G/W 哪一类

回目录回项目

普通 DP 下，N 张卡各自拿不同 mini-batch，前向/反向都在完整模型上做。每张卡显存里都有完整参数 W、完整梯度 G、完整优化器状态 O。模型一大，单卡显存就被重复副本浪费：N 张卡总显存很大，但每张卡仍必须装下完整训练状态。

ZeRO 的直觉是：既然每张卡算的是不同数据，但最终更新的是同一个模型，那训练状态没必要每张卡都完整存一份。

接下来的逻辑只有一条：先看 O/G/W 哪些状态被拆，再看为了让前向、反向、更新仍然正确，系统必须把哪些分片用 collective 临时补齐。

拆的是什么

回目录回项目
  • ZeRO-1：只拆优化器状态 O，例如 Adam 的 momentum、variance、master weight。
  • ZeRO-2：拆 O 和梯度 G。
  • ZeRO-3 / FSDP 全分片模式：拆 O、G 和参数 W。每张卡长期只保存自己负责的参数分片，算某一层时临时 all-gather 出这一层需要的完整参数。ZeRO-3 是 DeepSpeed 的命名，FSDP 全分片是 PyTorch 的命名，这一级两者做的是同一件事。

如果模型参数量记为 P，数据并行度为 N，混合精度 Adam 常见状态粗略可理解为：参数约 2P、梯度约 2P、优化器状态可达 8P 或更高。ZeRO 逐步把这些从“每卡 P 级完整副本”变为“每卡 1/N 分片”。

DP 基线：reduce + gather 为什么都存在

回目录回项目

普通 DP 每张卡都有完整 W，各自算出本卡 batch 的梯度 G_i。为了让所有卡更新成同一个新参数 W'，需要把所有 G_i 求平均：

  1. reduce：把多张卡对同一参数的梯度相加，例如 g = g_0 + g_1 + ... + g_{N-1}。
  2. gather / broadcast：让每张卡都拿到同一个结果，才能都更新出同一份 W'。

工程上常用 all-reduce，它可以理解成“reduce + 把结果分发给所有卡”。所以用户看到 DP 也常被说成 reduce + gather：本质是先把梯度合并，再让每张卡都拥有合并后的梯度。

ZeRO-1

回目录回项目
  • 前向/反向：每张卡仍有完整参数 W，反向像 DP 一样算出完整梯度 G。
  • 通信：梯度用 reduce-scatter（不是 all-reduce）——求和后各卡只留自己那份梯度分片；因为优化器状态已切片，每卡只需自己参数的梯度。
  • 更新：每卡用自己那份 O 分片 + 梯度分片，更新自己负责的参数分片；随后 all-gather 更新后的参数，让所有卡下一轮仍有完整 W。
  • 传的是什么：梯度分片（reduce-scatter）+ 更新后的参数分片（all-gather）。

ZeRO-2

回目录回项目
  • 前向/反向：每张卡仍有完整参数 W，但不长期保留完整梯度 G。
  • 通信：反向产生梯度时，不再 all-reduce 出完整 G 给每张卡，而是 reduce-scatter。它一边把所有卡的梯度相加，一边只把第 k 份结果留给第 k 张卡。
  • 更新：每张卡用自己保存的 O 分片和收到的 G 分片，更新对应 W 分片；随后 all-gather 参数分片，让所有卡得到完整 W。
  • 传的是什么：梯度分片在 reduce-scatter 中被求和并分发；参数分片在更新后被 all-gather。

ZeRO-3 / FSDP

回目录回项目
  • 长期状态：每张卡只长期保存 W/O/G 的 1/N 分片。
  • 前向前：某层要算 y = xW 时，每张卡只有 W 的一片，不够算完整层，所以对该层 W 做 all-gather，临时拼出完整 W_layer。
  • 前向后：这一层算完，完整 W_layer 可释放，只保留本卡分片。
  • 反向时：再次需要 W_layer 或其局部信息，会按 bucket 预取/聚合；梯度产生后用 reduce-scatter，把全局梯度求和后的分片留在对应卡。
  • 优化器 step：每卡只更新自己负责的参数分片。
  • 传的是什么：前向/反向前传参数分片，反向后传梯度分片；不是传样本，也不是传整个网络结构。

通信量与时机：显存省在哪里，通信补在哪里

回目录回项目

设完整参数大小为 P 字节，数据并行度为 N。忽略 bucket 边界、重叠和协议常数，单步大致可理解为：

策略主要通信单卡通信量级显存收益
DP梯度 all-reduce2 * (N-1)/N * P_grad，若梯度约 P，则约 2P不省 W/G/O，每卡仍完整保存

  • 同样字节数，能和计算重叠，暴露在 step time 里的通信就少很多。

通信时机与 bucket

回目录回项目

ZeRO/FSDP 实现不会等整张图都结束才通信，常见做法是按参数 bucket 或 FSDP unit 粒度流水：

  • 前向即将进入某个 block 前，预取该 block 参数分片并 all-gather。
  • block 前向算完后释放完整参数，只留 shard。
  • 反向产生某些梯度后立刻 reduce-scatter，避免完整梯度长期占显存。
  • 下一个 bucket 的通信尽量和当前 bucket 的计算重叠。

因此判断 ZeRO 好不好，不能只看总通信量，还要看 bucket 大小、layer 粒度、计算/通信能否掩盖、网络带宽和模型每层计算强度。

FSDP/FSDP2：同一类状态分片思想在 PyTorch 里的生命周期

回目录回项目

前面一直在讲 ZeRO，这里先明确三个名字，避免“讲完 ZeRO 突然接 FSDP2”的跳跃：

  • ZeRO：DeepSpeed 的分片思想，按“拆 O → 拆 O+G → 拆 O+G+W”分三级（stage 1/2/3）。
  • FSDP：PyTorch 对同一思想的实现。最强分片模式对应“参数、梯度、优化器状态都分片”（接近 ZeRO-3）；只分梯度和优化器状态的模式接近 ZeRO-2。所以“FSDP”和“ZeRO-3”不是两套完全无关的技术，而是同一类状态分片思想的不同实现/命名。
  • FSDP2：PyTorch 的第二代实现。它把 FSDP1“整块模块拍平成一个大 flat buffer、再整体 all-gather”改成按参数（DTensor）粒度分片，能精确控制“哪一刻 all-gather、哪一刻 reshard”，也更好和 torch.compile 配合。

一句话：ZeRO 是思想，FSDP1/FSDP2 是 PyTorch 的两代实现；FSDP2 相对 FSDP1 的进步，是把分片粒度从“模块”细到“参数”。

FSDP2 的参数生命周期：一次 AllGather 只服务一个模块的前向

回目录回项目

FSDP2 不是“先把整个模型永久装回每张卡”，而是逐模块/逐层做：AllGather → 前向 → reshard →（反向需要时再 AllGather）→ ReduceScatter → 本地 optimizer 更新。

  • 关键逻辑：参数只在被用到的那个瞬间才是完整的，用完立刻释放。
  • 所以显存峰值 = 持久分片 + 当前这一层（或预取的下一层）的完整参数，而不是整个模型的完整副本。

一个 FSDP 参数单元的概念时序：


前向前 AllGather 拼出本层完整参数 → 前向读取权重

  → reshard_after_forward=True 时释放完整表示，只留分片

  → 反向需要权重时按策略重新 AllGather

  → 梯度 ReduceScatter：全局梯度求和后的分片留在对应 rank

  → optimizer 更新本 rank 负责的参数分片

如果前向后不立刻重新分片，意思是把刚刚 all-gather 出来的完整权重多留一会儿，尝试省掉反向再汇集的时间；代价是完整参数占用更久。这只是生命周期策略变化，不等于 ZeRO-2。

四类状态与 18P 口径

回目录回项目

把一次更新涉及的显存分四类：参数、梯度、优化器状态（Adam m/v + 可能 FP32 master）、激活与临时缓冲。ZeRO/FSDP 主要分片前三类稠密状态；AC 影响激活；UniRec 管理稀疏表及其优化器——它们可能同时竞争 HBM，但不是同一个内存池的同一种优化。

理想化存储公式（BF16 参数 2B/元素、FP32 梯度 4B、FP32 master 4B、Adam m/v 各 4B，完整副本 18P；N=数据并行度）：

状态每 rank 字节（忽略 padding/bucket/激活）
全副本18P
ZeRO-16P + 12P/N
ZeRO-22P + 16P/N
ZeRO-318P/N

这只是理想化比较，step 峰值还可能同时包含当前完整层、预取下一层、通信 bucket、激活与 PS 缓存，不能据此承诺“2.25GB 就能训”。

一个容易漏的点：常驻状态下降幅度 ≠ 执行峰值下降幅度。

  • 分片后长期保存的是 1/N 分片，但执行某一层时，临时 all-gather 出的完整权重与原有分片同时存在。
  • FSDP2 的 CPU 小模型实验：进程数 2→4 时，保留状态从 18 MiB 减到 9 MiB（减半），执行峰值却只从 39 MiB 减到 30 MiB（减约 23%）——因为执行中还要 21 MiB 其他张量和缓冲。
  • 结论：分析容量不能只看常驻分片，要看模块执行时参数与激活各保存多久。

AC、FSDP2、MoE 怎么一起影响一次训练

回目录回项目

关键结论：AC 不能替代 All-Gather，FSDP 也不能替代激活重算。重算需要权重，但“开 AC 必多一次 All-Gather”也不成立——框架可能复用反向已汇集的参数。峰值显存要按时间取 max：


M_peak = max_t [持久状态 + 完整参数及预取 + 激活 + 梯度与通信临时区 + PS 工作集 + 其他]

接入顺序（本地 Qwen 示例）：先 AC → 再逐层编译 → 再 FSDP。先 AC 让重算语义进入层执行，再编译让编译器处理图，再 FSDP 组织参数生命周期。

常见误区

回目录回项目
  • 误区：ZeRO 是模型并行。 更准确说它是模型状态分片；ZeRO-3 运行时会临时 all-gather 参数，但层计算本身通常仍由每张卡用不同数据副本执行。

TP：把同一层的大矩阵乘法拆给多张 GPU

回目录回项目
03_concepts/tp_tensor_parallel.md

Tensor Parallelism（TP，张量并行）拆的是同一层里的矩阵乘法，不是把 batch 拆开，也不是把前后层拆开。它让多张 GPU 一起算同一个 layer 的不同矩阵块，单卡显存和单卡计算下降，但需要在层间同步中间结果。

主线：一层 FFN 里先升维再降维，TP 就沿这条矩阵链拆

回目录回项目

当 hidden size、intermediate size 或 attention projection 很大时，单张 GPU 既要放完整权重，又要独自完成大 GEMM，容易显存不够或算得太慢。TP 把同一层的大矩阵横向切给多张 GPU：每张卡只保存/计算一部分矩阵块，用一次或少量 collective 把局部结果合成下一层需要的 hidden。

W1 / W2 是什么，为什么会有两个矩阵

回目录回项目

Transformer block 里通常有 Attention 和 FFN/MLP。以最常见 FFN 为例，它不是一个矩阵，而是两次线性变换：


输入 hidden X [B,S,H]

  └─ W1: H -> 4H 或 intermediate_size，先升维

       得到 U = X @ W1

       经过激活函数 GeLU/SwiGLU

  └─ W2: 4H -> H，降回 hidden size

       得到 Y = act(U) @ W2

所以 W1/W2 不是“网络外面生成出来的两个东西”，而是 FFN 层天然就有的两组权重。Attention 里的 Q/K/V/O projection 也类似有多个矩阵，TP 的思想一致：把大矩阵按列或按行切开。

怎么设计：W1 列切产生分片中间态，W2 行切消费这份分片

回目录回项目

假设 TP=2，W1 形状是 [H, 4H]，W2 形状是 [4H, H]。

W1 列切：每张卡算一部分输出通道

回目录回项目

W1 = [ W1_a | W1_b ]       # 按列切，输出维度被切开



GPU0: U_a = X @ W1_a       # 得到前一半中间通道

GPU1: U_b = X @ W1_b       # 得到后一半中间通道



U = [U_a | U_b]            # 逻辑上拼起来就是完整 U

列切的好处是每张卡拿同一个输入 X，只算不同的输出列，不需要马上 all-reduce。中间激活 U 天然被分片，每卡保留自己的那一半即可。

W2 行切：每张卡吃自己那部分中间通道，输出需要求和

回目录回项目

W2 = [ W2_a

       W2_b ]              # 按行切，输入维度被切开



GPU0: Y_a = act(U_a) @ W2_a

GPU1: Y_b = act(U_b) @ W2_b



完整 Y = Y_a + Y_b         # 因为矩阵乘法按输入维度切时，结果要相加

这就是为什么常说 “W1 列切、W2 行切”：这样 W1 产生的分片 U 正好被 W2 的对应行分片消费，中间不用把 U 拼成完整张量，只在 W2 后做一次 all-reduce 求和得到完整 Y。

这条链解释了相邻小节的关系：先明白 W1/W2 为什么天然相接，再看切分如何让中间态保持分片，最后再看 W2 后为什么必须通信补齐 hidden。

它怎么并行，明明 W1 和 W2 有先后关系

回目录回项目

W1 和 W2 确实有先后关系，TP 并不是让 W1 和 W2 同时算。TP 的并行发生在每一层矩阵乘内部：


时间 t1：GPU0/GPU1 同时算 W1 的不同列块

时间 t2：GPU0/GPU1 同时算 W2 的不同行块

时间 t3：GPU0/GPU1 对 W2 的局部输出做 all-reduce

所以加速来自“同一个大 GEMM 被拆成多个小 GEMM 并行跑”，不是来自破坏层间依赖。依赖还在，但每个依赖节点内部变宽了。

通信与代价：W2 后补齐 hidden，长序列时通信放大

回目录回项目
  • 前向 W1 后：通常不通信，因为列切输出 U_a/U_b 可继续分片保留。
  • 前向 W2 后：需要 all-reduce，传的是每张卡算出的局部输出 Y_a/Y_b，通信后每张卡得到完整 Y，供残差连接、LayerNorm 或下一层使用。
  • 反向 W2：梯度会沿着相反路径传播；对行切/列切权重和输入梯度的通信位置与前向对应，常见会在某些输入梯度上 all-reduce 或 reduce-scatter。
  • Attention TP：QKV projection 可列切，O projection 可行切，逻辑与 FFN 的 W1/W2 类似。

核心边界：TP 通常不是以传权重为主，而是传每个 GPU 对同一个 token hidden 算出的局部结果或局部梯度，让下一步拿到完整或重新分片的 hidden。

通信量怎么粗算

回目录回项目

设 micro-batch token 数为 T = batch_size * seq_len，hidden size 为 H，TP 度为 N，每个元素 bytes 为 b。

  • W2 前向 all-reduce 的张量形状通常是 [T, H]，大小约 T * H * b。
  • ring all-reduce 单卡通信量约 2 * (N-1)/N * T * H * b。
  • 反向还会有对应的梯度通信，粗略可再乘一个相近量级。

这说明 TP 通信量跟参数量 P 不直接一一对应，而跟每层输出激活大小 T×H和层数强相关。序列长、batch 大、hidden 大时，TP all-reduce 带宽压力明显。

什么时候变快，什么时候变慢

回目录回项目
  • 单卡矩阵更小，单卡 FLOPs 约降为 1/N，能训练更大 hidden/intermediate。
  • 大矩阵 GEMM 拆分后仍能保持较高 GPU 利用率，尤其是单层计算强度足够大时。
  • W1 列切 + W2 行切把中间分片串起来，减少不必要的中间 all-gather。

什么时候会变慢

回目录回项目
  • batch/seq 太小，单卡 GEMM 太碎，通信延迟占比高。
  • TP 跨机而不是机内 NVLink/NVSwitch，all-reduce 带宽不足。
  • 层间需要频繁完整 hidden，导致 all-reduce 暴露，无法被计算掩盖。

和我的项目怎么关联

回目录回项目

项目一稠密层/Attention/MoE expert 内部 MLP 可能用 TP：

  • 用了什么能力：W1 列切 + W2 行切，把同一层大矩阵横向拆给多卡。
  • 解决什么问题：单层大 GEMM 的显存/计算放不下。
  • 达到什么效果：支撑 B 级稠密 backbone 和 30B 级 MoE expert 内部 MLP 的单层计算；代价是随 token 数增长的激活通信，所以动态组批和负载均衡会直接影响 TP 暴露通信时间。

PP：把网络层分段，像流水线一样传激活

回目录回项目
03_concepts/pp_pipeline_parallel.md

Pipeline Parallelism（PP，流水线并行）拆的是模型层。例如 48 层 Transformer 分给 4 张 GPU，每张卡负责连续 12 层。前向时上一段把激活传给下一段，反向时下一段把激活梯度传回上一段。

主线：层放不下就切 stage，stage 之间传边界激活

回目录回项目

PP 的阅读顺序是：先看层怎么分到 stage，再看 stage 边界传什么，最后看 micro-batch 怎么填流水线。当模型层数太多或单卡放不下完整层参数/激活时，PP 把不同层放到不同 GPU 上，让每张卡只承担一段网络。它主要省单卡模型层显存，代价是 stage 之间传激活，并可能出现流水线气泡。

拆的是什么

回目录回项目

PP 拆 layer，不拆一个矩阵，也不拆 expert。它解决的问题是：完整模型层数太多，一张卡放不下所有层的参数/激活，就把不同层放到不同 GPU。


GPU0: Layer 0-11

GPU1: Layer 12-23

GPU2: Layer 24-35

GPU3: Layer 36-47

怎么设计：前向传 activation，反向传 activation gradient

回目录回项目
  • 前向传激活：GPU0 算完第 11 层，把 hidden activation 发给 GPU1。
  • 反向传梯度：GPU1 反向算出对输入 activation 的梯度，再发回 GPU0。
  • 传的是什么：层边界处的 activation 和 activation gradient，形状通常与 [micro_batch, seq_len, hidden] 相关。

PP 的通信量不主要看参数量，而看 stage 边界 activation 大小和 micro-batch 数。通信量可粗略按：2 * 边界数 * micro_batch_count * T * H * bytes，其中前向一次、反向一次。

为什么要 micro-batch

回目录回项目

如果整个 batch 一次性走完 GPU0 再走 GPU1，后面的 GPU 会一直等，流水线有气泡：

  • PP 把 batch 切成多个 micro-batch。
  • GPU0 算 micro-batch 2 时，GPU1 可以算 micro-batch 1，尽量让各段都忙起来。

设 p 个阶段完全平衡，每阶段前向 tf、反向 tb，m 个 micro-batch。填满排空调度的完成时间：


T = (m + p − 1)(tf + tb)，   卡利用率 u = m/(m + p − 1)

m 项是真实计算，p−1 项是填充和排空的气泡。micro-batch 越多气泡占比越小，但全局 batch 不变时 micro-batch 变小，要和小矩阵的执行时间一起权衡。

代价

回目录回项目
  • 有 pipeline bubble，stage 越多、micro-batch 越少，空等越明显。
  • 层切分不均会让慢 stage 拖住全局。
  • 与 TP/DP/ZeRO 组合时，调度复杂，激活重算和通信重叠要一起考虑。

调度选择：时间轴和显存轴是两回事

回目录回项目

比较调度要看两根轴：完成时间（气泡大小）和显存峰值（每份激活要保存多久才等到自己的反向）。没有一种调度两根轴同时占优：

调度气泡主要代价
填满排空 fill-drain最大（先全部前向再全部反向）激活驻留最高，容量紧张时不可行
1F1B与 fill-drain 相同显存最省，但比 fill-drain 略慢约 3%
交错 1F1B（虚拟流水线）缩小到 1/v（v=每卡层块数）跨界消息翻倍以上
零气泡 Zero-Bubble把权重梯度 dW 填入空隙，下界可到 0靠后阶段激活保留更久
DualPipemicro-batch 两端相向注入每卡保存两份参数，参数量翻倍

关键结论：“1F1B 更好”只在显存轴上成立，在时间轴上反而略慢。所以先判断约束在时间还是容量，再选调度；容量紧张时先排除峰值不可行的，再比完成时间。

回目录回项目

项目里 PP 不是主路径：

  • 用了什么能力（边界）：层切分 + stage 间激活/梯度传递 + micro-batch 填气泡，用于解释“层切分和激活传递”。
  • 解决什么问题：30B 级优先用 ZeRO/FSDP、TP、EP、AC/SAC；是否启用 PP 取决于层数、单卡显存、跨机拓扑和框架支持。
  • 达到什么效果（诚实）：当前没有 PP 启用的项目证据，答辩别声称“用了 PP”，用这张卡讲清和 TP/EP 的区别即可。

SP：把序列维度的层内激活拆开，降低激活显存

回目录回项目
03_concepts/sp_sequence_parallel.md

Sequence Parallelism（SP，序列并行）通常和 TP 配合，把某些按 token 独立计算的层（LayerNorm、Dropout、部分 residual）沿 sequence/token 维度切到不同 GPU 上，从而减少每张卡保存的激活。

主线：把序列维切开，省非 GEMM 层的激活

回目录回项目

TP 会把 hidden/channel 维度切开，但有些层不需要完整 hidden 矩阵常驻每张卡。SP 进一步把 token/sequence 维度上的激活分散保存，降低每张卡的 activation 峰值。它通常不是单独使用的“扩模型主策略”，而是 TP 的配套显存优化。

拆的是什么

回目录回项目

SP 拆的是 token/sequence 维度上的激活，不是参数。假设 hidden 是 [T,H]，SP=2：


GPU0: token 0..T/2 的 hidden

GPU1: token T/2..T 的 hidden

对每个 token 独立的操作可以直接在本卡算；但如果下一步矩阵乘或 attention 需要 TP 布局，就要做 all-gather/reduce-scatter 在 TP 布局和 SP 布局之间切换。

为什么有效：GEMM 交给 TP，SP 省 LayerNorm/Dropout 等序列激活

回目录回项目

TP 只切 hidden/channel 维，但 LayerNorm、Dropout、residual 这类逐 token 算子每卡仍要过一遍完整 [T,H]，它们的中间结果每卡都存一份。SP 把 sequence 维也切开后：

  • 逐 token 算子的激活按 token 分片常驻：每卡只存自己那一段，峰值随之下降。
  • 不是省参数、也不省 GEMM 计算：专省“非 attention-heavy 层的激活”。

核心技术点

回目录回项目

SP 的核心不是切法，而是布局切换：SP 布局（token 分片）省激活，TP 布局（hidden 分片）适合 GEMM，两类算子在层内交替出现，所以要在两者之间 all-gather / reduce-scatter 切换。设计要点就是“哪一步用哪个布局、切换在哪发生、通信花多少”。

更易记的口径：AllReduce = ReduceScatter + AllGather，SP 只是把这两半拆到不同算子边界：

  • 进列并行线性层前 AllGather：把 token 分片收齐成完整序列布局。
  • 出行并行线性层后 ReduceScatter：求和后重新按位置分片。
  • 中间的 LayerNorm / Dropout / 残差：各卡只算自己的位置，不用每卡存一份完整激活。
  • 举例：[8192,4096] BF16 激活 64 MiB——四卡各存一段 → 每卡 16 MiB（合计 64）；四卡各存完整 → 256 MiB。省在“保持序列分片的那个区间”，不是所有激活都小四倍。

通信与边界：重分片 hidden，不等于 CP 环传 KV

回目录回项目
  • 传的是什么：token hidden 激活或其梯度。
  • 通信方式：常见是 all-gather 拿完整序列布局，或 reduce-scatter 把结果重新切回序列分片。
  • 为什么传：不同算子需要的张量布局不同。SP 布局省激活，TP 矩阵乘可能需要按 hidden/channel 分片。

和 CP 的区别

回目录回项目

SP 和 CP 别混：

  • SP：节省 Transformer 层内非 attention-heavy 部分的激活显存。
  • CP：面向长上下文 attention，把上下文/KV 分布到多卡，解决单卡承载不了超长序列 attention 的问题。
  • 一句话：SP 是层内激活布局优化，CP 是长上下文 attention 计算组织。

和我的项目怎么关联

回目录回项目

项目里 SP 是 TP 的配套能力，不是主亮点：

  • 用了什么能力（边界）：把序列维的非 GEMM 层激活按 token 分片，省激活显存。
  • 解决什么问题：TP 只切 hidden 维，LayerNorm/Dropout/残差的激活每卡仍存一份完整 [T,H]。
  • 项目落地边界：是否启用 Megatron 风格 SP 待核验；项目二“百级扩到十万级”的核心更靠 CP、SparseGroup、CP-GSU，别把 SP 讲成项目主用。

CP / Ring Attention：把长上下文切段，让 KV 环形流动

回目录回项目
03_concepts/cp_ring_attention.md

Context Parallelism（CP，上下文并行）拆的是attention 的序列上下文：每张 GPU 只常驻一段 token 的 K/V，本地 query 需要看全局上下文时，K/V 分块沿环形 send/recv 轮转。它解决的是超长上下文 attention 的 KV/激活显存峰值，不是 CP-GSU 那种 padding 稀疏计算。

主线：query 要看全局 KV，但单卡放不下完整上下文

回目录回项目

标准 attention 的语义是：每个 query token 都要和所有 key token 做相似度。如果序列长度 S 很大，问题会同时出现在三处：

  • KV 常驻显存大：每张卡如果都放完整 K/V，上下文越长越容易 OOM。
  • attention 工作区大：QKᵀ / softmax / block 中间态随 S 增长。
  • 计算量大：全局 attention 本身仍是 O(S²)。

CP 的思路不是改变 attention 语义，而是改变 K/V 的存放方式：完整上下文不再同时出现在每张卡上，而是被切成 N 段分散保存。

怎么设计：本地 query 不动，KV 分块绕环流动

回目录回项目

设 S=100k、CP=4，序列被切成四段：


GPU0: token 0..25k 的 Q/K/V

GPU1: token 25k..50k 的 Q/K/V

GPU2: token 50k..75k 的 Q/K/V

GPU3: token 75k..100k 的 Q/K/V

每张 GPU 负责本地 query，但这些 query 最终要看完整 K/V。Ring Attention 的做法是：

  1. 本轮先算本地块：GPU0 用 KV0 计算本地 query 对本地上下文的 attention；其它 GPU 同理。
  2. KV 块传给邻居：每张 GPU 把当前 KV 块 send 给下一张卡，同时 recv 上一张卡传来的 KV 块。
  3. 下一轮继续算远端块：GPU0 收到 KV3 后，继续算本地 query 对 KV3 的 attention。
  4. 转满一圈后语义完整：每张 GPU 的本地 query 都看过所有 KV 块，再合成完整 attention 结果。

所以 CP 传的主要是 K/V 分块（或实现优化后的 attention 中间块），不是参数，也不是样本。通信方式是相邻 rank 的 ring send/recv，不是 all-to-all。

省什么，不省什么

回目录回项目

CP 的收益要说准：

  • 省的是单卡上下文常驻显存：每卡只常驻约 1/N 的 K/V 和局部工作区。
  • 不省总 attention 计算量：每个 query 仍要看完整上下文，全局计算量仍接近 O(S²)。
  • 可隐藏一部分通信等待：KV 轮转可以和当前 attention block 计算重叠，但这属于第 5 层调度问题，不是 CP 本身减少通信量。

通信量粗算：每张 GPU 要接收其它 N-1 份 KV 分块；每个 token 的 K/V 约 2 * H * bytes，单卡通信约：


(N-1)/N * S * 2H * bytes

反向还会有梯度或重算相关通信，实际口径取决于实现。

和 SP / CP-GSU 的边界

回目录回项目
  • SP：更偏把层内序列维激活分片，省 LayerNorm/Dropout 等非 GEMM 层激活。
  • CP / Ring Attention：更偏让本地 query 通过 KV 轮转看到远端上下文。
  • CP-GSU：项目里的长序列稀疏化模块，核心是把 padding dense 计算改成只算真实行为位置；它不是 Ring Attention。

这三个都和“序列长”有关，但对象不同：SP 拆激活，CP 轮转 KV，CP-GSU 跳过 padding 无效位置。

EP：把 MoE 的专家拆开，让 token 送到目标专家

回目录回项目
03_concepts/ep_expert_parallel.md

Expert Parallelism（EP，专家并行）拆的是 MoE 层里的 expert 网络。每张 GPU 只放一部分 expert，token 经过 router 选中 expert 后，需要通过 all-to-all 被送到对应 expert 所在 GPU；expert 算完后，再 all-to-all 送回原 token 位置。

主线：先把 expert 参数铺开，再让 token 去找目标 expert

回目录回项目

EP 的叙事主线是“参数放哪、token 去哪、结果怎么回来”。MoE 模型想增加 expert 数量来扩大参数容量，但有两个“爆”要解决：

  • 每张 GPU 都复制所有 expert → 显存爆；每个 token 都跑所有 expert → 计算爆。
  • EP 的目标：expert 参数横向铺到多张 GPU，每个 token 只激活 top-k 个。
  • 代价：token 必须跨卡找 expert，all-to-all 成为核心通信。

MoE 里到底有什么

回目录回项目

一个 MoE FFN 可以理解成“很多个 FFN 专家 + 一个 router”：


输入 token hidden X [T,H]

  └─ router: 为每个 token 打分，选 top-k 个 expert

  └─ expert_0: 一个小 FFN

  └─ expert_1: 一个小 FFN

  └─ ...

  └─ expert_E-1

输出 Y：把选中 expert 的输出按 router 权重合并

expert 本身通常也是两层 MLP，例如 H -> intermediate -> H。EP 不等于 TP：TP 是切一个矩阵；EP 是把不同 expert 放在不同 GPU 上。

router 的口径分三步，最后一步按实现不同，要格外注意：

  • 打分：logits = x @ Wᵀ（[T,D]×[D,E] → [T,E]）。
  • 归一：专家维 softmax。
  • 选专家：top-k 选出专家编号和权重，再乘 route_scale。
  • ⚠️ 权重是否重归一化按实现不同：Qwen router 的 norm_topk_prob=True 会把选中的 top-k 权重重新归一成和为 1；UniAttention DeepSeek 风格是全专家 softmax 后直接取 top-k、不重归一（选中权重之和可能 <1）。比较两个实现前必须先固定这个开关，否则“专家编号一样”也不等于输出和梯度等价。

到这里就能接上下一节：router 决定 token 去哪个 expert，EP 决定 expert 放在哪张 GPU、token 如何跨卡往返。一个重要边界：MoE 只改变 FFN，不自动改变 Attention 或 PS。两件常被混的事要分清：

  • 本地融合（native/fused grouped GEMM）：单卡内“怎么让 token 过专家”的实现优化。
  • 专家并行（EP all-to-all）：跨卡“expert 参数放哪、token 怎么 dispatch/combine”。

怎么设计：expert 拆到不同 GPU，token 通过两次 all-to-all 往返

回目录回项目

设有 E 个 expert，EP=N。每张 GPU 放 E/N 个 expert。例如 E=8、EP=4：


GPU0: expert 0,1

GPU1: expert 2,3

GPU2: expert 4,5

GPU3: expert 6,7

每个 token 不会跑所有 expert，而是 router 选 top-k 个，例如 top-2。于是 token 可能原本在 GPU0 的 batch 里，却被 router 选中 GPU2 上的 expert 5，就必须跨卡发送过去。

dispatch → 本地算 expert → combine

回目录回项目

Step 1: 每张 GPU 持有一部分 token hidden

Step 2: router 在本地为这些 token 算 expert 分数，选 top-k expert

Step 3: 按目标 expert/GPU 对 token 分桶，得到 send buckets

Step 4: dispatch all-to-all，把 token hidden 发到 expert 所在 GPU

Step 5: 每张 GPU 对收到的 token 按 expert 分组，批量跑本地 expert

Step 6: combine all-to-all，把 expert 输出发回 token 原位置

Step 7: 对 top-k 输出按 router 权重合并，进入下一层

两次 all-to-all 传的都是 token hidden，不是 expert 参数：

  • Dispatch：把 token hidden 送到它选中的 expert 所在 GPU（带 expert id、原位置、router 权重等 metadata）。
  • Combine：expert 算完后把输出 hidden 送回 token 原位置（带合并 top-k 输出的位置信息）。

top-k=2 时，一个 token 被复制发给两个 expert，最后两个输出按 router 权重加权求和。

对象流向：router 为每个 token 选择目标 expert，dispatch all-to-all 把 token hidden 发到 expert 所在 rank，expert 计算后再通过 combine all-to-all 回到原 token 位置。

代价与收益：参数能扩，瓶颈转到 token all-to-all

回目录回项目

设总 token 数为 T，hidden size 为 H，top-k 为 K，每个元素 bytes 为 b。

  • dispatch 传输的 hidden 总量约 T * K * H * b。
  • combine 再传一次 expert 输出，约 T * K * H * b。
  • 总 hidden 通信量约 2 * T * K * H * b，再加少量 metadata。

单卡看到的通信量取决于 router 分配是否均匀。负载均衡理想时每张卡约处理 T*K/N 个 expert-token；router 偏向少数 expert 时，某些 GPU 会收到远超平均 token，通信和计算都排队。

为什么 EP 能扩模型

回目录回项目
  • 每张 GPU 只放一部分 expert 参数，MoE 总参数量可以很大，但每个 token 只激活 top-k 个 expert，实际计算量近似按 K 个 expert 算。
  • expert 参数规模随 E 增长，但每 token 计算不随 E 线性增长，这就是 MoE 的“参数多、计算相对省”。
  • EP 让 expert 参数横向铺到多卡上，降低单卡 expert 参数显存。

为什么 EP 不一定快

回目录回项目
  • all-to-all 是不规则通信，受网络拓扑、token 分布、bucket 粒度影响很大。
  • top-k 越大，token 被复制到更多 expert，dispatch/combine 通信量线性增加。
  • capacity factor 太小会丢 token 或降级，太大又会 padding 和 buffer 变大。
  • router 负载不均会让某些 expert/GPU 成为 straggler。

单卡内实现：native/fused 只优化本地 expert 计算，不替代 EP

回目录回项目

同一 MoE 层可以有两种本地 expert 执行方式；模型结构、expert 数、top-k 和维度都不变，只是“本地 expert 怎么算”的实现不同：

维度native（逐专家 for 循环）fused（grouped GEMM）
分发where/布尔索引，不排序permute 按专家排序成连续段
专家计算Python for 循环 E 次grouped GEMM：一次 kernel 算全部
kernel launchO(E) 次O(1) 次
合并y[idx]+= 散射累加unpermute（scatter_add 合 top-k 贡献）
权重布局每专家独立 Linear堆成 w1[E,D,2*inter]、w2[E,inter,D]

fused 的三阶段：

  1. permute：把乱序 token 按“要去的专家”重排成连续段，[T,D] → [T'=T×K,D] + offs + 逆映射。
  2. grouped GEMM：按 offs 分段，一次 kernel 内所有专家的 tile 并行铺满 GPU。
  3. unpermute：按逆映射把 [T',D] scatter_add 回 [T,D]，合并同 token 的 K 份贡献（不是简单撤销排序）。

w1[E,D,2*inter] 的来历：SwiGLU 把 gate+up 拼成一个 [D,2·inter]（2=两分支），再按专家堆 E 份。permute 是 grouped GEMM 的前提——先把 token 按专家排成连续段，才能按 offs 切段并行；代价是多两趟排序，换来并行净赚。

fused 快在两个层面：① 省 CPU launch（E 次 → 1 次）；② 小专家喂不满 GPU 的问题被“所有专家 tile 合起来一次调度”解决，Tensor Core 利用率高。数值上 fused 默认 bf16、native 可 fp32，数学等价但有舍入差。

FLOPs 口径（接 MFU 卡）：MoE 的 FFN 有效宽度 = k × 专家中间维，只按激活专家数 k 算，不按总专家数 E；grouped GEMM 和 native 是同一计算量的不同实现，不改变 FLOPs。

和 TP/DP 的关系

回目录回项目
  • DP：不同 GPU 处理不同样本，最后同步梯度。
  • TP：同一个 expert 或同一层矩阵内部再切矩阵。
  • EP：不同 expert 分布到不同 GPU，token 在 expert 之间分配。

调度与重叠：不减少工作量，只减少暴露等待

第 5 层回答：已经确定要读、要搬、要通信、要计算的工作，怎样排时间线，才能让 GPU 少空等。它不改变模型数学，也不减少必须传的字节；它减少的是这些工作暴露在 step time 里的等待。

这一层的内部逻辑

回目录

调度与重叠按三步读：

  1. 先找依赖：当前 batch 前向必须等样本、参数、稀疏向量准备好；反向通信必须等对应梯度产生。
  2. 再找可提前的工作：下一窗口样本读取、H2D、key 分发、Embedding 预取、参数 all-gather、梯度 bucket reduce-scatter，哪些能在当前计算背后启动。
  3. 最后看执行资源能否并行：CPU 线程、DMA、网络、GPU stream、NCCL/HCCL stream、event 依赖是否允许这些工作真的同时推进。

这层的核心判断不是“少做了多少”，而是：同样的工作，有多少从 critical path 上挪走了。

典型机制怎么串起来

这一层的内部逻辑

回目录

算子与编译优化按四类对象读：

  1. 少搬：FlashAttention 不落完整 attention 矩阵，减少 HBM 读写；这类优化主要解决带宽受限。
  2. 少算：CompileMask、CP-GSU 跳过不可见 block 或 padding 位置；这类优化直接减少无效 FLOPs。
  3. 少 launch / 少碎片：MoE 融合、grouped GEMM 把很多小 expert GEMM 组织成更大的执行单元，减少调度开销。
  4. 用重算换显存：AC/SAC 不减少总数学工作，反而多算一次，但换掉激活存储峰值。

这四类不能混写。比如 FA 主要不是“少算 attention”，而是少搬中间矩阵；MoE 融合主要不是“减少模型 FLOPs”，而是让碎小 GEMM 更适合硬件执行。

算子与运行时：kernel 怎么被提交、怎么在 GPU 上执行

回目录
03_concepts/kernel_runtime.md

一句话结论

回目录

“算子”描述数学工作（矩阵乘、激活），kernel 在加速器上真正执行它，launch 是 CPU 发起这次执行的异步动作。优化分两条：缩短 kernel 执行时间，以及减少主机提交与等待——后者是小算子多、GPU 等 CPU 时的主瓶颈。

主线：先分清异步提交、数据依赖和真正执行

回目录

CPU 提交后立即返回，GPU 按队列和依赖执行。提交是异步的，但计算要等数据就绪：数据何时传完、缓冲何时能复用，都要显式管理，否则会读到半成品、或覆盖还在用的数据。

怎么设计：三个机制

回目录

1. stream / event：执行顺序与缓冲复用

回目录
  • 同一条 stream 里任务按提交顺序执行：把 H2D 和读它的 kernel 放同 stream，计算自然排在复制后。
  • 跨 stream 用 event：复制流在 H2D 后 record 事件，计算流 wait 事件再读。
  • 缓冲复用的关键是“最后一次读写之后记录事件”：主机源缓冲在复制引擎读完后可写下一批；GPU 输入缓冲要在 kernel 用完才能覆盖。漏记一个“已用完”事件，复制引擎就永远等不到、程序停住（不是变慢）。

2. warp / occupancy / 延迟隐藏

回目录
  • warp 是 32 个线程一起发射的单位；线程块（block）由多个 warp 组成，SM 按 block 调度。
  • 驻留（residency）受三类资源限制：线程槽、寄存器、共享内存，取三者的最小值；occupancy = 驻留 warp 数 / SM 最大 warp 数。
  • 延迟隐藏靠驻留 warp 提供的在途请求：要达到 HBM 峰值带宽，需要 在途字节 ≥ 带宽 × 延迟（Little 定律）。工作集越大 → 驻留块越少 → 在途字节越少 → 有效带宽可能反而降。

3. 计算单元分工与 warp specialization

回目录
  • 矩阵单元按固定形状块执行 MMA（如 16×8×16，一条指令 4096 FLOPs）；向量单元做激活/逐元素。Hopper 的 warpgroup 级 MMA 异步执行，发出后能做别的。
  • warp specialization：生产者 warp 只发异步复制、消费者 warp 只做计算，用共享内存里的栅栏交接（“满”栅栏=复制完成，“空”栅栏=算完可覆盖）。FlashAttention-3 就这么安排 producer/consumer warpgroup。

为什么有效：缩短执行 + 减少等待

回目录

一次调用的耗时 = 提交 + H2D + kernel + D2H：

  • kernel 快了，提交和复制还在：例子里 kernel 从 20 μs 降到 5 μs，整次只从 35 μs 降到 20 μs（加速 1.75 倍），剩下 15 μs 是提交+复制。
  • 所以优化要么重叠（双缓冲、warp specialization），要么合并（减少小算子）。

诊断与边界：停住、变慢、昇腾对应关系

停住 vs 变慢：程序完全不动，是在等一个不会到来的事件（漏记 event、跨流循环等待、或集合通信缺一个对端）；程序仍在出结果只是慢，是带宽/延迟问题，回到时间线逐段计时。

这张卡讲的不是并行策略，而是：模型已经能跑之后，单卡/单层内部还有哪些无效工作可以压掉。

主线分两段：

Attention 链路：FA 决定块内怎么算，CompileMask 决定哪些块要算，Label Packing 决定哪些 token 允许互看

回目录回项目

FlashAttention 解决的是 标准 attention 的 IO 问题：

  1. 按 tile 读取 Q/K/V。
  2. 在片上维护行级 max/sum。
  3. 用 online softmax 得到和标准 attention 等价的结果。
  4. 不把完整 [L,L] score/probability 写回 HBM。
  5. 反向时用轻量统计量重算必要块。

关键口径：FA 不改变标准 attention 的数学目标，主要减少巨大中间矩阵的 HBM 读写。FA1 主要解决 IO；FA2 改进并行划分；FA3 面向 Hopper 做 TMA 搬运和 WGMMA 异步流水；FA4 面向 Blackwell 继续处理非 MMA 瓶颈，例如指数、shared memory、TMEM 和前后向流水。

CompileMask 解决的是 复杂 mask 的表达和 block 跳过。它不是一个固定 mask，而是 UniAttention 自研的声明式 mask 编译栈：

  • frontend：用 BoolExpr/MaskSpec AST 表达 (q,kv)→bool 的可见性规则。
  • codegen：把 AST 编译到 TileLang kernel，并从 forward mask 符号推导 backward kernel。
  • verifier：校验编译出的 kernel 是否和声明规则一致。

真正加速点是：区间分析 → block 跳过。codegen 用 _DenseIntervalValue [lower,upper] 推导每个 query 可见的 kv 连续区间，把边界对齐到 block，只循环这些 block。被 mask 的 block 连 QKᵀ 都不算，不是算完再乘 0。

Label Packing 是上面两者的业务触发场景。它把多个目标拼进一条序列，让历史只编码一次；但拼接后必须保证 组间不该互看，否则 listwise 语义会被破坏。

  • 普通 causal mask 不够：隔离不了“后组看前组”。
  • 逐点 mask 太慢：会带来 N² 判断，并且可能先算 QKᵀ 再丢弃。
  • CompileMask 的作用：把组隔离规则编译成 block-sparse attention，整块不可见就整块跳过。

正确性边界也要说清：teacher forcing 要每组分别右移，不能把多组整体右移导致输入侧泄漏；独立多目标训练 p(SID_j | history) 和 listwise p(item_j | history, item_<j) 是不同任务，不能只因为“多个商品拼起来”就混为一种优化。

MoE 链路：EP 负责跨卡送 token，融合算子只解决本地 expert 怎么高效算

回目录回项目

MoE 慢不只慢在 expert 计算，还慢在 router 分桶、dispatch/combine、padding 和许多小 GEMM。先分清两层：

  • EP all-to-all：跨卡通信，负责把 token hidden 送到 expert 所在 rank。
  • MoE 融合：单卡内部执行优化，负责把本地收到的 token 高效过专家。

因此，MoE 融合 不会减少 EP dispatch/combine 的 token hidden 字节数。

native 实现的问题是：Python for 循环逐专家算，O(E) 次 launch；每个专家 token 数又可能很少，导致 GEMM 规模小、矩阵单元利用率低。

fused grouped GEMM 的链路是：

  1. permute：把 token 按目标 expert 排成连续段。
  2. grouped GEMM：按 offs 分段，在一次 kernel 内并行计算多个专家。
  3. unpermute / scatter_add：回到原 token 位置，合并 top-k 贡献。

权重常堆成 w1[E,D,2*inter] 和 w2[E,inter,D]，其中 2*inter 来自 SwiGLU 的 gate+up 两支。它快在两点：减少 CPU launch，以及 把多个小专家 GEMM 组织成一次 grouped GEMM，提高 Tensor Core 利用率。

Token 负载均衡和动态组批是另一条链：router 分布越均匀，EP all-to-all 和 expert 计算越容易同步结束；按 token 预算组批可以减少某些 rank token 过多导致的 straggler。它们改善的是 负载波动和等待暴露，不等于 fused grouped GEMM 本身减少了理论计算量。

FLOPs 口径也要固定：MoE FFN 有效宽度按 k × moe_intermediate_size 算，不按总专家数 E 算；grouped GEMM 和 native 是同一计算量的不同实现，不改变理论 FLOPs。

CP-GSU 稀疏化：把 padding dense 计算改成只算真实行为

回目录回项目
03_concepts/cp_gsu.md

一句话结论

回目录回项目

CP-GSU 解决的是长序列推荐里的 padding 冗余计算：旧方式把行为序列补齐成 [batch, max_seq, hidden] 后全量计算，padding 位置也消耗显存和 FLOPs；CP-GSU 改成保留真实行为位置索引，只对有效位置做 gather / scatter / 聚合，成本跟着真实长度走。

主线：从 dense padding 张量，改成稀疏有效位置流

回目录回项目

旧链路为了 batch 化，会把每个用户的行为序列补齐到同一长度。这样算子看到的是一个规整 dense tensor：


[batch, max_seq, hidden]

问题是，padding 位置并不是真实行为，却会进入计算图：它会占 HBM，产生中间激活，也会消耗算力。序列上限到十万级时，max_seq 远大于多数用户真实行为长度，冗余就会被放大。

CP-GSU 的核心变化是：不再把 padding 位置当成真实 token 物化出来。它保留三类东西：

  • 有效位置索引：哪些位置是真实行为。
  • 用户/序列分组信息：哪些行为属于同一个样本或同一段序列。
  • 紧凑 value：只存真实行为对应的向量或特征值。

后续算子只对这些有效位置做 gather、scatter、聚合或 GSU 相关计算。代价是多维护索引元数据和更复杂的稀疏算子；收益是不用为 padding 付出 dense 成本。

省什么，怎么算

回目录回项目

dense 方式的成本大致随 B·S_max·H 增长；稀疏方式的成本大致随 B·S_real·H + index_metadata 增长。

当真实长度 S_real 远小于补齐长度 S_max 时，冗余比例约为：


1 - S_real / S_max

项目口径是：减少 70% 冗余计算、显存 70GB→20GB、训练吞吐提升 70%。这个收益来自两件事：

  • 少算 padding：无效位置不再进入主要计算。
  • 少存 padding 激活/中间结果：HBM 峰值跟真实行为数走。

这里要保持诚实边界：这张卡目前能讲清机制和项目口径，但 CP-GSU 全称、模型内具体位置、输入输出 shape 仍待逐行核验。

激活重计算（AC / SAC）：用算力换激活显存

回目录
03_concepts/activation_checkpointing.md

激活重计算（Activation Checkpointing，AC）不改变模型、不改变梯度数值，只把“反向要用的中间激活”从前向存下来，改成“反向要用时再重算一遍”。本质是用额外的前向算力，换掉激活显存。

主线：前向少存激活，反向按需重算

回目录

正常训练前向会把每层中间结果存着给反向算梯度用。激活显存 ∝ batch × 序列长 × 层数，层一多、batch 一大就 OOM。AC 让前向不存这些中间激活，反向时拿输入重跑一层现算，用完即弃。

它和 FSDP2/ZeRO 不是一回事：ZeRO/FSDP 分片的是参数、梯度、优化器状态；AC 省的是激活。两条是相互独立又相互依赖的生命周期——释放完整参数不等于释放激活。

拆的是什么

回目录

把“前向算出的中间结果”按是否值得保存拆开：

  • 边界输入：必须保留（反向重算的起点），通常很小。
  • 昂贵算子输出：matmul、attention 的 [N,N]、grouped GEMM，重算贵，倾向保存。
  • 便宜算子输出：silu、layernorm、add、mul 等逐元素算子，重算几乎不花时间，倾向丢弃。

怎么设计：从 PyTorch checkpoint 到 Full/SAC/Memory Budget

回目录

torch.utils.checkpoint 本质是一个自定义 autograd.Function，核心两步：

  1. 前向在 torch.no_grad() 里跑：不建图、不存中间激活，只存最外层输入 x。
  2. 反向时 enable_grad 用 x 重跑一遍前向，这次正常存激活，立刻算梯度。

所以“重计算”不是 OneRec 自造，是 PyTorch 自带能力；OneRec 做的是把它按“逐算子 / 逐层 / 编译器预算”三种方式接进训练。下一步才是选择粒度：整层丢弃最省显存但最慢，SAC 只丢便宜算子，Memory Budget 交给编译器折中。

MoE 的特殊处理：两个 grouped GEMM 只存一个

回目录

MoE 块有 gate_up 和 down 两个 grouped GEMM，都在保存名单里本该都存，但显存存不下两个，于是按收缩维挑一个重算：每单位重算省下的显存 ≈ 1/收缩维。

  • gate_up 收缩维 = hidden，down 收缩维 = moe_intermediate_size。
  • inter ≥ hidden → 重算 gate_up（Mixtral 类）。
  • inter < hidden → 重算 down（Qwen3-30B-A3B：768 < 2048）。

边界与代价：AC 只换本地显存，不改变 collective 语义

回目录

AC 是“本地算力 ↔ 本地显存”的权衡，和跨卡通信无关：

  • 保存名单特意包含 reduce_scatter_tensor（ZeRO 梯度通信算子）并标为“保存、不重算”：否则重算区域会重复触发跨卡 collective，白增通信、破坏集合通信语义。
  • MoE 的重算选择只在本地专家计算内，不碰 all-to-all。
  • 所以 AC 开关前后，ZeRO/MoE 的通信次数和量都不变。

HSTU：用 silu/N 代替 softmax 的排序侧 backbone

回目录
03_concepts/hstu_backbone.md

一句话结论

回目录

HSTU（Hierarchical Sequential Transduction Unit）是 OneRec 排序侧的 dense backbone。核心变化是：把历史行为对候选的影响建模成逐对相关性，而不是 softmax 概率分布。

它的结构特征是：无独立 FFN、UVQK 融合投影、silu(QKᵀ·α)/N 替代 softmax、以及 user 路门控输出。

核心矛盾：排序侧历史贡献不一定是 softmax 概率

回目录

标准 Transformer 的 softmax attention 会把每个 query 对所有可见 key 的注意力归一成一行概率，总和为 1。这个设计的问题是：所有历史行为必须竞争同一个总量。

推荐排序里更常见的语义是：

  • 多个历史行为可以同时提供正向证据。
  • 某些行为也可以被抑制到接近 0。
  • 历史贡献更像 pairwise relevance，不一定是概率分配。

所以 HSTU 的替换逻辑是：


排序侧需要多个历史行为共同影响候选

→ softmax 行归一会让贡献互相竞争

→ silu/N 不跨位置归一

→ 每个 pair 的相关性可以独立放大、抑制或接近 0

/N 的作用不是概率归一，而是控制序列长度变化带来的量级漂移。

一层 HSTU 怎么算：UVQK 融合投影、silu/N attention、user 门控输出

回目录

一层 HSTU 顺着张量看是五步：

  1. 输入 LayerNorm：按 d_model 维归一。
  2. UVQK 融合投影：一个大 Linear(d_model, 2Dv·H + 2A·H) 同时产出 user/value/query/key 四路，投影后整体过 silu 再 split。
  3. HSTU attention：用 silu(QKᵀ·α)/N 替代 softmax；alpha = 1/√A，A 是每头 QK 维。
  4. user 门控：attention 输出过 LN 后，被 user 路逐元素门控，即 user * LN(attn)。
  5. 残差投影：输出投影回 d_model，加回输入。

三个结构差异要一起看：

  • 无独立 FFN：silu 激活已经融进 UVQK 投影。
  • attention 不行归一：按 pair 做 silu 相关性，并用 /N 控制尺度。
  • user 路控制输出：类似 GLU/SwiGLU，决定 attention 输出放行多少。

张量形态也要清楚：token 维 T 全程不变。输入输出是变长 JaggedData(values[T,d_model], seqlen[B], offsets[B+1])；attention 内部临时 jagged→padding 成 [B,H,N,·] 算 QKᵀ，算完再 dense_to_jagged 压回 [T,H,Dv]。因此 padding 只存在于 attention 中间，不是整条 backbone 都变成 dense padding。

mask 是这条链的一部分，不是额外机制。模型会为每个样本生成一个 [B,N,N] 可见性矩阵，用来说明“哪个位置能看哪个位置”。它对应 OneRec 的三类序列位置：

  • contextual：用户画像等上下文 token。
  • history：历史行为。
  • candidates：待排候选。

mask 的三层语义是：因果可见性、候选分组可见性、上下文可见性。这些规则决定哪些 pair 进入 silu(QKᵀ·α)/N，不是跨卡通信，也不是模型外逻辑。

工程边界与融合实现：HSTU 本身不引入 collective，融合版省本地访存和调度

回目录

HSTU 是 sample rank 本地的 dense backbone：

  • 输入：上游稀疏侧通过 Emb A2A 送回来的 embedding 向量。
  • 输出：排序分数。
  • 跨卡通信边界：发生在上游稀疏查表/梯度回传，或下游更大模型上的 TP/EP/ZeRO，不发生在 HSTU 这一层本身。

这个边界很重要：不要把“排序 backbone 怎么算”和“分布式通信怎么传”混在一起。

生产版 FusedHSTULayerFunction 与 native 逐步计算等价，但执行组织更适合 GPU：

  • 融合 LN/linear/silu 路径：addmm_silu_fwd 让 matmul 结果在片上直接过 silu，减少一次 [T,4Dv] 往返读写。
  • 手写 backward：不完全依赖 autograd 自动微分。
  • 重算省显存：forward 只保存最小集合，backward 重算 silu/qkv。
  • async wgrad：权重梯度在独立 stream 上异步算，和主反向重叠。

这些收益是本地访存、显存和调度效率，不是通信量下降。

和我的项目怎么关联：项目口径、来源与待核验

回目录

项目里排序侧 backbone 就是 HSTU：UniRec 查向量后，HSTU 用 silu/N attention + UVQK 融合投影 + 三层 mask + user 门控 计算排序分数，生产路径走 FusedHSTULayerFunction 融合 kernel。

它解决的是：softmax 概率分布不一定适合排序侧逐对相关性建模。效果是：排序侧结构更贴合业务语义，同时融合 kernel 省一次 [T,4Dv] 往返、async wgrad 与主反向重叠，是模型正确性和吞吐的一部分。

  • native output-norm：weight/bias 疑似未参与计算（表达式结果未赋回），与融合版 norm 口径是否真一致。
  • 融合 kernel 细节：FusedHSTULayerFunction 的 Triton tiling、async wgrad 的 stream/event 顺序仍未逐行展开。

多硬件底座（Backbone Infra）：把 GPU/NPU 差异隔离开

回目录回项目

一句话结论

回目录回项目

换硬件不只是换后端：算子、通信库、编译、精度、profiler 全都不同，直接把 GPU 代码搬上 NPU 会遇到算子缺失、编译入口不支持、精度分叉、归约顺序差异。Backbone Infra 把这些差异隔离在底座里，覆盖 T5 / T5-MoE / Qwen3 / DeepSeek-V4，业务只碰一层统一接口。

怎么设计：三条边界先分清

回目录回项目

多硬件底座不是“到处加 if npu”，而是把变化收在三条边界里：

  1. 路径边界：训练、生成、导出分开。训练一次处理已有目标前缀并反向；生成先 prefill 再逐 token decode；导出对齐在线推理。三条路径输入长度、cache 状态、控制分支不同，所以底座为训练和生成保留不同编译入口；是否启用生成编译由配置开关控制。
  2. 模型边界：不同 backbone 的编译粒度不同。T5 整个 Backbone 作一个 torch.compile 入口；Qwen3 逐 Transformer Block 编译；两者都不包括 Reader、UniRec PS 和 DeepSpeed step，避免把数据/稀疏/优化器状态混进模型图。
  3. 硬件边界：GPU/NPU 差异只在底座层处理，包括算子替换、通信库选择（NCCL/HCCL）、精度策略、profiler 口径和 fallback。业务模型只调用统一接口，不直接感知具体硬件分支。

为什么有效：业务只碰统一接口

回目录回项目

这一层的内部逻辑

回目录

观测层按闭环读，而不是按指标名读：

为什么 GPU-Util 不够

回目录

  • 分子是哪些模型 FLOPs：attention、FFN、MoE 是否按激活专家 k 计。
  • 分母用哪个硬件峰值：纸面 bf16 Tensor Core 峰值，还是更接近持续算力的口径。
  • step time 是否包含通信、数据等待、checkpoint、warmup。

回目录

答辩里常被问“GPU 利用率 100% 是不是就充分利用”，答案是否定的：

  • GPU-Util 高，可能只是 kernel 一直在跑，却大量是 padding 或无效计算。

  • 通信算子时间长，不一定是网络慢，也可能是慢 rank 让其它 rank 等。

任何“慢/没吃满”都先落到四类资源约束之一，再决定上什么优化：

瓶颈典型表现典型入口

怎么设计 MFU 口径：FLOPs、FLOPS、MoE 激活专家和在线统计

回目录

先分清三个词：

  • FLOPs（小写 s）：浮点运算个数（计算量）。
  • FLOPS / TFLOPS（大写 S = per Second）：浮点运算速度，T = 每秒 10¹² 次。
  • MFU：模型有效算力 ÷ 硬件峰值算力。

MFU = (一步理论 FLOPs / delta_time) ÷ 峰值 FLOPS × 100%

    = 实际 FLOPS / (峰值 TFLOPS × 1e12) × 100%

关键口径：

  • 分母用 Tensor Core 峰值（bf16），大头 FLOPs 都是矩阵乘、跑在 Tensor Core 上；silu/norm 等逐元素算子占比极小，不进分子也不进分母。B200/B300 峰值 = 2250 TFLOPS。
  • 一步理论 FLOPs ≈ 前向 ×3：前向一个线性层 Y=X·W 是 1 个矩阵乘；反向要算 2 个（dW=Xᵀ·dY、dX=dY·Wᵀ），大小都 ≈ 前向。
  • 矩阵乘基石：[M,K]×[K,N] = 2·M·N·K（2 = 一次乘 + 一次加）。

两类统计量对应两类 FLOPs

回目录

varlen 训练把 batch 拉平成 [T,d]（无 padding，cu_seqlens 标边界），从真实 mask 累计两个统计量：

  • sum_n = ΣN_i（线性）→ 投影/FFN/lm_head ∝ N。
  • sum_n_sq = ΣN_i²（二次）→ attention ∝ N²，且是逐样本平方和，ΣN_i² ≠ (ΣN_i)²。

投影/FFN 每个 token 独立过权重 → ∝ N；attention 的 QKᵀ 让 token 两两交互 → ∝ N²。

MoE 的 FLOPs 按激活专家数 k，不按总专家数 E

回目录

MoE 的 FFN 有效宽度 = k × moe_intermediate_size（k=每 token 激活的 top-k 专家数）：

  • 参数量用总专家数 E（权重都在显存）。
  • FLOPs/MFU 用激活数 k（每 token 只算 k 个）——这正是“参数多、计算省”的体现。
  • router 的 gate Linear 不计入 FLOPs。

在线版 vs 离线版

  • 离线手算：把参数、batch、seq_len 写死，只能估一个固定场景。
  • 在线统计：训练时从真实 mask 累计 sum_n/sum_n_sq，能反映变长样本和 label-packing 的真实计算量。

从 MFU 推卡数下界

回目录

总计算量 F、卡数 p、单卡峰值 P、平均计算效率 η、可用时间 T，则：


T = F / (p·P·η)，    p_compute = ceil(F / (P·η·T_available))

口径要分清：

  • 按完整迭代时间算：MFU 已经计入通信等待。
  • 只按加速器计算时间算：得到的是单卡计算效率，通信/气泡/重算/掉队者/checkpoint 要另外逐项加。
  • 参考：Llama 3 405B 在 8K–16K 张 H100 上 BF16 MFU 约 38%–43%（按整步耗时，已含通信）。
