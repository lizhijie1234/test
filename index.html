6 站（数据流）主要落在 8 层中的哪一层
① 数据（读文件 + 动态组批）第 3 层·数据与存储
② 稀疏查表（key 分发/查表/回传）第 3 层·数据与存储（内部是五级流水）

横穿全程的四个横切层是：第 1 层·硬件与集群（所有站的物理基础）、第 5 层·调度与重叠（同样的搬运/通信如何少暴露等待）、第 6 层·算子与编译（单个 kernel/attention/MoE 内部如何少算、少搬、少 launch）、第 8 层·观测（每站怎么判断是否真的快）。它们不是训练 step 的先后站点，而是每一站都会受到的约束或验证口径。

两个跨站维度：省什么、为什么难

项目一｜GR 分布式训练引擎建设与性能优化

回目录
04_projects/gr_distributed_training_engine.md

这个项目的核心不是“做了一个训练框架”，而是把零售推荐从传统 LRM 推向生成式推荐 GR 时，训练系统要同时承载 TB 级稀疏 Embedding、B 级稠密 backbone、30B 级 MoE、复杂 Attention/MoE 结构、多硬件 GPU/NPU。我的工作重点是把这些能力工程化到统一训练引擎里，并针对显存、通信、计算和数据链路做性能优化。

项目拆解

回目录

这个项目要同时压三座山，对应三条线：

  • 稀疏线：TB 级 Embedding 放不下单卡 HBM。
  • 稠密线：B 级稠密模型和 30B 级 MoE 放不下、算不动。
  • 算子/多硬件线：单卡执行效率、动态 shape、跨卡负载波动和 GPU/NPU 适配同时限制吞吐。

关键技术点

回目录
  1. 稀疏线：10TB 表放不下 HBM。难点是表整体巨大、每步只用一小块。方案是把全量参数按 key 分片放 owner 的 host MEM，HBM 只放窗口工作集，再用五级流水让“查表”和“算模型”错位执行。为什么有效：HBM 只装工作集省显存，预取让 host 侧查表与当前窗口计算重叠，减少等待暴露；代价是必须用双 Buffer + 交集同步保证预取不读旧参数。
  2. 稠密线：30B 级 MoE 放不下、算不动。难点是参数、梯度、优化器状态、激活四类显存都超单卡。方案是 ZeRO/FSDP2 切模型状态、AC/SAC 重算激活、EP 拆专家。为什么有效：状态分片省显存，MoE 每 token 只激活 top-k 专家、参数容量和计算解耦；代价是参数 all-gather、梯度 reduce-scatter、EP all-to-all 和重算开销。
  3. 算子线：有效计算密度不够。难点是 attention 中间张量反复落 HBM、expert 小 GEMM/launch 太碎、复杂 mask 仍触发无效 block 计算、长短样本混批造成慢 rank。方案是 FA4、MoE 融合、CompileMask、Label Packing 分别减少 HBM 往返、kernel launch、不可见 block 计算和重复历史编码，Token 预算动态组批 压平每卡 token 量。为什么有效：FA 改 attention tile 的访存组织，MoE 融合把多个小专家 GEMM 组成 grouped GEMM，CompileMask 在 block 级跳过不可见 QKᵀ，动态组批减少同步点上快卡等待慢卡。
  4. 多硬件线：GPU/NPU 迁移成本。难点是算子、通信库、编译路径、精度、profiler 都要适配两套硬件。方案是 Backbone Infra（多硬件底座） 把模型结构、训练/导出路径和硬件差异隔离开，业务只碰一层统一接口。

结果与指标

回目录

这些结果要按“业务落地、容量扩展、模型规模、有效算力”四类看，不要只堆数字。

  • 业务落地：支撑 10+ 业务场景从 LRM 向 GR 升级落地，说明训练引擎能力能被多场景复用。
  • 稀疏容量：支撑 10TB 级稀疏参数与千卡横向扩展，对应的是 HBM 放不下大表时，用 owner-shard、HBM–MEM 工作集和五级流水解决容量与等待问题。10TB 是系统级容量目标；千卡线性比 NPU 512 die 约 0.89、1024 die 从 0.64 回到 0.926（Nest 双流后），归因是 Nest 让 emb 通信与 dense 计算重叠，不是减少通信量，更不能归给外层五级流水。
  • 稠密/MoE 规模：支撑 30B 级 MoE 模型训练（如 Qwen3-30B-A3B：总参约 30B、每 token 激活约 3B）。核心衡量点不是只看参数量，而是 expert 分布、token dispatch/combine、负载均衡和显存状态分片是否能协同。
  • 有效算力：B300 上 Qwen3-4B、Qwen3-30B-A3B Backbone MFU 分别达 53.8%、29.57%。这是 Backbone 前反向的 MFU，是否含 dataloader / embedding / 通信时间需按 profiler 口径确认；MFU 衡量的是有效模型 FLOPs 吃到硬件峰值的比例，比单看 GPU-Util 更能说明训练效率。

答辩深水区

回目录
  • 强一致怎么保证：双 Buffer 提前预取会读到旧参数，靠窗口边界做 current∩next 交集 key 的整行同步再切表（key=100 从 10 更新成 9 的例子）。这是稀疏线最该讲深的一点。
  • 千卡线性比的归因：512 die 约 0.89、1024 die 0.64，Nest 双流后 1024 die 回到 0.926（+34.3%）——归因是让 A2A 与 dense 计算重叠、减少暴露等待，不能把数字归给五级流水或“减少通信量”。
  • MFU 53.8%/29.57% 的口径：是 Backbone 前反向口径，是否含 dataloader/embedding/通信时间要先说清，否则会被追问。

项目二-1｜LRM 长序列训练能力建设

回目录
04_projects/lrm_long_sequence_training.md

这个项目的核心是把推荐模型的行为序列从百级扩展到十万级。序列变长后，问题不是“显存大一点”这么简单，而是数据 IO、稀疏 Embedding、通信索引、padding 计算、模型结构和导出链路都会一起放大。我主导从 0 到 1 建设长序列训练能力，并把性能做到优化前 4 倍。

项目拆解

回目录

序列变长，不是“显存大一点”，而是四个环节一起被放大，对应四条优化：

  • 数据：样本解析和特征构造越来越重，训练进程容易等 CPU 备数。
  • 查表与通信：Embedding 查询碎片多、多路行为重复传坐标。
  • 计算：padding 把无效位置也算了。
  • 模型：要支持长行为建模并打通导出。

关键技术点

回目录
  1. 数据线：CPU 备数拖住训练。难点是样本解析、特征构造和变长列处理是 CPU-heavy；如果这些逻辑跟训练 worker 绑在一起，GPU 到达下一 step 前会等待样本就绪。方案是 Sample Service（分布式数据 IO 框架）把数据处理解耦成可横向扩展的服务。为什么有效：数据服务提前产出训练批次，训练 worker 减少等待，训练吞吐提升 1.6 倍。
  2. 查表/通信线：碎片多 + 重复传坐标。难点是多次 Embedding 查询碎片化、多路行为各传一份坐标。方案是合表/合并查询把查询聚合成批量操作，SparseGroup 让组内共享一份 indices/dense_shape。为什么有效：算子数减少 40%、吞吐提升 7.5%；H2D/RPC 稀疏输入载荷降约 56%。
  3. 计算线：padding 冗余计算。难点是把 [batch,max_len,hidden] 全量 dense 算，padding 也占算力和显存。方案是 CP-GSU 改成只算真实行为位置。为什么有效：冗余计算减 70%、显存 70GB→20GB、吞吐提升 70%（项目口径，结构待核验）。
  4. 模型线：长行为要能建出模、导出。难点是长行为建模不只训练能跑，还要稳定服务导出和线上推理。方案是完成 SIM、TWIN、MARM 三大模型并打通训练到导出流程。

结果与指标

回目录

这些结果要按“序列规模、数据供给、稀疏通信、有效计算”四类看。

  • 序列规模：序列长度从百级扩展至十万级，说明长行为链路从模型、数据、通信到导出都打通了。
  • 整体收益：综合训练性能达到优化前 4 倍，这是数据 IO、稀疏参数、通信压缩和计算稀疏化叠加后的端到端结果。
  • 数据供给：Sample Service 训练吞吐提升 1.6 倍，衡量的是 CPU 样本处理不再明显拖住 GPU。
  • 查表效率：合表与算子融合使算子数量减少 40%，吞吐提升 7.5%，对应的是减少 Embedding 查询碎片和 kernel 调度开销。
  • 通信压缩：SparseGroup 使 H2D/RPC 稀疏输入载荷降低约 56%（六列值+坐标理论载荷 144T→64T），衡量的是共享 indices/dense_shape 后少传重复坐标带来的总载荷下降；不是整模吞吐降 56%。
  • 计算稀疏化：CP-GSU 冗余计算减少 70%，显存 70GB 降至 20GB，吞吐提升 70%（项目口径，结构待逐行核验），衡量的是从 padding dense 改成只算真实行为后的收益。

答辩深水区

回目录
  • 4 倍是叠加结果：数据、查表/通信、计算三条线的端到端叠加，不是某个单项；各自贡献比例目前没有单独归因。
  • SparseGroup 56% 是载荷口径：是六列值+坐标理论载荷和对应 H2D/RPC 场景的下降，不是单独坐标字节下降，也不是整模通信或吞吐降 56%。
  • CP-GSU 的结构未逐行核验：机制和口径能讲清，但全称/结构/shape 还是待补，别声称已核验实现。

关键技术点

回目录
  1. DAG：硬编码没法复用。难点是训练是一条从样本到导出的流水线，每个业务各写一套没法换组件。方案是把数据、特征、模型、loss、评估、导出拆成组件，业务用配置组合。为什么有效：节点边界清楚，换数据源/模型/导出策略不用改代码，业务建模周期从月级到周级。

一、先按训练系统的四类瓶颈定位

回目录

二、再按“拆什么”理解并行策略

回目录

用户问并行策略时，必须先回答“拆的是谁”，否则后面的通信量都讲不清。

  • DP / ZeRO / FSDP：样本维度复制模型或切模型状态。每张卡处理不同 batch，最后要让所有卡对同一份模型更新达成一致。通信核心是“梯度/参数/优化器状态如何同步或临时补齐”。
  • TP：把同一层里的大矩阵乘法切到多张卡上。通信核心是“矩阵乘完后，下一步需要完整结果还是局部结果”。
  • PP：把不同层放到不同卡上。通信核心是“上一段的激活传给下一段，反向时梯度再传回来”。
  • SP / CP：把序列维度切开。SP 多用于层内激活省显存，CP 面向长上下文 attention，把 Q/K/V 或 KV 上下文分段放在不同卡上。通信核心是“每个 token 看别的 token 时缺哪些上下文”。
  • EP：把 MoE 的专家切开，每张卡只放一部分 expert。通信核心是“router 选出来的 token 要被送到对应专家所在的卡，专家算完再送回原来的 token 位置”。
  • 稀疏 Embedding 分层：把超大稀疏表按 owner rank 放在 host MEM，HBM 只放当前/下一窗口工作集。通信核心是“样本 rank 把 key 发给 owner，owner 回传向量；反向后样本 rank 把 embedding 梯度发回 owner 更新”。

一句话结论

回目录

分布式训练的通信上限由物理互联决定：机内走 PCIe / NVLink / HCCS，机间走 RoCE / InfiniBand，GPU 内部靠 DMA 和 HBM。所有集合通信原语最终都跑在这些链路上。

难点：不同链路带宽差几个数量级

回目录

机内 NVLink 的带宽远高于 PCIe，机间 RoCE/IB 又远低于机内直连。不同链路带宽差几个数量级，选错链路、或把小通信放到慢链路上，就会成为瓶颈。

怎么分类：先按“两个端点在哪里”分层

回目录

链路分类不要先背名字，先看一次数据搬运的起点和终点。端点不同，瓶颈资源不同，优化手段也不同：

分类口径端点在哪里典型链路/介质典型用途主要瓶颈
片内搬运同一张 GPU/NPU 内部寄存器 / SMEM / L2 / HBM / DMAkernel 内 tile 搬运、片上缓存复用片上容量、HBM 带宽、访存合并

这四类不是并列的“产品名”，而是一次数据流会经过的空间层级。例如稀疏查表可能同时涉及：owner 的 host MEM 读参数行 → H2D 到 owner HBM → owner 通过 RoCE/IB 把向量发回 sample rank → sample rank 在本卡 kernel 内使用向量。

为什么有效：通信优化先选对链路

回目录

通信时间 ≈ 字节数 / 有效带宽 + 延迟 × collective 次数。优化三条路——少传字节、用更快链路、减少小而碎的 collective——都建立在对“当前通信走哪条链路”的判断上。

存储层次：容量、带宽、延迟是三件事

回目录

GPU 内存储分层（从快到慢）：

  • 寄存器 / 共享内存（SM 私有）→ L2（分片 + 交叉互连，SM 间交换的唯一通道）→ HBM/显存 → 主机内存。
  • HBM 靠堆叠存储 die + 宽接口提带宽；GDDR 靠多颗存储芯片。
  • 统一内存两种别混：Apple UMA 是 CPU/GPU 共享同一块物理内存（无需复制）；CUDA Unified Memory 是统一虚拟地址、按需在 CPU/GPU 间迁移页（不是同一物理内存）。

三个量别混：容量是能放多少，带宽是单位时间传多少，延迟是一次请求多久返回。H100 SXM = 80 GB / 3.35 TB/s，H200 SXM = 141 GB / 4.8 TB/s——容量和带宽的增幅并不同步。

要跑满带宽，得靠并发在途请求（Little 定律）：在途事务数 ≥ R_target × L / s。接口带宽再高，在途请求不够就喂不满；在途请求太多又会排队加延迟。

互联的时间模型：固定开销 + 数据量

回目录

一次点对点传输 T = α + V/R（α=启动/完成通知固定开销，R=有效单向带宽，V=数据量）。所以：

  • 小消息被 α 主导：8 KiB 在 NVLink 上传输约 0.02 μs，但 α=2 μs，总耗时 2.02 μs；换更快链路几乎没收益。
  • 大消息被 V/R 主导：2 MiB 传输约 4.66 μs，换更快链路收益明显。
  • 转折点 V* = αR：H100 NVLink（450 GB/s、α=2 μs）约 879 KiB；小于它就该合并传输省 α，大于它才值得提带宽或减字节。

多卡集合通信的固定开销更狠：跨机 16 bytes 的 AllReduce 实测约 25 μs，100 次就是 2.5 ms——此时减少轮次比减少字节更有效。

矩阵乘法计算量 F = 2MKN，读写量 V = 2MK + 2KN + 2MN（权重 K×N、输入 M×K、输出 M×N）。

算术强度：算力 vs 带宽的比值，判断瓶颈

回目录

算术强度 I = F/V（每字节数据能做的 FLOPs）。同一个矩阵乘，batch 越大、权重被复用次数越多，I 越高：

  • M=1（单行）：I ≈ 1——权重搬进来只算一次，带宽受限。
  • M 增大到 256：FLOPs 涨 256 倍，权重访存几乎不涨，I 也涨约 256 倍——转向算力受限。

这就是 roofline 的核心：硬件有个“转折点” = 峰值算力 / 峰值带宽（如 H100 约 295 FLOPs/byte）：

  • I 低于转折点 → 带宽受限：优先减少 HBM 往返或提升数据复用，例如 FlashAttention 不落完整 attention 矩阵。
  • I 高于转折点 → 算力/调度受限：优先让矩阵单元持续有大块工作，例如 grouped GEMM、kernel fusion、减少 launch。
  • 三类优化别混：FA 主要降访存、提高有效算术强度；CompileMask 通过块跳过减少被 mask 区域的 QKᵀ 和访存；MoE 融合主要改善小 GEMM/launch/调度效率，不等于单纯把 I 抬高。

为什么有效：先判断瓶颈，再选优化方向

回目录

算术强度把“算多少”和“搬多少”放到同一把尺上。I 低说明矩阵单元在等数据，优化要先减少 HBM 往返或提高复用；I 高但吞吐仍低，说明问题更可能在矩阵单元利用率、kernel launch、调度或功率封顶。这样可以避免把所有加速都笼统说成“提高算力”。

能耗层次：数据搬移比计算更耗电

回目录

每字节能耗随距离增长（量级）：

  • 片上 SRAM ~1 pJ/byte、NVLink-C2C ~10 pJ/byte、HBM2 ~32 pJ/byte、LPDDR DRAM ~160 pJ/byte；一次 BF16 乘加（2 FLOPs）只 ~0.75 pJ/FLOP。
  • 数据搬移比计算更耗电：单请求 decode 的能量里，权重读取占约 90%，计算几乎可以忽略。
  • 所以数据复用首先是能耗问题，其次才是带宽问题——这也是 batch 越大越省电、以及“别反复搬数据”的根因。

功率封顶：峰值算力为什么不能持续

回目录

芯片有热设计功耗（TDP，H100 SXM 700 W、B200 1000 W），由内存和计算共用：

  • HBM 满带宽约吃掉 100 W，留给计算约 0.60 pJ/FLOP 的预算。
  • 实际每 FLOP 能耗超过预算，功率控制器就降频，峰值算力到不了。
  • 所以 MFU 的分母严格说该用“持续算力”，而不是纸面峰值——这也是“GPU 100% 不等于充分”的硬件根源。

怎么设计：九种原语各搬什么

回目录回项目
  • Broadcast：root rank 把同一份 tensor 发送给通信域内所有 rank。
  • Gather：多个 rank 把各自 tensor 收集到一个 root rank。
  • Scatter：root rank 把一份 tensor 切成多片，分别发送给不同 rank。
  • All-Gather：每个 rank 提供一片，最终每个 rank 都得到拼完整的数据。
  • Reduce：多个 rank 的 tensor 按 sum/max/min 等规则合成一个结果，结果只保留在 root rank。
  • All-Reduce：先 reduce，再把结果分发给所有 rank，使每个 rank 都得到同一个归约结果。
  • Reduce-Scatter：先 reduce，再把归约后的结果切片分给不同 rank。
  • All-to-All：每个 rank 把本地 tensor 切成 N 份，分别发送给所有 rank，同时接收自己对应的 N 份。
  • All-to-AllV：All-to-All 的变长版本，每个目标 rank 收到的数据量可以不同。MoE token dispatch 常会遇到这种不均匀。

通信量估算的通用口径

回目录回项目

通信时间不是只看“用了哪个原语”，而要看三件事：

  1. payload bytes：传输的数据字节数，例如 T * H * bytes 或参数大小 P。
  2. effective bandwidth：HCCS/NVLink/RDMA/RoCE 等链路的实际可用带宽。
  3. latency 与 collective 次数：小 bucket 或小 token 分桶会让启动延迟占比变大。

粗略公式：


communication_time ≈ bytes / effective_bandwidth + latency * collective_count

所以优化通信有三种方向：少传字节、用更快链路、减少小而碎的 collective，并尽量和计算重叠。

集合通信算法：环形、树形、分层与在网归约

回目录回项目

同一原语有多种实现算法，差别在轮数、每轮传输量、以及哪些链路被用上。设 n 张卡、每卡持有 M 字节、每轮固定开销 α、单向有效带宽 B：

  • 环形 AllReduce：先 ReduceScatter（n−1 轮，每轮传 M/n），再 AllGather（n−1 轮），共 2(n−1) 轮，每卡发送 2(n−1)M/n。

  T_ring = 2(n−1)·α + 2(n−1)·M/(n·B)

小消息被 2(n−1)·α 主导（α 取 2 μs：八卡 10 KiB 约 28 μs，其中 28 μs 是启动）；大消息被 M/B 主导。

  • 树形（二项树）：两两归约 + 广播，2log₂(n) 轮，但关键路径每轮都传完整张量：

  T_tree = 2log₂(n)·(α + M/B)

小消息轮数少、树更快；大消息环更快。令 T_ring = T_tree，八卡 α=2 μs、450 GB/s 时转折点约 1.65 MiB——小于它树更快，大于它环更快。

跨机时还要分层（hierarchical AllReduce）：先机内 ReduceScatter → 跨机 AllReduce → 机内 AllGather。

  • 好处：减少跨机字节，更关键的是让每张网卡都有分片要传。
  • 何时划算：跨机带宽由多张独立网卡提供时，分层几乎无代价（NVLink 450 GB/s 远高于网卡 50 GB/s）。
  • 何时不划算：跨机带宽是共享接口（如多卡共用一张网卡的 PCIe 槽）时，本地归约增加的时间可能盖过它省下的远端传输。

在网归约（in-network，NVIDIA SHARP）：让交换机在转发时顺带做加法，端点每份数据只发一次、收一次，不再两两传递。服务器越多越划算：两台时和环只差一次启动，32 台时在网归约时间约为环的 49%。瓶颈会从网卡转到交换机归约引擎的吞吐。

选算法的口径：先看数据量落在 α 主导还是 V/R 主导，再看跨机带宽是独立网卡还是共享接口，最后决定用环、树、分层还是在网归约。

动态 token 预算组批：让每个 batch 按 token 量而不是按样本数装

动态 token 预算组批（Dynamic Token Batching）把组批单位从“固定样本数”改成“固定 token 预算”：历史长的样本少装几条，历史短的样本多装几条，让每个 micro-batch 的真实计算量接近，减少多卡同步时“快 rank 等慢 rank”的时间。它同一条数据路径上还配套 Arrow 列式备数，用来降低 Python 逐行对象处理开销。

先看核心矛盾：样本数相同，不代表计算量相同

回目录回项目

推荐样本的历史长度差异很大。固定 batch_size=N 时，两个 batch 样本数一样，但 token 量可能差很多：

  • 长历史 batch：真实 token 多，attention/embedding/backbone 都更重，step 时间长。
  • 短历史 batch：真实 token 少，先算完的 rank 会在梯度同步或 MoE dispatch/combine 等同步点等待慢 rank。

所以这张卡的核心不是“batch size 怎么设”，而是：训练系统应该按真实计算量组批，而不是按样本条数组批。

  1. airecord（通用 IO 层）：负责读文件、按 max_tokens 预算切 batch、断点续训、EOS 退出。它只知道“这一行成本是多少、哪些行放进同一个 batch”，不认识 OneRec 的业务字段。
  2. OneRec（领域层）：ColumnarArrowCollator / KJTCollator 接收 airecord 给出的列式 batch，读取 seq_groups 等业务字段，组装成 KeyedJaggedTensor 和 [B,W] 标签。

依赖方向是单向的：OneRec import airecord，airecord 不认识 OneRec。这样通用 Reader 可以复用，业务语义只留在 OneRec collator 里。

组批算法：成本 → 前缀和 → 切点 → carry

回目录回项目

设 Reader 一次读 R 行（chunk），token 预算为 M。组批过程只有四步：

  1. 算成本：token_counter_fn 给每行一个 token 成本；项目里不会把所有列都等权计入，而是只统计真正决定算力的历史字段长度。
  2. 做前缀和：计算“前 k 行累计成本”，得到每个候选切点的 token 总量。
  3. 找切点：选择累计成本 ≤ M 的最长前缀，作为一个 batch。
  4. 保留 carry：本 chunk 没用完的行不丢，带到下一个 batch 或下一个 chunk 开头继续凑。

项目配置示例：max_tokens=286720，Reader chunk 1024。这里有两个容易混的边界：

  • file_reader_batch_size 是 Reader 一次读多少行，不是最终训练 batch 大小。
  • 动态路径下 batch_size=None，因为 batch 已经由数据集按 token 预算切好了。

正确性约束：动态 batch 必须同步改 loss / GAS 归一

回目录回项目

动态组批改变了每个 micro-batch 的有效监督 token 数 n_micro（labels != -100 的位置数）。如果仍然“每个 micro 内先求 mean，再对 micro 求平均”，一个 3 个有效 token 的 micro 和一个 9 个有效 token 的 micro 会被等权处理，训练目标就变了。

正确目标应该等价于一次更新窗口内的：


loss_update = 全局 Σloss / 全局有效监督 token 总数 N

实现口径：

  1. 模型 forward 返回 sum（reduction="sum"），不要在 micro 内除以 n_micro。
  2. 训练循环累计整个更新窗口的有效监督 token 总数 N。
  3. 关掉 DeepSpeed 默认的 /GAS（scale_wrt_gas=False），避免重复缩放。
  4. 窗口边界用 scale_gradients 把 W/N 补回来（W=数据并行卡数）。

一句话：组批可以动态，但每个有效监督 token 在 loss 里的权重必须不变。

为什么有效：减少等待，但不改变模型数学目标

回目录回项目

动态 token 预算组批的因果链是：


历史长度差异大

→ 固定样本数组批导致各 rank token 量不均

→ 慢 rank 决定同步点完成时间

→ 按 token 预算组批压平每个 micro 的真实计算量

→ 快 rank 等慢 rank 的时间减少

Arrow 列式备数的因果链是：


逐行 Python 对象构造多

→ CPU collate/解析时间高

→ GPU 等数据

→ Arrow 列式读取 + 零拷贝 collator

→ CPU 备数开销下降

这两条链路可以叠加，但不能互相替代：token 预算解决负载波动，Arrow 解决CPU 备数开销。

什么时候有效 / 什么时候收益不大

回目录回项目

  • 收益不大：样本长度本来均匀，或瓶颈在显存、通信带宽、MoE all-to-all，而不是 batch 内 token 波动。
  • 评估口径：默认看累计 per_rank_samples/s、MFU、step time 分布；不能只看单个 batch。

特征编码：ID 怎么变成全局唯一 key

回目录

一句话结论

回目录

同名不同字段必须查 embedding 表里不同的两行：brand="Nike" 和 shop="Nike" 字面相同，但一个是品牌行、一个是店铺行，只拿 "Nike" 算 key 就会撞车。所以 key 不能只由 ID 决定，要带上字段身份——先判类型（是否查表）、string 先分词，最后把 (slot, id) 编码成一个全局唯一 key。

怎么设计：ID → key 三步

回目录
  1. 判类型：FeatureInfo.type 是 CATEGORICAL 才走稀疏查表，NUMERICAL 直接进 dense。
  2. string 分词：TokenizeSparse 把 query 等 string 切成变长 token（jagged：indices+values+shape）；有词表出 token id，没词表出字符串交给下一步 hash。
  3. global_hash：key = Hash64Combine(Hash64(slot_name), Hash64(id))，用 slot 前缀做命名空间隔离。

为什么有效：slot 前缀隔离，同名不同字段不撞

回目录

brand 和 shop 的 Hash64("Nike") 相同，但 Hash64("brand") ≠ Hash64("shop")，Combine 后 key 不同，查不同行。三个要点：

  • “global hash” = 全局只有一张 key 空间：slot 不是物理分表，而是编码进 key 的逻辑命名空间。
  • Hash64Combine 用黄金比例常数 + 双向位移做雪崩扩散：避免 a^b 的交换律碰撞。
  • 同时避免“同 slot 海量 id 淹没 slot 区分”的问题。

  • 用了什么能力：判类型 → string 分词 → global_hash，用 slot 前缀把 (slot, id) 编码成全局唯一 key。
  • 解决什么问题：长序列多字段同名不同义（brand="Nike" vs shop="Nike"），key 撞了就查错行。
  • 达到什么效果：保证多字段、多表查表正确，是后续 InputDist 分桶、查表、更新正确性的前提。具体走 NoneHash 还是 Murmur 分支待核验。

稀疏 Embedding 五级流水：一次查表→更新，四类对象如何流转

回目录回项目
03_concepts/sparse_embedding_pipeline.md

一句话结论

回目录回项目

稀疏表太大，HBM 放不下；所以全量参数按 key 分片放在各卡的 host MEM，HBM 只放当前/下一窗口的工作集。训练时，sample rank 负责“用向量算模型”，owner rank 负责“存参数并更新”；五级流水 + 双 Buffer 让“查表”和“算模型”错开执行。切换窗口前，再把上一窗口更新过且下一窗口也会命中的交集行同步到最新版。

主角：四样东西，两个角色

回目录回项目

整条链路只围绕四样东西、两个角色转。先明确两个角色，避免把 owner 和 CPU/GPU 混为一谈：

  • rank（卡）：训练里的一个设备进程（GPU/NPU），每张卡既有主机内存（host MEM），也有设备内存（HBM）。
  • owner（属主 rank）：负责保管某个参数 shard 的那张卡——全量参数行长期存在它的 host MEM，训练时只把当前窗口命中的工作集搬到它的 HBM。
  • sample rank（样本所在卡）：样本被分到的那张卡，负责用查出的向量算稠密前反向。
东西是什么谁持有/谁负责
key稀疏特征 ID（商品/用户/行为），只是个整数索引样本产生，owner 按 key 分片保管
参数行key 对应的 embedding 参数（可带 optimizer state）owner 的 host MEM 长期存该分片的参数行
向量查表得到的 embedding，参与稠密前向owner 查出后交给 sample rank
梯度反向得到的“向量该怎么改”sample rank 算出来，交回 owner 聚合

两个角色一句话分工：sample rank 用向量算模型，owner rank 存参数并更新。 样本落在 A 卡，不代表它的 key 就归 A 管——key 可能归 B 卡管，这是后面所有通信的来源。

怎么设计：一个窗口的 5 次搬运（单窗口内的串行闭环）

回目录回项目

先别管“五级”，只看一个窗口：一份样本从 key 到参数更新，四样东西各动一次，串成 5 步。拿“样本在 A 卡、商品 key 归 B 卡管”走一遍：

  1. Input Dist（A→B）：A 对 key 去重、按“key 归属的 owner”分桶，把 key 发给 owner B——“这些 key 我要用”。
  2. 参数行 Load（B 的 host MEM→B 的 HBM）：B 从自己 host MEM 里的分片，把命中的参数行搬进 HBM 工作集。
  3. 查表 + 向量回传（B→A）：B 在 HBM 查表，把向量发回 A。
  4. 稠密前反向（A 本地）：A 拼特征过 backbone 算 loss，反向得到这些向量的梯度。
  5. Grad A2A + 更新（A→B）：A 把梯度发回 B，B 聚合同 key 的多份梯度后更新参数行。

记住两点：这 5 步有先后、不能乱；Grad A2A 传的是“当前 batch 命中的那些向量的梯度”，不是 loss 也不是整表梯度。

怎么设计：五级流水让相邻窗口的 5 步错位重叠

回目录回项目

这里最容易混，先明确边界：“五级流水”和上面的“5 次搬运”是两回事。 上面是一个窗口内部的 5 步串行；五级流水是把多个窗口排成队，让每个窗口处在不同阶段，错位重叠。

五级的端到端口径是 5 站：


① Data Prefetch（提前读样本）→ ② Data H2D（样本搬上设备）→ ③ Input Dist（key 分桶交换）→ ④ Emb Lookup（查表回向量）→ ⑤ Fwd/Bwd/Opt（稠密前反向 + 更新）

上面第 3 节的 5 次搬运，主要落在 ③④⑤ 这三站里。真正的并行是：同一时刻，多个窗口各在干一件事——


G0 在 ⑤ 算模型/更新，G1 在 ④ 查表/预取，G2 在 ③ 分桶交换，G3 在 ② 搬样本……

所以“为什么快”不是“一个窗口五件事同时做”，而是“搬表、查表与当前窗口计算重叠，减少设备等待 host 侧查表和网络交换”。代价也在这：HBM 要放两份工作集，且提前加载会带来正确性问题。

双 Buffer 是错位的落地

回目录回项目

每张表有两块 HBM buffer（物理编号 A/B），current/next 是角色不是固定名字：


训练 G0：A=current 在算，后台对 B 先 Dump 旧窗 G−1、再 Load 新窗 G1（同一次复用任务，相差两个窗口）

G0 结束：等预取 + 等 G0 更新完成 → 同步交集行 → 切换 current/next

训练 G1：B=current 在算，后台对 A 先 Dump G0、再 Load G2

补充一句防误解：源码 STAGES 只写了 h2d/input_dist/prefetch 三个准备阶段，Reader 在上游、当前窗口的查表与前反向在它之外——“端到端五级”和“三个 Python stage”是不同范围，别当成五级=三个。

唯一的难点：提前预取会读到旧参数 → 强一致

回目录回项目

双 Buffer 的副作用是：G1 的 next 可能提前装好了 key=100，但 G0 反向后把 key=100 从 10 更新成了 9。如果 G1 直接用 next 里的旧值，就读错了。

修法是在窗口边界做交集同步：


G1 预取 future.get() 完成 ───────┐

                                 ├→ 把 G0∩G1 交集 key 的最新整行 A→B → 切表 → G1 前向

G0 反向和更新完成 ────────────────┘

语义保证：下一窗口读到的参数，不早于上一窗口更新完成后的版本。

  • 连续命中的 key 靠交集同步保持新鲜。
  • 隔窗再次出现的 key 靠旧 buffer 退役回写 host MEM、再从 host MEM 表加载。
  • 诚实边界：源码交集函数还留着“current 独有 key 回写”的 TODO，完整强一致要结合 buffer 退役、checkpoint/eval flush 和运行验证，不能只凭交集函数下结论。

怎么选、代价、口径（收尾）

回目录回项目
  • 怎么选 EmbType：LOCAL_PS_EMB_DOUBLE（现搬，慢）→ LOCAL_PS_EMB_PREFETCH（预取+双 Buffer，大表主路径）→ LOCAL_PS_EMB_HBM（整表常驻，小表最快）→ DP_EMB（每卡完整小表）。主线就是“现搬能跑但慢 → 预取双 Buffer 藏等待 → 全 HBM 最快但容量受限”。⚠️ 一个配置陷阱：OneRec 配置文件里写的是 LOCAL_PS_EMB_DOUBLE，但 PipelineUniRecEmbedding 构造时会被强制覆盖成 LOCAL_PS_EMB_PREFETCH，所以判断实际路径要追到模块构造处，不能只看配置初值。
  • 本质代价：用通信（key/向量/梯度 A2A）、H2D 搬运和调度复杂度，换 HBM 容量。
  • 10TB/千卡是系统级口径：10TB 是分布式容量目标，不是单机内存或单卡 HBM；千卡线性比 NPU 512 die 约 0.89，扩到 1024 die 塌到 0.64，Nest 嵌套双流后 1024 die 回到 0.926（+34.3%）。归因是 Nest 让 emb 通信与 dense 计算重叠（盖住约 71% 通信），不是减少通信量，更不是外层五级流水单独做到。

项目一的稀疏线核心就是这条流水：

  • 用了什么能力：owner 按 key 分片 + host MEM–HBM 两级存储 + 五级流水 + 双 Buffer + 交集同步。
  • 解决什么问题：TB 级稀疏表放不下单卡 HBM，查表还会让设备等待 host 侧查表和网络交换。

SparseGroup：共享稀疏索引，减少超长行为通信

回目录回项目
03_concepts/sparse_group.md

同一个用户行为的 SKU、品类、品牌按位置严格对齐，却各存一套坐标——重复传了好几遍。SparseGroup 让组内共享一份坐标（indices + dense_shape），每列只留自己的 values，省掉重复的元数据传输。

注意边界：这是 Tritium/TF 输入侧的实现（tf.SparseTensor 接口），不是 OneRec 当前 PyTorch 的 JaggedTensor 输入，不能把两者接口混为一谈。

解决什么问题

回目录回项目

长序列推荐里，行为序列从百级扩到十万级后，稀疏 Embedding 查询和跨设备传输会携带大量坐标信息：

  • 坐标 = 每个有效行为的“样本号 + 行内位置”，即 indices [T,2]，再加逻辑形状 dense_shape。
  • 很多数据不是 dense tensor，而是“哪些位置有值”的稀疏结构。
  • 如果每个字段都重复传自己那份坐标，通信就会被元数据和重复结构放大。

拆的是什么

回目录回项目

SparseGroup 拆的不是模型层，而是把稀疏数据表示拆成两部分：

  • 共享一份索引结构：indices [T,2]（每个有效行为的“样本号、行内位置”）+ dense_shape [2]（逻辑矩阵范围）。
  • 每列各一份值：values [T]（该字段自己的 ID），g 列共 g 份。

如果多路特征共用同一批行为位置（组内各列有效位置与顺序严格一致），就只生成一次坐标，让多路值复用它。仅总长度相等不足以共享，必须位置对齐。

通信对象与方式

回目录回项目
  • 传的是什么：一份共享 indices [T,2] + 一份 dense_shape [2] + g 份 values [T]。
  • 不重复传什么：组内每列各自重复的 indices 坐标。
  • 怎么发生：Table/Parquet IO → Dataset parser 对变长列 Ragged/DataFrame.Value → SparseTensor → 若配置 SparseGroup，只对参考列生成一次坐标、收集各列 values → 跨 Dataset 边界传 SparseGroupDict(indices, value_list, dense_shape) → model_input 处恢复逐字段 tf.SparseTensor。

恢复入口不是对 ID 解码，也不是重新逐列 RaggedToSparse，而是构造 tf.SparseTensor 时直接传入同一个 group_indices 张量，各字段引用同一份坐标。

通信量为什么能降低

回目录回项目

设 B=batch 样本数、T=某列有效值数、g=同组字段数，值和坐标均为 int64，每个行为坐标有两个整数：

组织方式值坐标合计
每列独立 SparseTensor8gT16gT24gT
SparseGroup8gT16T(8g+16)T

节约比例：


(24gT - (8g+16)T) / 24gT = (2/3)(1 - 1/g)

g=6 时 144T → 64T，节约 55.56%（约 56%）。这就是 56% 的原始口径：它是值和坐标的理论字节量，不含容器、形状和运行时开销；使用手册“58%以上”与公式不符，六列按公式约 56%。

边界要讲清：56% 是六列值+坐标理论载荷以及对应 H2D/RPC 场景的下降，不是单独坐标字节下降 56%，也不是整模吞吐提升 56%，更不能推出模型参数显存、Embedding 表容量或整卡显存也降 56%。

收益分别来自哪里

回目录回项目
  1. 解析 CPU：原先多列分别 RaggedToSparse，组内只转参考列，减少重复转换（周报记录转换次数 48→6，同资源下 SW CPU 利用率降约 15%—20%，是特定实验）。
  2. 缓冲与通信：少一批重复 indices，降低流水线缓冲、H2D 和相关 RPC 载荷。
  3. 接口兼容：模型入口恢复逐字段 SparseTensor，下游稀疏 Embedding/行为层无需同步改 RaggedTensor。

不要混淆：SparseGroup 省输入元数据/解析，合表省 Embedding 访问组织，PS 流水省通信等待，Jagged 计算省 Padding 算力——四个不是同一机制。

为什么可能提升吞吐

回目录回项目
  • 网络传输字节减少。
  • 稀疏索引处理和反序列化次数减少。
  • 后续 Embedding 查询和聚合可以更容易批量化。

什么时候收益不大

回目录回项目
  • 各路特征索引重合度低，无法共享。

准入与淘汰：稀疏表怎么控制容量

回目录

一句话结论

回目录

稀疏表不是无限大：access（准入）决定一个新 key 够不够格建行，shrink（淘汰）决定一个老 key 该不该被踢出去。两者卡在 key 生命周期的两端。

难点：长尾 ID 占绝大多数却几乎学不到东西

回目录

每个出现一次的 ID 都建一行，表会无限膨胀，而长尾 ID 大多是噪声、不值得学一行参数。

怎么设计：先挡新 key，再清老 key

回目录

一条 key 的生命周期分两道闸：

  1. 入表前先准入（access / Filter）：样本里来了一个新 key，先不直接创建参数行，而是用 filter 判断它是否值得建行。
  • None：全准入，最简单但表增长最快。
  • Count：出现次数达到阈值才准入，挡一次性长尾。
  • Probability：按概率准入，高频 key 累计更容易进表。
  • ShowClick：用 α·展现 + β·点击 形成分数，分数过阈值才准入。
  1. 入表后再淘汰（shrink / ShrinkPolicy）：已经有参数行的 key，如果太久不用、频次低或参数范数学不到东西，就在 shrink 阶段删除。
  • GlobalStep：距离上次更新太久则淘汰。
  • L2Weight：参数范数太小说明贡献弱，可淘汰。
  • TimeFreqCombine：同时考虑时间和频次，清理又久又低频的 key。

关键实现点：Value.version 这个 32-bit 字段被多种策略复用——GlobalStep/Count 当“步数/次数”用，ShowClick 用 reinterpret_cast<float*> 位重解释当“分数”用。同一块内存不同读法，绝不能混用。

为什么有效

回目录

准入发生在入表前，目标是“不为明显低价值 key 建参数行”；淘汰发生在入表后，目标是“把已经占空间但长期无贡献的 key 清掉”。两端一收，长尾噪声挡在表外、冷 key 及时腾空间，表容量和 host MEM 可控。

DP：复制模型，拆 batch，同步梯度

回目录回项目
03_concepts/dp_data_parallel.md

Data Parallelism（DP，数据并行）是最基础的多卡训练：每张 GPU 放一份完整模型 W，拿不同数据算前向/反向，最后把所有 GPU 对同一参数算出来的梯度求平均，让每张卡更新出同一份新参数 W'。

解决什么问题

回目录回项目

单张 GPU 的吞吐有限，DP 通过让多张卡同时处理不同样本来提高总 batch 吞吐。它不减少单卡模型显存，因为每张卡仍放完整模型；它解决的是“同一个模型如何并行吃更多数据”，代价是每步要同步梯度。

拆的是什么

回目录回项目

DP 拆的是 batch/样本，不是模型。假设全局 batch 是 1024，8 张卡，每张卡处理 128 个样本。每张卡都有完整参数 W，区别只是看到的数据不同。

梯度从哪来，怎么加和

回目录回项目

单卡训练时，一个 batch 经过模型得到 loss，反向传播会算出每个参数对 loss 的梯度。DP 下每张卡的 batch 不同，所以梯度也不同：


GPU0: loss_0 -> gradient G_0

GPU1: loss_1 -> gradient G_1

...

GPU7: loss_7 -> gradient G_7

如果直接各自更新，8 张卡的 W 会变成 8 份不同模型。为了让它们等价于“一个大 batch 训练”，必须对同一个参数位置的梯度求平均：


G_avg = (G_0 + G_1 + ... + G_7) / 8

W' = optimizer_update(W, G_avg)

reduce 和 gather 分别是什么

回目录回项目
  • reduce：把多张卡上的同一类数据合并成一个结果。DP 里合并的是梯度，操作是求和/平均。
  • gather / broadcast：把合并后的结果让需要它的卡都拿到。
  • all-reduce：把这两步合在一个 collective 里：每张卡都参与求和，每张卡最后都得到同一个求和结果。

所以 DP 说“reduce + gather”是概念分解；工程上通常直接用 all-reduce 完成。

通信对象与通信量

回目录回项目
  • 传的是什么：梯度张量 G，不是样本，不是参数 W。
  • 什么时候传：反向传播产生梯度后，优化器 step 前。
  • 为什么传：为了让不同数据上算出的梯度合成全局 batch 的平均梯度。
  • 通信量：若梯度总大小为 P_grad 字节，N 张卡 ring all-reduce 单卡通信量约 2 * (N-1)/N * P_grad。

和 ZeRO 的关系

回目录回项目

ZeRO 是对 DP 的训练状态做拆分。DP 保留完整 W/G/O；ZeRO-1 拆 O；ZeRO-2 拆 O/G；ZeRO-3 拆 O/G/W。它们都保留“不同卡看不同数据、需要全局一致更新”的 DP 语义。

和我的项目怎么关联

回目录回项目

项目里 DP 是两处落地：

  • 用了什么能力：复制模型、拆 batch、all-reduce 同步梯度。
  • 解决什么问题：项目二-2 ModelZoo 的多后端里，稠密网络梯度要跨卡平均——PS 管稀疏、Horovod/all-reduce 管稠密；项目一里 DP 也是 ZeRO/FSDP 的语义底座。
  • 达到什么效果：支撑稀疏/稠密混合训练；显存放不下完整模型时再升级到 ZeRO、TP、PP 或 EP。

ZeRO / FSDP：把“模型状态”拆开，用通信换显存

回目录回项目
03_concepts/zero_parallelism.md

ZeRO（DeepSpeed）的核心不是把网络层切开，而是把训练时最占显存的三类状态拆到多张卡上：优化器状态 O、梯度 G、参数 W。FSDP（PyTorch）是同一思想的另一套实现。DP 是每张卡都放完整模型；ZeRO/FSDP 是尽量只在“需要用到的瞬间”把缺的部分通信回来，用更多通信换更低显存。

解决什么问题

回目录回项目

普通 DP 下，N 张卡各自拿不同 mini-batch，前向/反向都在完整模型上做。每张卡显存里都有完整参数 W、完整梯度 G、完整优化器状态 O。模型一大，单卡显存就被重复副本浪费：N 张卡总显存很大，但每张卡仍必须装下完整训练状态。

ZeRO 的直觉是：既然每张卡算的是不同数据，但最终更新的是同一个模型，那训练状态没必要每张卡都完整存一份。

拆的是什么

回目录回项目
  • ZeRO-1：只拆优化器状态 O，例如 Adam 的 momentum、variance、master weight。
  • ZeRO-2：拆 O 和梯度 G。
  • ZeRO-3 / FSDP(FULL_SHARD)：拆 O、G 和参数 W。每张卡长期只保存自己负责的参数分片，算某一层时临时 all-gather 出这一层需要的完整参数。ZeRO-3 是 DeepSpeed 的命名，FSDP FULL_SHARD 是 PyTorch 的命名，这一级两者做的是同一件事。

如果模型参数量记为 P，数据并行度为 N，混合精度 Adam 常见状态粗略可理解为：参数约 2P、梯度约 2P、优化器状态可达 8P 或更高。ZeRO 逐步把这些从“每卡 P 级完整副本”变为“每卡 1/N 分片”。

通信对象与通信方式

回目录回项目

DP 基线：reduce + gather 为什么都存在

回目录回项目

普通 DP 每张卡都有完整 W，各自算出本卡 batch 的梯度 G_i。为了让所有卡更新成同一个新参数 W'，需要把所有 G_i 求平均：

  1. reduce：把多张卡对同一参数的梯度相加，例如 g = g_0 + g_1 + ... + g_{N-1}。
  2. gather / broadcast：让每张卡都拿到同一个结果，才能都更新出同一份 W'。

工程上常用 all-reduce，它可以理解成“reduce + 把结果分发给所有卡”。所以用户看到 DP 也常被说成 reduce + gather：本质是先把梯度合并，再让每张卡都拥有合并后的梯度。

ZeRO-1

回目录回项目
  • 前向/反向：每张卡仍有完整参数 W，反向像 DP 一样算出完整梯度 G。
  • 通信：梯度用 reduce-scatter（不是 all-reduce）——求和后各卡只留自己那份梯度分片；因为优化器状态已切片，每卡只需自己参数的梯度。
  • 更新：每卡用自己那份 O 分片 + 梯度分片，更新自己负责的参数分片；随后 all-gather 更新后的参数，让所有卡下一轮仍有完整 W。
  • 传的是什么：梯度分片（reduce-scatter）+ 更新后的参数分片（all-gather）。

ZeRO-2

回目录回项目
  • 前向/反向：每张卡仍有完整参数 W，但不长期保留完整梯度 G。
  • 通信：反向产生梯度时，不再 all-reduce 出完整 G 给每张卡，而是 reduce-scatter。它一边把所有卡的梯度相加，一边只把第 k 份结果留给第 k 张卡。
  • 更新：每张卡用自己保存的 O 分片和收到的 G 分片，更新对应 W 分片；随后 all-gather 参数分片，让所有卡得到完整 W。
  • 传的是什么：梯度分片在 reduce-scatter 中被求和并分发；参数分片在更新后被 all-gather。

ZeRO-3 / FSDP

回目录回项目
  • 长期状态：每张卡只长期保存 W/O/G 的 1/N 分片。
  • 前向前：某层要算 y = xW 时，每张卡只有 W 的一片，不够算完整层，所以对该层 W 做 all-gather，临时拼出完整 W_layer。
  • 前向后：这一层算完，完整 W_layer 可释放，只保留本卡分片。
  • 反向时：再次需要 W_layer 或其局部信息，会按 bucket 预取/聚合；梯度产生后用 reduce-scatter，把全局梯度求和后的分片留在对应卡。
  • 优化器 step：每卡只更新自己负责的参数分片。
  • 传的是什么：前向/反向前传参数分片，反向后传梯度分片；不是传样本，也不是传整个网络结构。

通信量怎么粗算

回目录回项目

设完整参数大小为 P 字节，数据并行度为 N。忽略 bucket 边界、重叠和协议常数，单步大致可理解为：

  • DP all-reduce 梯度：每张卡通信约 2 * (N-1)/N * P_grad。若梯度大小约 P，则约 2P 量级。
  • ZeRO-1：梯度 reduce-scatter 约 (N-1)/N·P + 参数 all-gather 约 (N-1)/N·P，合计约 2P 量级（≈2Φ）。它主要省 O 的重复副本，梯度通信和 DP 基本同量级。
  • ZeRO-2：梯度 all-reduce 变成 reduce-scatter，单卡通信约 (N-1)/N * P_grad，再加参数 all-gather 约 (N-1)/N * P。总量与 DP 同量级，但每卡不保留完整 G，显存省很多。
  • ZeRO-3：每层参数都要在使用前 all-gather，反向梯度 reduce-scatter。单步通信通常比 ZeRO-2 更频繁，因为参数不再常驻完整副本；优势是显存最低。

准确通信时间还要乘以通信拓扑和带宽：time ≈ bytes / effective_bandwidth + latency × collective_count。

  • ZeRO-3 的 bucket、prefetch、overlap 决定“看起来慢不慢”。
  • 同样字节数，能和计算重叠，暴露在 step time 里的通信就少很多。

通信时机与 bucket

回目录回项目

ZeRO/FSDP 实现不会等整张图都结束才通信，常见做法是按参数 bucket 或 FSDP unit 粒度流水：

  • 前向即将进入某个 block 前，预取该 block 参数分片并 all-gather。
  • block 前向算完后释放完整参数，只留 shard。
  • 反向产生某些梯度后立刻 reduce-scatter，避免完整梯度长期占显存。
  • 下一个 bucket 的通信尽量和当前 bucket 的计算重叠。

因此判断 ZeRO 好不好，不能只看总通信量，还要看 bucket 大小、layer 粒度、计算/通信能否掩盖、网络带宽和模型每层计算强度。

FSDP 是什么，和 ZeRO、FSDP2 什么关系

回目录回项目

前面一直在讲 ZeRO，这里先明确三个名字，避免“讲完 ZeRO 突然接 FSDP2”的跳跃：

  • ZeRO：DeepSpeed 的分片思想，按“拆 O → 拆 O+G → 拆 O+G+W”分三级（stage 1/2/3）。
  • FSDP：PyTorch 对同一思想的实现。FULL_SHARD ≈ ZeRO-3（O/G/W 全分片），SHARD_GRAD_OP ≈ ZeRO-2（分 O/G）。所以“FSDP”和“ZeRO-3”不是两套技术，是同一件事的两套命名。
  • FSDP2：PyTorch 的第二代实现。它把 FSDP1“整块模块拍平成一个大 flat buffer、再整体 all-gather”改成按参数（DTensor）粒度分片，能精确控制“哪一刻 all-gather、哪一刻 reshard”，也更好和 torch.compile 配合。

一句话：ZeRO 是思想，FSDP1/FSDP2 是 PyTorch 的两代实现；FSDP2 相对 FSDP1 的进步，是把分片粒度从“模块”细到“参数”。

FSDP2 的参数生命周期：一次 AllGather 只服务一个模块的前向

回目录回项目

FSDP2 不是“先把整个模型永久装回每张卡”，而是逐模块/逐层做：AllGather → 前向 → reshard →（反向需要时再 AllGather）→ ReduceScatter → 本地 optimizer 更新。

  • 关键逻辑：参数只在被用到的那个瞬间才是完整的，用完立刻释放。
  • 所以显存峰值 = 持久分片 + 当前这一层（或预取的下一层）的完整参数，而不是整个模型的完整副本。

一个 FSDP 参数单元的概念时序：


前向前 AllGather 拼出本层完整参数 → 前向读取权重

  → reshard_after_forward=True 时释放完整表示，只留分片

  → 反向需要权重时按策略重新 AllGather

  → 梯度 ReduceScatter：全局梯度求和后的分片留在对应 rank

  → optimizer 更新本 rank 负责的参数分片

reshard_after_forward=False 表示前向已汇集的完整权重多留一会儿，尝试省掉反向再汇集的时间，代价是完整参数占用更久。它不等于 ZeRO-2。

四类状态与 18P 口径

回目录回项目

把一次更新涉及的显存分四类：参数、梯度、优化器状态（Adam m/v + 可能 FP32 master）、激活与临时缓冲。ZeRO/FSDP 主要分片前三类稠密状态；AC 影响激活；UniRec 管理稀疏表及其优化器——它们可能同时竞争 HBM，但不是同一个内存池的同一种优化。

理想化存储公式（BF16 参数 2B/元素、FP32 梯度 4B、FP32 master 4B、Adam m/v 各 4B，完整副本 18P；N=数据并行度）：

状态每 rank 字节（忽略 padding/bucket/激活）
全副本18P
ZeRO-16P + 12P/N
ZeRO-22P + 16P/N
ZeRO-318P/N

这只是理想化比较，step 峰值还可能同时包含当前完整层、预取下一层、通信 bucket、激活与 PS 缓存，不能据此承诺“2.25GB 就能训”。

一个容易漏的点：常驻状态下降幅度 ≠ 执行峰值下降幅度。

  • 分片后长期保存的是 1/N 分片，但执行某一层时，临时 all-gather 出的完整权重与原有分片同时存在。
  • FSDP2 的 CPU 小模型实验：进程数 2→4 时，保留状态从 18 MiB 减到 9 MiB（减半），执行峰值却只从 39 MiB 减到 30 MiB（减约 23%）——因为执行中还要 21 MiB 其他张量和缓冲。
  • 结论：分析容量不能只看常驻分片，要看模块执行时参数与激活各保存多久。

AC、FSDP2、MoE 怎么一起影响一次训练

关键结论：AC 不能替代 All-Gather，FSDP 也不能替代激活重算。重算需要权重，但“开 AC 必多一次 All-Gather”也不成立——框架可能复用反向已汇集的参数。峰值显存要按时间取 max：


M_peak = max_t [持久状态 + 完整参数及预取 + 激活 + 梯度与通信临时区 + PS 工作集 + 其他]

常见误区

回目录回项目
  • 误区：ZeRO 是模型并行。 更准确说它是模型状态分片；ZeRO-3 运行时会临时 all-gather 参数，但层计算本身通常仍由每张卡用不同数据副本执行。
  • 误区：ZeRO-3 一定更快。 它显存最省，但参数 all-gather 更频繁，计算量不够大或网络慢时可能更慢。

TP：把同一层的大矩阵乘法拆给多张 GPU

回目录回项目
03_concepts/tp_tensor_parallel.md

Tensor Parallelism（TP，张量并行）拆的是同一层里的矩阵乘法，不是把 batch 拆开，也不是把前后层拆开。它让多张 GPU 一起算同一个 layer 的不同矩阵块，单卡显存和单卡计算下降，但需要在层间同步中间结果。

解决什么问题

回目录回项目

当 hidden size、intermediate size 或 attention projection 很大时，单张 GPU 既要放完整权重，又要独自完成大 GEMM，容易显存不够或算得太慢。TP 把同一层的大矩阵横向切给多张 GPU：每张卡只保存/计算一部分矩阵块，用一次或少量 collective 把局部结果合成下一层需要的 hidden。

W1 / W2 是什么，为什么会有两个矩阵

回目录回项目

Transformer block 里通常有 Attention 和 FFN/MLP。以最常见 FFN 为例，它不是一个矩阵，而是两次线性变换：


输入 hidden X [B,S,H]

  └─ W1: H -> 4H 或 intermediate_size，先升维

       得到 U = X @ W1

       经过激活函数 GeLU/SwiGLU

  └─ W2: 4H -> H，降回 hidden size

       得到 Y = act(U) @ W2

所以 W1/W2 不是“网络外面生成出来的两个东西”，而是 FFN 层天然就有的两组权重。Attention 里的 Q/K/V/O projection 也类似有多个矩阵，TP 的思想一致：把大矩阵按列或按行切开。

拆的是什么

回目录回项目

假设 TP=2，W1 形状是 [H, 4H]，W2 形状是 [4H, H]。

W1 列切：每张卡算一部分输出通道

回目录回项目

W1 = [ W1_a | W1_b ]       # 按列切，输出维度被切开



GPU0: U_a = X @ W1_a       # 得到前一半中间通道

GPU1: U_b = X @ W1_b       # 得到后一半中间通道



U = [U_a | U_b]            # 逻辑上拼起来就是完整 U

列切的好处是每张卡拿同一个输入 X，只算不同的输出列，不需要马上 all-reduce。中间激活 U 天然被分片，每卡保留自己的那一半即可。

W2 行切：每张卡吃自己那部分中间通道，输出需要求和

回目录回项目

W2 = [ W2_a

       W2_b ]              # 按行切，输入维度被切开



GPU0: Y_a = act(U_a) @ W2_a

GPU1: Y_b = act(U_b) @ W2_b



完整 Y = Y_a + Y_b         # 因为矩阵乘法按输入维度切时，结果要相加

这就是为什么常说 “W1 列切、W2 行切”：这样 W1 产生的分片 U 正好被 W2 的对应行分片消费，中间不用把 U 拼成完整张量，只在 W2 后做一次 all-reduce 求和得到完整 Y。

它怎么并行，明明 W1 和 W2 有先后关系

回目录回项目

W1 和 W2 确实有先后关系，TP 并不是让 W1 和 W2 同时算。TP 的并行发生在每一层矩阵乘内部：


时间 t1：GPU0/GPU1 同时算 W1 的不同列块

时间 t2：GPU0/GPU1 同时算 W2 的不同行块

时间 t3：GPU0/GPU1 对 W2 的局部输出做 all-reduce

所以加速来自“同一个大 GEMM 被拆成多个小 GEMM 并行跑”，不是来自破坏层间依赖。依赖还在，但每个依赖节点内部变宽了。

通信对象与方式

回目录回项目
  • 前向 W1 后：通常不通信，因为列切输出 U_a/U_b 可继续分片保留。
  • 前向 W2 后：需要 all-reduce，传的是每张卡算出的局部输出 Y_a/Y_b，通信后每张卡得到完整 Y，供残差连接、LayerNorm 或下一层使用。
  • 反向 W2：梯度会沿着相反路径传播；对行切/列切权重和输入梯度的通信位置与前向对应，常见会在某些输入梯度上 all-reduce 或 reduce-scatter。
  • Attention TP：QKV projection 可列切，O projection 可行切，逻辑与 FFN 的 W1/W2 类似。

核心边界：TP 通常不是以传权重为主，而是传每个 GPU 对同一个 token hidden 算出的局部结果或局部梯度，让下一步拿到完整或重新分片的 hidden。

通信量怎么粗算

回目录回项目

设 micro-batch token 数为 T = batch_size * seq_len，hidden size 为 H，TP 度为 N，每个元素 bytes 为 b。

  • W2 前向 all-reduce 的张量形状通常是 [T, H]，大小约 T * H * b。
  • ring all-reduce 单卡通信量约 2 * (N-1)/N * T * H * b。
  • 反向还会有对应的梯度通信，粗略可再乘一个相近量级。

这说明 TP 通信量跟参数量 P 不直接一一对应，而跟每层输出激活大小 T×H和层数强相关。序列长、batch 大、hidden 大时，TP all-reduce 带宽压力明显。

为什么可能变快

回目录回项目
  • 单卡矩阵更小，单卡 FLOPs 约降为 1/N，能训练更大 hidden/intermediate。
  • 大矩阵 GEMM 拆分后仍能保持较高 GPU 利用率，尤其是单层计算强度足够大时。
  • W1 列切 + W2 行切把中间分片串起来，减少不必要的中间 all-gather。

什么时候会变慢

回目录回项目
  • batch/seq 太小，单卡 GEMM 太碎，通信延迟占比高。
  • TP 跨机而不是机内 NVLink/NVSwitch，all-reduce 带宽不足。
  • 层间需要频繁完整 hidden，导致 all-reduce 暴露，无法被计算掩盖。

和我的项目怎么关联

回目录回项目

项目一稠密层/Attention/MoE expert 内部 MLP 可能用 TP：

  • 用了什么能力：W1 列切 + W2 行切，把同一层大矩阵横向拆给多卡。
  • 解决什么问题：单层大 GEMM 的显存/计算放不下。
  • 达到什么效果：支撑 B 级稠密 backbone 和 30B 级 MoE expert 内部 MLP 的单层计算；代价是随 token 数增长的激活通信，所以动态组批和负载均衡会直接影响 TP 暴露通信时间。

PP：把网络层分段，像流水线一样传激活

回目录回项目
03_concepts/pp_pipeline_parallel.md

Pipeline Parallelism（PP，流水线并行）拆的是模型层。例如 48 层 Transformer 分给 4 张 GPU，每张卡负责连续 12 层。前向时上一段把激活传给下一段，反向时下一段把激活梯度传回上一段。

解决什么问题

回目录回项目

当模型层数太多或单卡放不下完整层参数/激活时，PP 把不同层放到不同 GPU 上，让每张卡只承担一段网络。它主要省单卡模型层显存，代价是 stage 之间传激活，并可能出现流水线气泡。

拆的是什么

回目录回项目

PP 拆 layer，不拆一个矩阵，也不拆 expert。它解决的问题是：完整模型层数太多，一张卡放不下所有层的参数/激活，就把不同层放到不同 GPU。


GPU0: Layer 0-11

GPU1: Layer 12-23

GPU2: Layer 24-35

GPU3: Layer 36-47

通信对象与时机

回目录回项目
  • 前向传激活：GPU0 算完第 11 层，把 hidden activation 发给 GPU1。
  • 反向传梯度：GPU1 反向算出对输入 activation 的梯度，再发回 GPU0。
  • 传的是什么：层边界处的 activation 和 activation gradient，形状通常与 [micro_batch, seq_len, hidden] 相关。

PP 的通信量不主要看参数量，而看 stage 边界 activation 大小和 micro-batch 数。通信量可粗略按：2 * 边界数 * micro_batch_count * T * H * bytes，其中前向一次、反向一次。

为什么要 micro-batch

回目录回项目

如果整个 batch 一次性走完 GPU0 再走 GPU1，后面的 GPU 会一直等，流水线有气泡：

  • PP 把 batch 切成多个 micro-batch。
  • GPU0 算 micro-batch 2 时，GPU1 可以算 micro-batch 1，尽量让各段都忙起来。

设 p 个阶段完全平衡，每阶段前向 tf、反向 tb，m 个 micro-batch。填满排空调度的完成时间：


T = (m + p − 1)(tf + tb)，   卡利用率 u = m/(m + p − 1)

m 项是真实计算，p−1 项是填充和排空的气泡。micro-batch 越多气泡占比越小，但全局 batch 不变时 micro-batch 变小，要和小矩阵的执行时间一起权衡。

代价

回目录回项目
  • 有 pipeline bubble，stage 越多、micro-batch 越少，空等越明显。
  • 层切分不均会让慢 stage 拖住全局。
  • 与 TP/DP/ZeRO 组合时，调度复杂，激活重算和通信重叠要一起考虑。

五种调度：时间轴和显存轴是两回事

回目录回项目

比较调度要看两根轴：完成时间（气泡大小）和显存峰值（每份激活要保存多久才等到自己的反向）。没有一种调度两根轴同时占优：

调度气泡主要代价
填满排空 fill-drain最大（先全部前向再全部反向）激活驻留最高，容量紧张时不可行
1F1B与 fill-drain 相同显存最省，但比 fill-drain 略慢约 3%
交错 1F1B（虚拟流水线）缩小到 1/v（v=每卡层块数）跨界消息翻倍以上
零气泡 Zero-Bubble把权重梯度 dW 填入空隙，下界可到 0靠后阶段激活保留更久
DualPipemicro-batch 两端相向注入每卡保存两份参数，参数量翻倍

关键结论：“1F1B 更好”只在显存轴上成立，在时间轴上反而略慢。所以先判断约束在时间还是容量，再选调度；容量紧张时先排除峰值不可行的，再比完成时间。

和我的项目怎么关联

回目录回项目

项目里 PP 不是主路径：

  • 用了什么能力（边界）：层切分 + stage 间激活/梯度传递 + micro-batch 填气泡，用于解释“层切分和激活传递”。
  • 解决什么问题：30B 级优先用 ZeRO/FSDP、TP、EP、AC/SAC；是否启用 PP 取决于层数、单卡显存、跨机拓扑和框架支持。
  • 达到什么效果（诚实）：当前没有 PP 启用的项目证据，答辩别声称“用了 PP”，用这张卡讲清和 TP/EP 的区别即可。

SP：把序列维度的层内激活拆开，降低激活显存

回目录回项目
03_concepts/sp_sequence_parallel.md

Sequence Parallelism（SP，序列并行）通常和 TP 配合，把某些按 token 独立计算的层（LayerNorm、Dropout、部分 residual）沿 sequence/token 维度切到不同 GPU 上，从而减少每张卡保存的激活。

解决什么问题

回目录回项目

TP 会把 hidden/channel 维度切开，但有些层不需要完整 hidden 矩阵常驻每张卡。SP 进一步把 token/sequence 维度上的激活分散保存，降低每张卡的 activation 峰值。它通常不是单独使用的“扩模型主策略”，而是 TP 的配套显存优化。

拆的是什么

回目录回项目

SP 拆的是 token/sequence 维度上的激活，不是参数。假设 hidden 是 [T,H]，SP=2：


GPU0: token 0..T/2 的 hidden

GPU1: token T/2..T 的 hidden

对每个 token 独立的操作可以直接在本卡算；但如果下一步矩阵乘或 attention 需要 TP 布局，就要做 all-gather/reduce-scatter 在 TP 布局和 SP 布局之间切换。

为什么有效：省的是“非 GEMM 层的激活”

回目录回项目

TP 只切 hidden/channel 维，但 LayerNorm、Dropout、residual 这类逐 token 算子每卡仍要过一遍完整 [T,H]，它们的中间结果每卡都存一份。SP 把 sequence 维也切开后：

  • 逐 token 算子的激活按 token 分片常驻：每卡只存自己那一段，峰值随之下降。
  • 不是省参数、也不省 GEMM 计算：专省“非 attention-heavy 层的激活”。

核心技术点

回目录回项目

SP 的核心不是切法，而是布局切换：SP 布局（token 分片）省激活，TP 布局（hidden 分片）适合 GEMM，两类算子在层内交替出现，所以要在两者之间 all-gather / reduce-scatter 切换。设计要点就是“哪一步用哪个布局、切换在哪发生、通信花多少”。

更易记的口径：AllReduce = ReduceScatter + AllGather，SP 只是把这两半拆到不同算子边界：

  • 进列并行线性层前 AllGather：把 token 分片收齐成完整序列布局。
  • 出行并行线性层后 ReduceScatter：求和后重新按位置分片。
  • 中间的 LayerNorm / Dropout / 残差：各卡只算自己的位置，不用每卡存一份完整激活。
  • 举例：[8192,4096] BF16 激活 64 MiB——四卡各存一段 → 每卡 16 MiB（合计 64）；四卡各存完整 → 256 MiB。省在“保持序列分片的那个区间”，不是所有激活都小四倍。

通信对象与方式

回目录回项目
  • 传的是什么：token hidden 激活或其梯度。
  • 通信方式：常见是 all-gather 拿完整序列布局，或 reduce-scatter 把结果重新切回序列分片。
  • 为什么传：不同算子需要的张量布局不同。SP 布局省激活，TP 矩阵乘可能需要按 hidden/channel 分片。

和 CP 的区别

回目录回项目

SP 和 CP 别混：

  • SP：节省 Transformer 层内非 attention-heavy 部分的激活显存。
  • CP：面向长上下文 attention，把上下文/KV 分布到多卡，解决单卡承载不了超长序列 attention 的问题。
  • 一句话：SP 是层内激活布局优化，CP 是长上下文 attention 计算组织。

CP / Ring Attention：把长上下文分段，让 KV 环形流动

回目录回项目
03_concepts/cp_ring_attention.md

Context Parallelism（CP，上下文并行）拆的是序列上下文。每张 GPU 只保存一段 token 的 Q/K/V 或 KV cache，通过环形通信让每段 query 逐步看到其它 GPU 的 key/value，从而支持超长序列 attention。

解决什么问题

回目录回项目

标准 attention 里每个 query token 都要和所有 key token 做相似度：

  • 序列长度 S 很大时，attention 的激活、KV 和计算都会爆炸。
  • CP 的思路：不要让每张卡都保存完整 S 的上下文——把 S 切成 N 段，每张卡保存一段。
  • 需要看全局上下文时，KV 分块在 GPU 间轮转。

怎么设计：把 S 切成 N 段，KV 环形传

回目录回项目

设 S=100k，CP=4：


GPU0: token 0..25k 的 Q/K/V

GPU1: token 25k..50k 的 Q/K/V

GPU2: token 50k..75k 的 Q/K/V

GPU3: token 75k..100k 的 Q/K/V

每张 GPU 的 query 负责本地 token，但 attention 需要所有 token 的 K/V。Ring Attention 让 K/V 分块一轮一轮传过来。


Round 0: GPU0 用 KV0，GPU1 用 KV1，GPU2 用 KV2，GPU3 用 KV3

Round 1: GPU0 收 KV3，GPU1 收 KV0，GPU2 收 KV1，GPU3 收 KV2

Round 2: 继续环转，直到每张 GPU 都看过所有 KV 块
  • 传的是什么：K/V 分块，或经过实现优化后的 attention 中间块；不是传完整参数。
  • 怎么传：相邻 GPU send/recv，形成环。每一轮本卡用当前 K/V 块计算本地 Q 的一部分 attention，再把 K/V 块传给下一张卡。

为什么能解决：单卡不用常驻完整上下文

回目录回项目

核心矛盾是“每个 query 都要看全部 key”，S 一大，KV 和 attention 工作区就爆显存。环形传 KV 后：

  • 每张卡只常驻 1/N 的上下文 K/V 和局部 attention 工作区，完整的 S 不再需要在任何一张卡上同时存在——超长序列从“放不下”变成“能训”。
  • 计算量没有凭空消失：全局 attention 仍是 O(S²)，只是被分摊到 N 张卡。CP 换的是显存峰值，不是总计算。

通信量与计算量

回目录回项目
  • 通信量：每张 GPU 要接收其它 N-1 份 KV 分块；每个 token 的 K/V 约 2 * H * bytes，单卡通信约 (N-1)/N * S * 2H * bytes，反向还有梯度或重算相关通信。
  • 计算量：全局 attention 仍是 O(S²)，不因 CP 减少；只是配合 FlashAttention/blocking 降低显存峰值，并用环形流水把通信和 attention block 计算重叠。

和我的项目怎么关联

回目录回项目

这是解释“长上下文 attention 如何跨卡”的底层能力卡，项目里的实际用法要分清：

  • 用了什么能力：把序列 S 切成 N 段，KV 分块在 GPU 间环形轮转，单卡只常驻 1/N 上下文。
  • 解决什么问题：超长序列 attention 的 KV 和激活在单卡放不下。
  • 项目落地边界：项目二长序列的实际落地更靠 CP-GSU（省 padding 算）和 SparseGroup（省坐标通信）；项目里是否真启用了 Ring Attention 待核验，答辩别声称“用了 CP”。

EP：把 MoE 的专家拆开，让 token 送到目标专家

回目录回项目
03_concepts/ep_expert_parallel.md

Expert Parallelism（EP，专家并行）拆的是 MoE 层里的 expert 网络。每张 GPU 只放一部分 expert，token 经过 router 选中 expert 后，需要通过 all-to-all 被送到对应 expert 所在 GPU；expert 算完后，再 all-to-all 送回原 token 位置。

解决什么问题

回目录回项目

MoE 模型想增加 expert 数量来扩大参数容量，但有两个“爆”要解决：

  • 每张 GPU 都复制所有 expert → 显存爆；每个 token 都跑所有 expert → 计算爆。
  • EP 的目标：expert 参数横向铺到多张 GPU，每个 token 只激活 top-k 个。
  • 代价：token 必须跨卡找 expert，all-to-all 成为核心通信。

MoE 里到底有什么

回目录回项目

一个 MoE FFN 可以理解成“很多个 FFN 专家 + 一个 router”：


输入 token hidden X [T,H]

  └─ router: 为每个 token 打分，选 top-k 个 expert

  └─ expert_0: 一个小 FFN

  └─ expert_1: 一个小 FFN

  └─ ...

  └─ expert_E-1

输出 Y：把选中 expert 的输出按 router 权重合并

expert 本身通常也是两层 MLP，例如 H -> intermediate -> H。EP 不等于 TP：TP 是切一个矩阵；EP 是把不同 expert 放在不同 GPU 上。

router 的口径分三步，最后一步按实现不同，要格外注意：

  • 打分：logits = x @ Wᵀ（[T,D]×[D,E] → [T,E]）。
  • 归一：专家维 softmax。
  • 选专家：top-k 选出专家编号和权重，再乘 route_scale。
  • ⚠️ 权重是否重归一化按实现不同：Qwen router 的 norm_topk_prob=True 会把选中的 top-k 权重重新归一成和为 1；UniAttention DeepSeek 风格是全专家 softmax 后直接取 top-k、不重归一（选中权重之和可能 <1）。比较两个实现前必须先固定这个开关，否则“专家编号一样”也不等于输出和梯度等价。

一个重要边界：MoE 只改变 FFN，不自动改变 Attention 或 PS。两件常被混的事要分清：

  • 本地融合（native/fused grouped GEMM）：单卡内“怎么让 token 过专家”的实现优化。
  • 专家并行（EP all-to-all）：跨卡“expert 参数放哪、token 怎么 dispatch/combine”。

拆的是什么

回目录回项目

设有 E 个 expert，EP=N。每张 GPU 放 E/N 个 expert。例如 E=8、EP=4：


GPU0: expert 0,1

GPU1: expert 2,3

GPU2: expert 4,5

GPU3: expert 6,7

每个 token 不会跑所有 expert，而是 router 选 top-k 个，例如 top-2。于是 token 可能原本在 GPU0 的 batch 里，却被 router 选中 GPU2 上的 expert 5，就必须跨卡发送过去。

怎么设计：dispatch → 本地算 expert → combine

回目录回项目

Step 1: 每张 GPU 持有一部分 token hidden

Step 2: router 在本地为这些 token 算 expert 分数，选 top-k expert

Step 3: 按目标 expert/GPU 对 token 分桶，得到 send buckets

Step 4: dispatch all-to-all，把 token hidden 发到 expert 所在 GPU

Step 5: 每张 GPU 对收到的 token 按 expert 分组，批量跑本地 expert

Step 6: combine all-to-all，把 expert 输出发回 token 原位置

Step 7: 对 top-k 输出按 router 权重合并，进入下一层

两次 all-to-all 传的都是 token hidden，不是 expert 参数：

  • Dispatch：把 token hidden 送到它选中的 expert 所在 GPU（带 expert id、原位置、router 权重等 metadata）。
  • Combine：expert 算完后把输出 hidden 送回 token 原位置（带合并 top-k 输出的位置信息）。

top-k=2 时，一个 token 被复制发给两个 expert，最后两个输出按 router 权重加权求和。

对象流向：router 为每个 token 选择目标 expert，dispatch all-to-all 把 token hidden 发到 expert 所在 rank，expert 计算后再通过 combine all-to-all 回到原 token 位置。

通信量怎么粗算

回目录回项目

设总 token 数为 T，hidden size 为 H，top-k 为 K，每个元素 bytes 为 b。

  • dispatch 传输的 hidden 总量约 T * K * H * b。
  • combine 再传一次 expert 输出，约 T * K * H * b。
  • 总 hidden 通信量约 2 * T * K * H * b，再加少量 metadata。

单卡看到的通信量取决于 router 分配是否均匀。负载均衡理想时每张卡约处理 T*K/N 个 expert-token；router 偏向少数 expert 时，某些 GPU 会收到远超平均 token，通信和计算都排队。

为什么 EP 能扩模型

回目录回项目
  • 每张 GPU 只放一部分 expert 参数，MoE 总参数量可以很大，但每个 token 只激活 top-k 个 expert，实际计算量近似按 K 个 expert 算。
  • expert 参数规模随 E 增长，但每 token 计算不随 E 线性增长，这就是 MoE 的“参数多、计算相对省”。
  • EP 让 expert 参数横向铺到多卡上，降低单卡 expert 参数显存。

为什么 EP 不一定快

回目录回项目
  • all-to-all 是不规则通信，受网络拓扑、token 分布、bucket 粒度影响很大。
  • top-k 越大，token 被复制到更多 expert，dispatch/combine 通信量线性增加。
  • capacity factor 太小会丢 token 或降级，太大又会 padding 和 buffer 变大。
  • router 负载不均会让某些 expert/GPU 成为 straggler。

native vs fused：单卡内“怎么让 token 过专家”

回目录回项目

同一模型（E、top-k、维度全同），只是 decoder_ffn_type 一个字段不同：

维度native（逐专家 for 循环）fused（grouped GEMM）
分发where/布尔索引，不排序permute 按专家排序成连续段
专家计算Python for 循环 E 次grouped GEMM：一次 kernel 算全部
kernel launchO(E) 次O(1) 次
合并y[idx]+= 散射累加unpermute（scatter_add 合 top-k 贡献）
权重布局每专家独立 Linear堆成 w1[E,D,2*inter]、w2[E,inter,D]

fused 的三阶段：

  1. permute：把乱序 token 按“要去的专家”重排成连续段，[T,D] → [T'=T×K,D] + offs + 逆映射。
  2. grouped GEMM：按 offs 分段，一次 kernel 内所有专家的 tile 并行铺满 GPU。
  3. unpermute：按逆映射把 [T',D] scatter_add 回 [T,D]，合并同 token 的 K 份贡献（不是简单撤销排序）。

w1[E,D,2*inter] 的来历：SwiGLU 把 gate+up 拼成一个 [D,2·inter]（2=两分支），再按专家堆 E 份。permute 是 grouped GEMM 的前提——先把 token 按专家排成连续段，才能按 offs 切段并行；代价是多两趟排序，换来并行净赚。

fused 快在两个层面：① 省 CPU launch（E 次 → 1 次）；② 小专家喂不满 GPU 的问题被“所有专家 tile 合起来一次调度”解决，Tensor Core 利用率高。数值上 fused 默认 bf16、native 可 fp32，数学等价但有舍入差。

FLOPs 口径（接 MFU 卡）：MoE 的 FFN 有效宽度 = k × 专家中间维，只按激活专家数 k 算，不按总专家数 E；grouped GEMM 和 native 是同一计算量的不同实现，不改变 FLOPs。

和 TP/DP 的关系

回目录回项目
  • DP：不同 GPU 处理不同样本，最后同步梯度。
  • TP：同一个 expert 或同一层矩阵内部再切矩阵。
  • EP：不同 expert 分布到不同 GPU，token 在 expert 之间分配。

实际 MoE 训练常组合使用：DP 复制 MoE 层副本，EP 分 expert，TP 切 expert 内部矩阵，ZeRO/FSDP 管 dense 或 expert 状态。回答时必须说清当前讨论的是哪一层切分，否则通信量会混在一起。

项目一稠密线用 EP 训 MoE：

  • 用了什么能力：EP 把 expert 横向铺到多卡，token 经 router 选 top-k 后 dispatch/combine all-to-all。
  • 解决什么问题：Qwen3-30B-A3B（总参约 30B、每 token 激活约 3B）参数显存放不下、全跑 expert 又算不动。

调度与重叠：不减少工作量，减少等待暴露

回目录
02_domain_map/layer5_scheduling_overlap.md

一句话

回目录

这一层回答“同样的通信、H2D、查表和计算，怎样排时间线才能少等”。它不改变模型数学、不减少必需字节数，核心是把可提前的工作放到当前计算背后，把串行等待变成重叠执行。

解决什么问题

回目录

很多训练瓶颈不是“总工作量太大”，而是工作排队顺序差：GPU 算完后等 H2D、等查表、等 all-to-all、等参数 all-gather。调度与重叠层要先问三个问题：

  1. 哪些工作有依赖：当前 batch 的前向必须等它的输入和参数工作集就绪。
  2. 哪些工作可提前：下一窗口样本读取、H2D、key 分发、Embedding 预取可以在当前窗口计算时做。
  3. 哪些工作能并行：DMA、host 线程池、网络通信、GPU SM、不同 CUDA stream/HCCL/NCCL stream 是否能同时推进。

所以这一层的收益不是“少传了多少”，而是同样要传的内容，有多少不再暴露在 step time 里。

算子与运行时：kernel 怎么被提交、怎么在 GPU 上执行

回目录

一句话结论

回目录

“算子”描述数学工作（矩阵乘、激活），kernel 在加速器上真正执行它，launch 是 CPU 发起这次执行的异步动作。优化分两条：缩短 kernel 执行时间，以及减少主机提交与等待——后者是小算子多、GPU 等 CPU 时的主瓶颈。

难点：提交是异步的，但计算要等数据就绪

回目录

CPU 提交后立即返回，GPU 按队列和依赖执行。提交是异步的，但计算要等数据就绪：数据何时传完、缓冲何时能复用，都要显式管理，否则会读到半成品、或覆盖还在用的数据。

怎么设计：三个机制

回目录

1. stream / event：执行顺序与缓冲复用

回目录
  • 同一条 stream 里任务按提交顺序执行：把 H2D 和读它的 kernel 放同 stream，计算自然排在复制后。
  • 跨 stream 用 event：复制流在 H2D 后 record 事件，计算流 wait 事件再读。
  • 缓冲复用的关键是“最后一次读写之后记录事件”：主机源缓冲在复制引擎读完后可写下一批；GPU 输入缓冲要在 kernel 用完才能覆盖。漏记一个“已用完”事件，复制引擎就永远等不到、程序停住（不是变慢）。

2. warp / occupancy / 延迟隐藏

回目录
  • warp 是 32 个线程一起发射的单位；线程块（block）由多个 warp 组成，SM 按 block 调度。
  • 驻留（residency）受三类资源限制：线程槽、寄存器、共享内存，取三者的最小值；occupancy = 驻留 warp 数 / SM 最大 warp 数。
  • 延迟隐藏靠驻留 warp 提供的在途请求：要达到 HBM 峰值带宽，需要 在途字节 ≥ 带宽 × 延迟（Little 定律）。工作集越大 → 驻留块越少 → 在途字节越少 → 有效带宽可能反而降。

3. 计算单元分工与 warp specialization

回目录
  • 矩阵单元按固定形状块执行 MMA（如 16×8×16，一条指令 4096 FLOPs）；向量单元做激活/逐元素。Hopper 的 warpgroup 级 MMA 异步执行，发出后能做别的。
  • warp specialization：生产者 warp 只发异步复制、消费者 warp 只做计算，用共享内存里的栅栏交接（“满”栅栏=复制完成，“空”栅栏=算完可覆盖）。FlashAttention-3 就这么安排 producer/consumer warpgroup。

为什么有效：缩短执行 + 减少等待

回目录

一次调用的耗时 = 提交 + H2D + kernel + D2H：

  • kernel 快了，提交和复制还在：例子里 kernel 从 20 μs 降到 5 μs，整次只从 35 μs 降到 20 μs（加速 1.75 倍），剩下 15 μs 是提交+复制。
  • 所以优化要么重叠（双缓冲、warp specialization），要么合并（减少小算子）。

诊断：停住 vs 变慢

回目录

停住 vs 变慢：程序完全不动，是在等一个不会到来的事件（漏记 event、跨流循环等待、或集合通信缺一个对端）；程序仍在出结果只是慢，是带宽/延迟问题，回到时间线逐段计时。

FlashAttention 解决什么

回目录回项目

标准 attention 会生成 [L, L] 的 score/probability，中间结果大、HBM 往返多。FlashAttention 的核心是分块 + online softmax：

  1. 按 tile 读 Q/K/V。
  2. 在片上维护行级 max/sum。
  3. 不把完整 [L,L] attention 矩阵写回 HBM。
  4. 反向时用保存的轻量统计量重算必要块。

关键口径：它不改变标准 attention 的数学目标，主要减少巨大中间表的 HBM 读写。

FA1 到 FA4 的演进

  • FA2：优化并行划分，增加 Q 维并行，减少 warp 间归并。
  • FA3：面向 Hopper，把 TMA 搬运和 WGMMA 计算做异步流水。
  • FA4：面向 Blackwell，继续处理非 MMA 瓶颈，例如指数、shared memory、TMEM 和前后向流水。

CompileMask / 编译优化解决什么

回目录回项目

CompileMask 是 UniAttention 自研的声明式 mask 编译栈：不是“一个固定 mask”，而是“写一条逐位可见性规则 (q,kv)→bool，自动编译成稀疏 attention kernel”。三层结构：

  1. frontend：声明式 mask 表达式（BoolExpr/MaskSpec AST），例 look_ahead 的组隔离规则。
  2. codegen：AST → TileLang kernel（含块跳过优化），并从 fwd mask 符号推导 bwd kernel。
  3. verifier：校验编译出的 kernel mask 与声明规则一致。

核心加速点不在布尔判断本身，而在“区间分析 → 块跳过”：

  • codegen 用 _DenseIntervalValue [lower,upper] 对 mask 规则做符号区间推导，推出每个 query 的可见 kv 落在哪些连续区间。
  • 把区间边界对齐到 block，生成“只循环这些 block、整块跳过其余”的 kernel。
  • 被 mask 的 block 连 QKᵀ 都不算（不是算了乘 0），这是 block-sparse 的本质。

一个例子（Label Packing 布局：prompt 2 位 + 组A 4 位 + 组B 4 位）：组B 的 query 对组A 的列整块不可见，codegen 识别“组A block 不在组B 的可见区间”就跳过该 block。

vs FlexAttention

回目录回项目

两者核心思路相同：都把逐位可见性编译成 block-sparse attention kernel、跳过全被 mask 的 block。差异在后端和推导方式：

  • CompileMask：codegen → TileLang，覆盖 NPU；编译期符号区间推导（精确）；bwd 从 fwd 符号推导独立 kernel；内置 verifier。自研动机正是 FlexAttention 的 Triton 覆盖不了 NPU。
  • FlexAttention：torch.compile → Triton，主 NVIDIA；运行时 create_block_mask 采样块角点判空；autograd 自动微分；score_mod 还能改分数（ALiBi/soft-cap）。

和 FlashAttention 的关系

回目录回项目

FA 的 tiling 决定“块内怎么算（online softmax，不落 [N,N]）”，CompileMask 的块跳过决定“哪些块要算（mask 区间）”——同一 tile 框架下的两件事，可叠加：既不存 N×N，又跳过被 mask 的块。

Label Packing 解决什么

回目录回项目

Label Packing 把多个目标（多 label / 多任务）拼进一条序列，让历史只编码一次，省历史侧的重复编码开销。但它引入一个新问题：拼进来的目标组之间不该互相看见（组隔离），否则 listwise 语义被破坏。

组隔离怎么做：

  • 普通 causal 隔离不了“后组看前组”；逐位算 mask 又太慢（N² 次判断，被 mask 的点仍算了 QKᵀ 再丢弃）。
  • CompileMask 用 look_ahead 的块跳过做组隔离——这是 Label Packing 的第二种实现（第一种业务 Collator 只拼不隔离）。

三个必须讲清的口径：

  1. 每组分别右移：teacher forcing 输入必须每组各自 BOS + 前 m-1 个目标，不能把多组先整体右移——否则当前位置的输入会直接带上另一组目标的真实 SID，即使 mask 屏蔽了跨组 attention，输入侧已经泄漏。
  2. 独立多目标 ≠ listwise：独立 Packing 训练多个 p(SID_j | history)，后目标不条件于前目标；listwise 是刻意训练 p(item_j | history, item_<j)。两者任务定义不同，不能把“多个商品拼起来”笼统叫同一种优化。
  3. 生产接线要分仓库看：OneRec 主 wrapper 构造 VarlenMetadata 时没有传 compile_mask（迁移指南标生产接线未完成）；但 custom_sft 业务路径已用 require_compile_mask=True 接上。所以准确说法是“OneRec 主干未接、custom_sft 业务已接”，不是笼统的“已完成”或“完全没接”。

MoE 融合和 Token 负载均衡

回目录回项目

MoE 层不只慢在 expert 计算，也慢在 router 分桶、dispatch/combine、padding 和很多小 GEMM。

  • MoE 融合（native → fused grouped GEMM）：native 是 Python for 循环逐专家算（O(E) 次 launch，单个专家 GEMM 规模小、矩阵单元利用率低）；fused 先 permute 按专家排序，再 grouped GEMM 一次 kernel 算全部（O(1) 次 launch），最后 unpermute 合并 top-k 贡献。权重堆成 w1[E,D,2*inter]（2=gate+up），减少 CPU launch，并把多个小 GEMM 组织成一次 grouped GEMM 来提高 Tensor Core 利用率。
  • Token 预算动态组批：按 token 数而不是样本数平衡 batch，减少某些 rank token 过多导致的 straggler。
  • 负载均衡：router 分布越均匀，EP all-to-all 和 expert 计算越容易同步结束。

CP-GSU 稀疏化：把 padding 稠密计算改成只算真实行为

回目录回项目
03_concepts/cp_gsu.md

一句话结论

回目录回项目

长行为序列为了 batch 化被 padding 到同一长度，但 padding 位置不是真实行为，不该占计算和显存。CP-GSU 把“对 [batch,max_seq,hidden] 全量 dense 算”改成“只对真实有效行为位置算”，冗余计算和显存都降下来。

难点：padding 被当成真实 token 冗余计算

回目录回项目

推荐长序列里，最长可能 10 万级，但很多用户真实行为远小于上限。旧方式按最大长度构造 dense tensor，所有位置都进算子——等于把 padding 当成真实 token 参与计算，既多算了、又多存了中间激活。

怎么设计：把稀疏索引当第一等公民

回目录回项目

不再物化 padding 后的 dense 张量，而是保留“真实有效行为”的位置/用户分组/序列 offset 索引 + 紧凑 value，算子只对有效位置做 gather / scatter / 聚合 / GSU 相关计算。代价是多一份索引元数据和更复杂的算子实现。

为什么有效：算的量和存的量都跟着真实长度走

回目录回项目

成本跟着真实长度走：

  • dense 成本约 B·S_max·H，稀疏约 B·S_real·H + index_metadata。
  • 当 S_real << S_max 时，冗余比例约 1 - S_real/S_max。

项目口径：减少 70% 冗余计算、显存 70GB→20GB、训练吞吐提升 70%。收益来自“少算 padding + 少存 padding 激活/中间结果”。

⚠️ 这是“思想能讲清、结构未逐行核验”的卡：全称、模型内位置、输入输出 shape 仍是 open 缺口，答辩时只讲机制与口径，不声称已核验具体实现。

和 SparseGroup 的区别

回目录回项目

SparseGroup 是通信压缩（共享坐标、少传重复结构），CP-GSU 是计算稀疏化（只算真实行为、少算 padding）。两者都依赖“稀疏索引是第一等公民”，但一个省通信、一个省计算，别混。

激活重计算（AC / SAC）：用算力换激活显存

回目录
03_concepts/activation_checkpointing.md

激活重计算（Activation Checkpointing，AC）不改变模型、不改变梯度数值，只把“反向要用的中间激活”从前向存下来，改成“反向要用时再重算一遍”。本质是用额外的前向算力，换掉激活显存。

解决什么问题

回目录

正常训练前向会把每层中间结果存着给反向算梯度用。激活显存 ∝ batch × 序列长 × 层数，层一多、batch 一大就 OOM。AC 让前向不存这些中间激活，反向时拿输入重跑一层现算，用完即弃。

它和 FSDP2/ZeRO 不是一回事：ZeRO/FSDP 分片的是参数、梯度、优化器状态；AC 省的是激活。两条是相互独立又相互依赖的生命周期——释放完整参数不等于释放激活。

拆的是什么

回目录

把“前向算出的中间结果”按是否值得保存拆开：

  • 边界输入：必须保留（反向重算的起点），通常很小。
  • 昂贵算子输出：matmul、attention 的 [N,N]、grouped GEMM，重算贵，倾向保存。
  • 便宜算子输出：silu、layernorm、add、mul 等逐元素算子，重算几乎不花时间，倾向丢弃。

核心流程（PyTorch 怎么实现）

回目录

torch.utils.checkpoint 本质是一个自定义 autograd.Function，核心两步：

  1. 前向在 torch.no_grad() 里跑：不建图、不存中间激活，只存最外层输入 x。
  2. 反向时 enable_grad 用 x 重跑一遍前向，这次正常存激活，立刻算梯度。

所以“重计算”不是 OneRec 自造，是 PyTorch 自带能力；OneRec 做的是把它按“逐算子 / 逐层 / 编译器预算”三种方式接进训练。

三档实现

SAC 的选择标准是“存贵的，重算便宜的”：matmul、attention（aten.mm、_grouped_mm、_scaled_dot_product_flash_attention）进保存名单，silu/norm/mul 重算。这样既省了便宜算子的激活显存，又不用为最贵的 GEMM 付重算代价。

MoE 的特殊处理：两个 grouped GEMM 只存一个

回目录

MoE 块有 gate_up 和 down 两个 grouped GEMM，都在保存名单里本该都存，但显存存不下两个，于是按收缩维挑一个重算：每单位重算省下的显存 ≈ 1/收缩维。

  • gate_up 收缩维 = hidden，down 收缩维 = moe_intermediate_size。
  • inter ≥ hidden → 重算 gate_up（Mixtral 类）。
  • inter < hidden → 重算 down（Qwen3-30B-A3B：768 < 2048）。

为什么不改变通信量

回目录

AC 是“本地算力 ↔ 本地显存”的权衡，和跨卡通信无关：

  • 保存名单特意包含 reduce_scatter_tensor（ZeRO 梯度通信算子）并标为“保存、不重算”：否则重算区域会重复触发跨卡 collective，白增通信、破坏集合通信语义。
  • MoE 的重算选择只在本地专家计算内，不碰 all-to-all。
  • 所以 AC 开关前后，ZeRO/MoE 的通信次数和量都不变。

HSTU：用 silu/N 代替 softmax 的排序侧 backbone

回目录
03_concepts/hstu_backbone.md

HSTU（Hierarchical Sequential Transduction Unit，Meta 提出、UniRec 自带实现）是 OneRec 排序侧的一个 dense backbone：它没有独立 FFN，激活融进 UVQK 投影，attention 用 silu(QKᵀ·α)/N 代替 softmax(QKᵀ/√d)。

解决什么问题

回目录

标准 Transformer 的 softmax attention 把注意力做成“行归一的概率分布”，但推荐排序场景里，一个历史行为对候选的贡献不必然是个概率——它更像“逐对相关性”。HSTU 用 silu（逐元素激活、可正可负、不跨位置归一）+ 固定 /N 缩放，把 attention 当成“相关性的加权”而不是“注意力概率”，更贴合排序侧语义。

拆的是什么：一层 HSTU 的五步

回目录
  1. 输入 LayerNorm：按 d_model 维归一。
  2. UVQK 融合投影 + silu + split：一个大 Linear(d_model, 2Dv·H+2A·H) 同时产出 user/value/query/key 四路，投影后整体过 silu。
  3. HSTU attention：silu(QKᵀ·α)/N 代替 softmax（核心差异）。
  4. gated 输出 norm：user * LN(attn)，user 路作门控逐元素控制 attention 输出放行多少。
  5. 残差投影：H·Dv → d_model，加回输入 x。

token 维 T 全程不变（变长拉平贯穿，JaggedData：values[T,d_model] + seqlen[B] + offsets[B+1]），只有特征维在 d_model ↔ H·Dv 之间变换。

HSTU 与标准 Transformer 的三处核心差异

回目录
  1. 无独立 FFN：silu 激活融进 UVQK 投影，不是单独的 feed-forward 子层。
  2. silu(QKᵀ·α)/N 代替 softmax：silu 逐元素激活（每行不归一到 1），/N 只做规模归一（序列越长项越多，除以 N 把量级拉回可比范围）；mask 非法位置直接乘 0（不走 softmax 的 -inf，因为没有指数）。
  3. gated 输出：user * LN(attn)，类似 GLU/SwiGLU 的门控思想。

为什么有效：把排序侧历史贡献当相关性而非概率

回目录

标准 softmax 会把一行注意力归一成概率分布，所有可见位置竞争同一个总量 1；HSTU 的 silu/N 不做跨位置归一，每个历史行为对候选的贡献可以独立放大、抑制或接近 0。这样更符合排序侧“多个历史行为可以共同提供相关性证据”的目标，同时 /N 控制序列长度变化带来的量级漂移。

计算对象与数值细节

回目录
  • 缩放系数 alpha = 1/√A（A=每头 QK 维，和标准 1/√d 同形）。
  • QKᵀ 和加权求和都升 fp32 再降 bf16，保点积精度。
  • attention 内部先 jagged→padding 成 [B,H,N,·] 算 QKᵀ，算完 dense_to_jagged 压回 [T,H,Dv]——padding 只活在 attention 中间，进来变长、出去也变长。

边界：HSTU 自身不引入跨卡通信

回目录

HSTU 是单卡内的 dense backbone，自身不引入跨卡通信：

  • 输入：UniRec 稀疏侧通过 Emb A2A 送回 sample rank 的 embedding 向量；输出：排序分数。
  • 跨卡通信发生在上游的稀疏查表/梯度回传和下游的稠密并行（TP/EP/ZeRO），不发生在 HSTU 这一层本身。
  • 融合 kernel 的 async wgrad 只在本地 stream 间重叠，不增加 collective。

mask：三层语义

回目录

_get_valid_attn_mask 产出 [B,N,N] 0-1 掩码，比标准因果 mask 多两层排序语义：

  1. 因果：对角 + 下三角可见（query 只看自己和历史）。
  2. 候选分组：num_targets + target_group_size，同组候选互见、跨组屏蔽（ranking 用）。
  3. 上下文：序列头部的 contextual token 可被全序列看到。

这三层对应 OneRec 序列结构：contextual（用户画像）+ history（历史行为）+ candidates（待排候选）。

融合版：五步融成一个 autograd.Function

回目录

生产用 FusedHSTULayerFunction，与 native 逐步等价但实现融合：

  1. LN+linear+silu 融成一个 kernel（addmm_silu_fwd），matmul 结果在片上直接过 silu，省一次 [T,4Dv] 往返读写。
  2. 手写 backward，不靠 autograd 自动微分。
  3. 重算省显存：forward 只存最小集合，backward 时重算 silu/qkv（recompute_input_layernorm），算力换显存。
  4. async wgrad：权重梯度在独立 stream 上异步算，和主反向重叠。

回目录

  • 用了什么能力：UniRec 查向量 → HSTU 算排序分数，用 silu/N 代替 softmax、UVQK 融合投影、三层 mask，生产走 FusedHSTULayerFunction 融合 kernel。

多硬件底座（Backbone Infra）：把 GPU/NPU 差异隔离开

一句话结论

回目录回项目

换硬件不只是换后端：算子、通信库、编译、精度、profiler 全都不同，直接把 GPU 代码搬上 NPU 会遇到算子缺失、编译入口不支持、精度分叉、归约顺序差异。Backbone Infra 把这些差异隔离在底座里，覆盖 T5 / T5-MoE / Qwen3 / DeepSeek-V4，业务只碰一层统一接口。

怎么设计：三条边界先分清

回目录回项目

多硬件底座不是“到处加 if npu”，而是把变化收在三条边界里：

  1. 路径边界：训练、生成、导出分开。训练一次处理已有目标前缀并反向；生成先 prefill 再逐 token decode；导出对齐在线推理。三条路径输入长度、cache 状态、控制分支不同，所以底座为训练和生成保留不同编译入口（enable_gen_compile 才建生成入口）。
  2. 模型边界：不同 backbone 的编译粒度不同。T5 整个 Backbone 作一个 torch.compile 入口；Qwen3 逐 Transformer Block 编译；两者都不包括 Reader、UniRec PS 和 DeepSpeed step，避免把数据/稀疏/优化器状态混进模型图。
  3. 硬件边界：GPU/NPU 差异只在底座层处理，包括算子替换、通信库选择（NCCL/HCCL）、精度策略、profiler 口径和 fallback。业务模型只调用统一接口，不直接感知具体硬件分支。

为什么有效：业务只碰统一接口

回目录回项目

三条边界分开后，问题定位也清楚：训练和生成结果不一致，先查路径边界；T5/Qwen3 编译表现不同，先查模型边界；GPU/NPU 数值或性能差异，先查硬件边界。这样业务换硬件、换底座不需要从零改，代价是底座要维护多套后端与适配逻辑。

训练约束与 MFU：别只看 GPU-Util，要看瓶颈资源

一句话结论

难点：为什么 GPU-Util 100% 不等于训练充分

回目录回项目

答辩里常被问“GPU 利用率 100% 是不是就充分利用”，答案是否定的：

  • GPU-Util 高，可能只是 kernel 一直在跑，却大量是 padding 或无效计算。
  • Tensor Core 忙，不代表有效 token/s 高。
  • 通信算子时间长，不一定是网络慢，也可能是慢 rank 让其它 rank 等。
  • 只有 MFU 高，才说明有效模型 FLOPs 接近硬件峰值。

怎么判断：先把瓶颈归到四类，再用 MFU 量化

回目录回项目

任何“慢/没吃满”都先落到四类资源约束之一，再决定上什么优化：

瓶颈典型表现典型入口
算力 compute-bound大 GEMM/attention 占主导，Tensor Core 吃得满本来高效；MoE grouped GEMM 凑大矩阵
显存 memory-bound参数/梯度/优化器状态/激活放不下ZeRO/FSDP、TP、PP、AC、稀疏 HBM–MEM
通信 communication-bound多卡传输/等待主导reduce-scatter/all-gather、EP all-to-all、稀疏 key/向量/梯度

判断时要把“传了什么”和“等了什么”分开：通信算子长，可能是真在传 bytes，也可能是在等慢 rank 到齐。

为什么有效：先归因，再量化有效计算

回目录回项目

GPU-Util 只能说明设备时间线上有 kernel 在跑，不能区分它是在做有效 token 计算、padding 冗余计算、通信等待，还是小 kernel 调度。先把瓶颈归到算力/显存/通信/供给四类，再用 MFU 量化有效模型 FLOPs 占硬件峰值的比例，才能判断优化是在提高真实训练效率，还是只是让卡更忙。

MFU 怎么算

回目录回项目

先分清三个词：

  • FLOPs（小写 s）：浮点运算个数（计算量）。
  • FLOPS / TFLOPS（大写 S = per Second）：浮点运算速度，T = 每秒 10¹² 次。
  • MFU：模型有效算力 ÷ 硬件峰值算力。

MFU = (一步理论 FLOPs / delta_time) ÷ 峰值 FLOPS × 100%

    = 实际 FLOPS / (峰值 TFLOPS × 1e12) × 100%

关键口径：

  • 分母用 Tensor Core 峰值（bf16），大头 FLOPs 都是矩阵乘、跑在 Tensor Core 上；silu/norm 等逐元素算子占比极小，不进分子也不进分母。B200/B300 峰值 = 2250 TFLOPS。
  • 一步理论 FLOPs ≈ 前向 ×3：前向一个线性层 Y=X·W 是 1 个矩阵乘；反向要算 2 个（dW=Xᵀ·dY、dX=dY·Wᵀ），大小都 ≈ 前向。
  • 矩阵乘基石：[M,K]×[K,N] = 2·M·N·K（2 = 一次乘 + 一次加）。

两类统计量对应两类 FLOPs

回目录回项目

varlen 训练把 batch 拉平成 [T,d]（无 padding，cu_seqlens 标边界），从真实 mask 累计两个统计量：

  • sum_n = ΣN_i（线性）→ 投影/FFN/lm_head ∝ N。
  • sum_n_sq = ΣN_i²（二次）→ attention ∝ N²，且是逐样本平方和，ΣN_i² ≠ (ΣN_i)²。

投影/FFN 每个 token 独立过权重 → ∝ N；attention 的 QKᵀ 让 token 两两交互 → ∝ N²。

MoE 的 FLOPs 按激活专家数 k，不按总专家数 E

回目录回项目

MoE 的 FFN 有效宽度 = k × moe_intermediate_size（k=每 token 激活的 top-k 专家数）：

  • 参数量用总专家数 E（权重都在显存）。
  • FLOPs/MFU 用激活数 k（每 token 只算 k 个）——这正是“参数多、计算省”的体现。
  • router 的 gate Linear 不计入 FLOPs。

在线版 vs 离线版

回目录回项目
  • 离线 mfu.py：参数、batch、seq_len 写死的手算脚本，只能单点估算。
  • 在线 FlopsCounter：用 VarlenStatAccum 从真实 mask 的 sum_n/sum_n_sq 算，精确反映变长/label-packing，训练实际用它。

从 MFU 推卡数下界

回目录回项目

总计算量 F、卡数 p、单卡峰值 P、平均计算效率 η、可用时间 T，则：


T = F / (p·P·η)，    p_compute = ceil(F / (P·η·T_available))

口径要分清：

  • 按完整迭代时间算：MFU 已经计入通信等待。
  • 只按加速器计算时间算：得到的是单卡计算效率，通信/气泡/重算/掉队者/checkpoint 要另外逐项加。
  • 参考：Llama 3 405B 在 8K–16K 张 H100 上 BF16 MFU 约 38%–43%（按整步耗时，已含通信）。
